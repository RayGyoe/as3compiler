# A native AOT compiler for ActionScript 3

Compile ActionScript 3 source code **ahead-of-time (AOT) into native machine code**, producing native executables — while keeping the AS3 syntax you already know.

Design philosophy: the compiler frontend only handles
`lexing → parsing → generating readable C`, delegating optimization and machine-code generation entirely to mature C compilers — no reinventing the wheel.

## Compilation pipeline

```
ActionScript source (.as)
        │  lexer.ts      lexical analysis (tokens)
        ▼
        │  parser.ts     recursive-descent parsing (AST)
        ▼
        │  codegen.ts    semantics + C code generation
        ▼
       C source (.c)
        │  build orchestration src/build.ts
        │  (build manifest JSON + -I/-L/-l/-D + --target)
        ▼
  ┌──────┴───────┐
  │ native        │  cc/clang -O2 -lm                 → native executable (Mach-O / ELF / PE)
  │ wasm          │  clang --target=wasm32-wasip1     → WASI .wasm
  └──────────────┘
```

"Generating a single readable `.c`" is the **default form** (simple to build, easy to read), not a law against linking third-party libraries:
when implementing heavy lifting such as graphics (skia/cairo/SDL), the correct approach is to **link** mature libraries (`-lskia`) rather than hand-rolling rasterization.
See "Build & Linking" and AGENTS.md §2.9.

## Running

Install (gives the `as-aot` command): `npm install -g as3compiler` (or locally `npm link`).

The installed command is **already-transpiled JavaScript** (`dist/`), so it runs on Node ≥ 18 and needs no type
stripping. In a **source checkout** the equivalent is `node src/index.ts ...` / `npm run compile -- ...` — that path runs
`.ts` directly and needs Node ≥ 22.18 (the version where type stripping is on by default; 22.6–22.17 additionally need
`--experimental-strip-types`).

`dist/` is generated before publishing by `scripts/build-dist.ts` (wired to `prepare`, so `npm pack` / `npm publish` run
it) — it converts `src/*.ts` to `.js` verbatim with Node's own `module.stripTypeScriptTypes()`, zero third-party
dependencies (AGENTS.md §3.1). **It is not optional**: Node refuses to strip types for files under `node_modules`
(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, a permanent loader restriction rather than a version gate), so pointing
`bin` back at `src/index.ts` makes **every** install crash on first run. The conversion blanks annotations in place
(line numbers map 1:1 onto `src/`, so stack traces still name the source), and the emitted C is **byte-identical** to
running the `.ts` directly.

**The npm package ships the compiler only** (`dist/` + `docs/`, about 2 MB compressed); it does **not** include the
third-party prebuilt libraries under `vendor/` (Skia / SDL2 / curl / sqlite) — plain C and WASI targets do not need them,
and only graphics / windowing / audio / networking / Stage3D targets do. Those libraries come with the **source checkout**;
`as-aot doctor` reports exactly what is missing (item, suggested command, remediation), and the recipes for rebuilding or
re-downloading them live in [`vendor/provision/`](vendor/provision/README.md); external fixtures are listed in
[`examples/EXTERNAL-FIXTURES.md`](examples/EXTERNAL-FIXTURES.md).

Requirements: Node ≥ 18 (to run the published `dist/`; running from source, or running `npm run build:dist` yourself,
needs Node ≥ 22.18), and a system `cc`/`clang`;
`--target wasm` needs the WASI SDK (`WASI_SDK_HOME` pointing at the SDK root, or an LLVM clang with a wasm32 backend),
and running the output requires a runtime supporting the exception-handling proposal (wasmtime/wasmer, see `docs/en/compile.md` §2);
`--target wasm --package web` needs the Emscripten SDK (`EMSDK_HOME` pointing at the emsdk root, see
`docs/en/html5-web.md`).

When a build will not start, run **`as-aot doctor`** first: it gathers every "what is missing" check from the
build path into one read-only report (`--air-app app.xml` trims it to what that app actually touches, `--json`
is machine-readable, `--fix` does sub-second idempotent repairs, and `--check-update` makes one **read-only**
registry lookup and prints the upgrade command -- it **never installs anything** and never moves the exit code),
and it shares **one check table** with the compiler -- what the report says is what a build says. See
`docs/en/compile.md` §3.6.

The version is **`as-aot --version`** (the same as `-V` or the `version` subcommand; the `doctor` header carries
it too). It has one source (`package.json`), so please include it in a bug report.

```bash
# Compile (default output: a file named after the input without extension, keeping the generated .c for reading)
as-aot examples/hello.as

# Compile and run
as-aot examples/fib.as --run

# Specify output name / specify the C compiler
as-aot examples/class.as -o build/class --cc clang --run

# Generate a macOS .app Xcode project (--package xcode-project: open/build/debug in Xcode, product is an .app)
as-aot src/Main.as --target native --package xcode-project -o build/Main

# Generate a browser HTML5-rendered page (--target wasm --package web, requires the Emscripten SDK)
as-aot examples/web/hello-web.as --manifest examples/web/hello-web.build.json
```

## Build & Linking

> Full compilation instructions (CLI arguments, build manifest JSON, multi-target backends, WASI toolchain) are in
> [`compile.md`](docs/en/compile.md).

Supports multiple targets and linking third-party libraries:

```bash
# WASI target (requires the WASI SDK or a clang with a wasm32 backend)
as-aot examples/hello.as --target wasm

# Link third-party libraries (skia/cairo/SDL etc.): include paths / library paths / libraries / macro definitions
as-aot app.as -I vendor/include -L vendor/lib -l skia -D USE_SKIA=1

# Embed bitmap asset classes and skin text from an SWC (stage ninety-five / one hundred forty-nine): named
# assets become BitmapData subclasses (`new logo(0, 0)`, or getDefinitionByName("logo") then new);
# DefineEditText text characters bake into real TextFields (initial text + font/size/color/align/indent/leading)
as-aot app.as --swc assets/skin.swc

# Build manifest (JSON, paths resolved relative to the manifest directory)
as-aot app.as --manifest examples/skia-link.build.example.json

# The text layout stack is linked only when the program uses flash.text; a program that draws no text
# automatically drops the whole SkParagraph/HarfBuzz/ICU chain (measured 19.43 MB -> 6.53 MB, stage 221;
# the build prints the + / - verdict). Links also carry -Wl,-dead_strip -Wl,-x (symbols kept under
# --debug-info), and ICU data is the 0.80 MB set: 3.55 MB text-free / 6.05 MB with text (stage 222)
as-aot notxt.as --manifest examples/draw-over.build.json

# Load AIR native extensions (ANE, stage one-hundred-seventy-eight): the host FRE runtime is wired in,
# and the rebuilt ANE plus the host library (asaot.dll / libasaot.dylib) land under
# <exe directory>/extensions/<extID>/<platform>/
as-aot app.as --manifest app.build.json --ane lib/WinCore.ane
as-aot app.as --manifest app.build.json --ane lib/WinCore.ane --ane-platform Windows-x86-64

# AIR projects: extensions need not be spelled out with --ane — the descriptor's <extensions> decides (stage one-hundred-eighty)
# Packages are looked up by ID under <appDir>/ext-aot, <appDir>/lib and <appDir>/ext-folder, and the result is written into <filename>.build.json
as-aot --air-app app.xml
as-aot --air-app app.xml --extdir vendor/anes    # look somewhere else (repeatable, overriding the three defaults above)
# Declared but not found ⇒ hard error (the adl policy), never a silent extension shortfall
# An extension rebuilt into its AOT form goes in <appDir>/ext-aot/<name>/ (ordered ahead of the default roots, stage one-hundred-eighty-two) —
# it declares the same <extensionID> as the AIR original and the winner is decided by root order rather than directory-name sorting; anything not rebuilt still comes from lib/

# Export top-level functions for direct JS calls (default WASI command modules only export _start)
as-aot examples/wasm-native/fib.as --target wasm --export fib

# Declarative exports: mark functions/static methods with [WasmExport] metadata to auto-export and generate .exports.json
as-aot examples/wasm-native/export-meta.as --target wasm

# Generate a browser HTML5-rendered page (--target wasm --package web, requires the Emscripten SDK)
as-aot examples/web/hello-web.as --manifest examples/web/hello-web.build.json

# Only generate C and print the compile command, without actually compiling (verify the command without a toolchain)
as-aot examples/hello.as --target wasm --dry

# Keep debug info: all three backends add -g, and wasm's default DWARF stripping is turned off (source-level debugging in DevTools)
as-aot examples/wasm-native/fib.as --target wasm --debug-info

# Window GPU backend (Windows only, and only for a window compiled with <renderMode>direct/gpu):
# auto (default) = D3D12, gl switches to WGL/OpenGL (system opengl32, no d3d12.dll). Frame time is the
# same either way (the submission path is what GL saves, ~1.1-1.3 ms/frame); `auto` clears a persisted choice
as-aot --air-app app.xml --gpu-backend gl
```

**Window GPU backend (`--gpu-backend`, stage 271)**: Windows has two window compositing backends — the default **D3D12**
(needs Win10 1507 + WDDM 2.0, no answer on Win7) and the newly landed **WGL/OpenGL** (system `opengl32.dll`).
`auto` falls back `D3D12 → GL → CPU`. The choice **cannot live in the AIR descriptor** (the XSD's `<windows>` is an
`xs:all` of four elements with no `xs:any` anywhere; `adt -package` rejects `<gpuBackend>` with error 103, and four
different foreign-namespace spellings all report 103 too; `adl` staying silent is not schema acceptance), so it travels
in **our generated manifest** as `gpu-backend`, which AIR never reads — the same road as `features`. Precedence:
`--gpu-backend` > the value persisted in the previous manifest > `ASC_GPU_BACKEND` (prototype alias, says so when it
loses) = `auto`. Five impossible combinations (no `--air-app`, web, non-Windows host, descriptor compiles no GPU
window, Stage3D) are **refused at build time** rather than looking honoured. Details in
[`compile.md`](docs/en/compile.md) and [`win32.md`](docs/en/win32.md) §3.1.1.

**ANE loading (stage one-hundred-seventy-eight)**: `--ane` / the manifest's `ane-paths` switch on `ASC_HAVE_FRE` and wire in the host FRE runtime.
Each entry may be an `.ane` package **or an unpacked directory** (`extension.xml` + `<platform key>/<native library>`, i.e. `adt`'s staging layout) —
the latter is the default form of the artifact rebuilt for AOT: its native library imports the host library (`asaot.dll` on Windows, `libasaot.dylib` on macOS, which forwards into **the generated program's own table**),
AIR has no such table, so it **cannot be loaded whether it is signed or not** and there is no consumer for a packaged one; the `library.swf` that an `.ane`
requires is dead weight too (`DoABC` is outside the compiler's scope and an extension's AS3 classes must be compiled from `.as` sources). An original signed `.ane` still reads fine (the `META-INF/ANE/` layout).
The host library `lib/bin/<platform>/asaot.{dll,dylib,a}` (header `lib/asaot.h`, **byte-for-byte ABI-aligned** with the AIR SDK's `FlashRuntimeExtensions.h`)
is a **thin forwarder**: all 51 FRE entry points go back through the `AsaotHost` function table to **the generated program's own** implementations,
so AS3 semantics has exactly one heap and one class registry. `lib/` holds only **hand-written sources** (the `asaot.h` contract, the `asaot_host.c` implementation,
the `build-asaot.bat` / `build-asaot.sh` recipes) and build products land per platform under `lib/bin/` (e.g. `lib/bin/windows-x64/`):
`-I` points at `lib/` and `-L` at that platform subdirectory — the header is one contract shared by all platforms, the import library is one platform's product.
Platform directory names are lowercase (`windows-x64`/`windows-x86`/`macos-x86-64`…), the same convention as `vendor/sdl2/lib/windows-x64` and
`vendor/curl/lib/windows-x64`; they are **not** AIR's platform keys verbatim (those are the names of ZIP subdirectories inside `extension.xml` and are handled separately by `ane-platform`).
The macOS cell **follows AIR's key spelling** (`macos-x86-64`), because **macOS's key does not encode the architecture**: the SDK's macOS runtime is a single universal binary
(two slices, `x86_64`+`arm64`) and the ANE-loader key is the same `MacOS-x86-64` in both slices (measured) — the architecture lives in the `.dylib`, so darwin's two architectures derive **the same key**,
and `MacOS-AOT` is not an AIR key (0 hits across the whole SDK), so no such directory is created.
The host library now exists for **two** platforms: Windows (`lib/bin/windows-{x86,x64}/asaot.dll` + `asaot.lib`) and macOS (`lib/bin/macos-x86-64/libasaot.dylib`, **a universal binary by default** -- the `MacOS-x86-64` key does **not** encode an architecture, and AIR's own macOS runtime is universal). `lib/build-asaot.sh` builds the macOS one (`--platform native` gives the host architecture only, for the edit/build loop) and **inspects the artefact** rather than trusting its own flags: the install name must be the relocatable `@executable_path/libasaot.dylib` (both slices agreeing), `asaot_bind` must be exported, 53 exports, no `Adobe AIR` dependency -- because an absolute-path install name **works on the author's machine and fails to load anywhere else**, while the build says nothing at all. The only platform still missing is **iOS**: it links extensions **into the application image** with no `dlopen` step, so there is no loadable host library to produce; `aneHostLibName()` **throws and explains** rather than borrowing the macOS name. Any other platform without a host library gets a build that **errors out directly, quoting that path** rather than looking for something never built.
`build-asaot.bat` **builds both widths by default** (`bin/windows-x86/` and `bin/windows-x64/`), and `build-asaot.bat x86` / `x64` rebuilds just one; an unknown argument **errors out** (no silent skip).
Which width is used is decided by `--ane-platform`, and the extension package declares its own platforms, so defaulting to "build only this machine's width"
would mean `--ane-platform Windows-x86` could be satisfied by a 64-bit host library — exactly the failure mode this default removes.
The two widths differ only in a `--target` triple (`asaot_host.c` is width-independent forwarding code), and the script ends with `findstr` verifying that the import library really is keyed on `asaot.dll`:
that failure is completely silent at build time (the import library `llvm-lib /DEF:` produces has an **empty** module name) and only shows up much later as "the rebuilt ANE still wants `Adobe AIR.dll`". Both widths are then **inspected as artefacts** (the same set of assertions `build-asaot.sh` makes on macOS): `asaot.dll` must export `asaot_bind`, its PE export count must be **exactly 53** (51 FRE entry points + `asaot_bind` + `asaot_is_bound`), and it must **not** import `Adobe AIR.dll` — a host library with the right name but the wrong contents still builds and links cleanly, and only explodes when some extension is loaded.
**Why Windows ARM64 is not in there**: AIR has no Windows ARM runtime — each of AIR SDK 51.4.1's two Windows runtimes recognizes **exactly one** platform key
(`win/`'s `Adobe AIR.dll` carries only `Windows-x86`, `win64/`'s only `Windows-x86-64`, and together those are the whole set of two), and the SDK ships only those two Windows runtimes
(the arm64 items in the release notes are Linux/iOS/macOS only). So no extension can declare an ARM64 Windows slice and no runtime will look for one: on Windows-on-ARM AIR itself runs the **x64 build** (under emulation) and still uses the x64 host library.
Hence `lib/bin/` **deliberately has no** `windows-arm64` (a library nobody can load is not "support", it is inventory), the host-width set is a **closed set** at this point, and on Windows ARM64 `as-aot --ane` **errors out directly** telling you to pass
`--ane-platform Windows-x86-64` (with `architecture: "64"`), rather than guessing at a key AIR has never had.
(The dependency script `vendor/provision/windows.ps1` does have `-Arch arm64`, but that is for **non-AIR** Windows-on-ARM artifacts and corresponds to no ANE platform key; `both` still means x64+x86 only. See [`docs/en/win32.md`](docs/en/win32.md) §2.11.)
The complete loading protocol is implemented in the generated program: at **compile time** `extension.xml` is parsed
and the platform entry fixed → in a **post-link stage** the ANE's native library and the host library land under `<exe directory>/extensions/<extID>/<platform>/` →
at runtime `LoadLibraryA` + `GetProcAddress(<initializer>)` → dispatch through `FRENamedFunction[]`.
The key prerequisite: **the ANE must be the version rebuilt against `asaot`** (its FRE imports must resolve to the host library, not to a hard-coded
`Adobe AIR.dll` — the latter is the module name AIR's own import library records and must not be used as our product's name); nothing about this affects `adl`, which keeps using the original ANE, and the two do not interfere.
`ExtensionContext` is modelled on AIR: `createExtensionContext` / `call` / `dispose` / `getExtensionDirectory` /
`actionScriptData` + asynchronous `StatusEvent` dispatch; AIR has **no** `extensionID` property (measured: `mxmlc` rejects it, `adl` reports `Error #1069`), and this runtime has none either — we do not invent an extra property just to "look more complete".
The rendering pipeline (`FREGetRenderMode` / `FRESetRenderSource` / `FREMediaBuffer*` / native window handles) is **not implemented in this phase**:
only stubs are exported and they **report loudly** when called, never silently returning a fabricated render mode.

**The complete procedure for migrating an existing ANE** (dual products + rebuild-with-renaming, the shim header, the three project properties, a symptom→cause table, and the full list of gaps) is in
[`docs/en/ane.md`](docs/en/ane.md); the smallest runnable loop is in [`examples/ane/`](examples/ane) (46 assertions, naming the package on the command line / in a manifest; **it really runs on both Windows and macOS**, and on macOS it loads a genuine `dlopen`ed `ProbeANE.dylib`) and
[`examples/ane-app/`](examples/ane-app) (8 assertions, going through `--air-app` + the descriptor's `<extensions>`).
A rebuilt product is a **staging directory tree** (`extension.xml` + `<platform>/<library>`, unpackaged); dropping it into `<appDir>/ext-aot/<extension id>/`
makes it get picked up automatically, so `adl` keeps using the original ANE and the two paths do not interfere.

Build manifest (JSON) fields: `target` (`native`/`wasm`), `package` (`raw`/`xcode-project`/`android-project`/`web`,
default `raw`, see `compile.md` §6), `c-compiler`, `opt`, `debug-info` (keep debug info, default `false`, see below),
`sources` (additional C/C++ sources),
`include-paths`, `link-libs`, `link-paths`, `defines`, `c-flags` (flags handed verbatim to the C compiler; CLI spelling `--cflag <f>` / `-w`, applied to every compile and link step), `objects` (precompiled `.o`), `exports` (C symbols exported to the .wasm export table),
`ane-paths` (a list of `.ane` paths to load, see "ANE loading" above), `ane-platform` (overrides the platform entry name,
derived from the build target by default, e.g. `Windows-x86-64`),
`swc-paths` (a list of `.swc` libraries; their **named bitmap assets** are extracted at compile time, re-encoded to PNG after un-premultiplying,
and embedded into the product, decoded by Skia at runtime; a `DefineBitsJPEG3`'s **separate alpha plane** is in turn decompressed at compile time
and composited with the JPEG at runtime, without which its transparent area paints as a black rectangle; **vector shapes and display trees** (`DefineShape*`/`DefineSprite`/`PlaceObject*`) as well as
**nine-slice** (`DefineScalingGrid`) and **button four-states** (`DefineButton2`) are likewise baked at compile time into runtime drawing calls —
**a symbol's own timeline script (`DoABC` frame script) is also decoded into an AST at compile time and reuses the same emitter** (`this.stop()` / `buttonMode` /
`addEventListener` + the `_self` closure / the `gotoAndStop` ternary etc.; unsupported bytecode shapes are **reported loudly**, never silently), so a control like
`agreebtn` whose "checked state lives in the skin" really does change frames under AOT —
see `docs/en/swc.md` §5/§6/§9),
`font-urls` (font byte-stream URL list for `--package web`, injected into Skia at runtime),
plus the `xcode-project` app metadata `bundle-id`/`display-name`/`icon`/`deployment-target` (see `compile.md` §6.4). CLI arguments override manifest fields of the same name.
Path-like fields resolve relative to the manifest file's directory. Example at
[`examples/skia-link.build.example.json`](examples/skia-link.build.example.json).

**Per-target layered linking (`targets`)**: top-level fields are the common defaults; a `targets.<native|wasm>` block applies only to the **matching target**
and **replaces wholesale** (replace, not append) the same-named top-level values — so **one manifest** can serve multiple targets with mutually exclusive link sets
(the typical case: native links curl, but WASI has no sockets and `-lcurl` makes `wasm-ld` fail, so it must be dropped for wasm). Merge order:
default configuration → manifest top level → manifest `targets.<final target>` → CLI overrides. Example
[`examples/flash-net-layered.build.example.json`](examples/flash-net-layered.build.example.json), see `compile.md` §4.1.

**Debug info (`--debug-info` / manifest `debug-info`, off by default)**: by default the product carries **no DWARF on any of the three backends** — native under `-O2`
has none anyway; `emcc -O2` strips it itself; only the **wasi backend**'s `libc.a` ships DWARF and `wasm-ld` keeps it by default (even an empty
`int main` drags in ~19 KB), so the wasm link adds **`-Wl,--strip-debug`** by default (`fib.wasm` 421 KB → **133 KB**; only `.debug_*` is dropped,
the `name` function-name section is kept ⇒ traps still print symbolized stacks). Turning on `--debug-info` adds `-g` to all three backends and stops
stripping wasm (`fib.wasm` ~640 KB, containing line numbers of the C we generate ⇒ source-level debugging in DevTools).


## Supported language subset

| Category | Supported |
|------|------|
| Types | `int`, `uint`, `Number`, `Boolean`, `String`, `void`, `Array`, `Vector.<T>`, `Function`, `RegExp`, `Class` (class reference), `Dictionary` (object-reference-keyed associative table), `*` (untyped → dynamic `any` boxing), class names (object types), interface names |
| Literals | integer, float, hexadecimal (`0xFF`), string (single/double quotes), `true`/`false`, `null`, `Infinity`/`NaN`, array literal `[...]`, object literal `{ ... }` (**keys may be numeric**: `{0: "a"}`, stage 106), **E4X XML literal** `<a b="1">…</a>` (nested/self-closing/attributes/comments/CDATA, stage 106; `{expr}` interpolation is **loudly rejected**), regex literal `/pattern/flags`, Vector literal `new <T>[...]` |
| Expressions | arithmetic `+ - * / %`, comparison `== != < <= > >=`, logical `&& \|\| !`, unary `- + ! ~`, bitwise `& \| ^ << >> >>>`, increment/decrement `++ --` (prefix/postfix), ternary `?:`, **null coalescing `??`** (lowest precedence, short-circuit, the left side is only hoisted into a boxed temporary when necessary, stage 106), **comma operator** `(a, b)` (lowest precedence, result is the right operand, stage 106), **E4X descendant axis** `x..name` / `x..*` (pre-order, excluding self, stage 106), **E4X computed names** `x.ns::[expr]` (child axis ⇒ `XMLList`) and `x.@[expr]` (attribute axis ⇒ `String`) (stage 108; the `ns` qualifier folds per "namespace transparency"), type checks `is` / casts `as` (supporting dotted fully-qualified names), coercion syntax `Type(expr)` (**split by class**: the native Error family (`Error`/`TypeError`/…/`SecurityError`), `RegExp` and `Namespace` **construct** (equivalent to `new`); every other class — including `flash.errors.*` and user `Error` subclasses — is a **runtime-checked coercion** — `null`/`undefined` → `null`, an instance of the class or a subclass → that very instance, otherwise `TypeError #1034`. It must **never** be emitted as a C pointer cast: before the fix `Error("msg")` boxed a string body as an object and the first `catch (e:Error)` read it as a vtable and crashed; stage one hundred and fifty-two), `typeof`, `delete`, membership `in`, array indexing `a[i]`, property access `o.x`, compound assignment `+= -= *= /= %= <<= >>= >>>= &= \|= ^=`, logical assignment `\|\|= &&=` |
| Statements | variable declarations (including multiple `var a:T, b:T, c:*;`), expression statements, `if/else`, `while`, `do-while`, `for`, **`with (obj) stmt`** (object members as the innermost scope), `for-in` (array indices / dynamic object keys / `Dictionary` object-reference keys), `for-each-in` (including the bare-identifier iteration form with `var` omitted), `switch/case/default`, `break`, `continue`, labeled statements `label: while(...){ break label; }`, `return`, `throw`, `try/catch/finally` (**multi-branch catch** `catch (e:A) … catch (e:B) …` matched in source order, clearing `as_exception` on a hit, rethrowing if none match, stage 106; **clauses are filtered by declared type** — measured on AIR, `catch (e:Error)` does **not** catch `throw "oops"`; only `catch (e:*)`/`catch (e:String)` do. ## Beyond AIR (enhancements, non-alignment)

Our product is a readable C file handed to `clang -O2`, able to link Skia/libcurl/SQLite, benefit from LTO/PGO, interoperate with host C,
and compile to native/WASI/web — so we can add enhancements where AIR **does not define / does not support / has no counterpart** (enhancements must be opt-in
and never silent). The criterion: the same input that `adl` runs correctly but we cannot ⇒ a legacy defect; something `adl` already errors on or an API that does not exist ⇒ an enhancement.

**Implemented (8 / 19)**:

- **Display refresh-rate query** — `VsyncStateChangeAvailabilityEvent` gains a read-only `refreshRate:Number` (AIR has no refresh-rate API at all; the read-only `available` is measured to be constantly `false`)
- **Multi-format image decoding** — WebP / BMP / ICO (`--features formats`; default reports `#2124` just like AIR)
- **Camera RAW / DNG** — `Loader.load("*.dng")` yields an image directly (`--features raw`, native)
- **SVG runtime decoding** — `Loader.load("*.svg")` → `Bitmap` (`--features svg`, native)
- **64-bit integers** — `int64` / `uint64` (AIR has no such type name)
- **LTO / PGO build switches** — manifest `lto`/`pgo`, CLI `--lto`/`--pgo`
- **Exit with a status code** — `System.exit(code)` (AIR's runtime throws `#2018`)
- **macOS menu-bar status item** — `SystemTrayIcon` behind a real `NSStatusItem` (`--features tray`; AIR on macOS has `supportsSystemTrayIcon=false` and throws `#2012` on construction)

The full 19-item list (the rest being Lottie, native shaders, FFI, server-side rendering…) and the five criteria are in
[`docs/en/enhancements.md`](docs/en/enhancements.md).
