# D3D11 与 D3D12：我们为什么落在 D3D12，以及什么时候才该碰 D3D11

> **状态：决策记录 + 机制对照，本次无代码改动、不改版本号。**
>
> **触发**：两次追问——①「GPUI 为什么用 D3D11？」（见 [`gpui-windows-renderer.md`](gpui-windows-renderer.md)）；
> ②「我们当时为什么选 D3D12 而不是 D3D11？我也发现大量其他应用使用 D3D11？」
>
> 本文要回答的是**三件事**，顺序不能颠倒：
>
> 1. **当初为什么是 D3D12？** ——不是性能，是**两条硬约束**：Skia 在 Windows 上只有 D3D12
>    一条 Direct3D 后端；Stage3D 必须与 2D 合成**共用同一个 device 和同一条队列**（§1）。
> 2. **D3D11 免费给的东西，我们手写了多少？** ——逐条列清，每条都给出 D3D11 的对应物与我们的
>    阶段/证据（§3）。这部分是"D3D11 省事"这句话的**具体内容**。
> 3. **什么条件下才该回头加 D3D11？** ——三条具体触发，其中两条的**正解不是 D3D11**（§6）。
>
> 一句话结论：**D3D12 是我们能用的唯一选择，不是我们挑中的最优选择；而 D3D11 的优势恰好是我们
> 已经用别的办法付过账的那部分。**

---

## 0. 结论速览

| 问题 | 结论 | 证据 |
|---|---|---|
| Skia 能用 D3D11 吗？ | **不能**。Ganesh 的 Direct3D 后端只有 D3D12：`GrD3DBackendContext` 里是 `ID3D12Device`/`ID3D12CommandQueue`，全部源码零 `ID3D11Device` | §1.1 |
| 那 2D 必须 D3D12？ | 是。除非改走 GL（WGL，`--gpu-backend gl`）或引入 ANGLE 把 GLES 翻译到 D3D11 | §1.1 |
| Stage3D 为什么也 D3D12？ | 为了**共 device + 共 queue**：3D 后缓冲就是 Skia 能直接包的 `ID3D12Resource`，零拷贝零跨设备同步 | §1.2 |
| 我们主张过 D3D12 更快吗？ | **从未**。唯一同机对照是 4.9 ms（D3D12 flip）vs 4.5 ms（D3D11 bitblt），差别主要来自 **flip vs blt** 而非 API 代次 | §4 |
| 别人为什么用 D3D11？ | 它们没有我们这两条约束：要么自绘（GPUI）、要么经 ANGLE（Chromium/Flutter）、要么默认自研 RHI（Qt 6） | §5 |
| 现在最该补的 D3D11 式能力是什么？ | 不是 D3D11，是**软件光栅回退**（虚拟机/RDP 里我们直接失败）。最小改动是 D3D12 **WARP**适配器，不是换 API | §6 |

## 1. 两条硬约束

### 1.1 Skia m124 只有 D3D12 一条 Direct3D 后端

```c
// vendor/skia/include/gpu/d3d/GrD3DBackendContext.h:28
struct SK_API GrD3DBackendContext {
    gr_cp<IDXGIAdapter1> fAdapter;
    gr_cp<ID3D12Device> fDevice;            // ← D3D12
    gr_cp<ID3D12CommandQueue> fQueue;       // ← D3D12
    sk_sp<GrD3DMemoryAllocator> fMemoryAllocator;
    GrProtected fProtectedContext = GrProtected::kNo;
};
```

- `vendor/skia/src/gpu/ganesh/` 下的图形后端目录是 `d3d`（内容全是 `GrD3D*`，即 D3D12）、`gl`、`vulkan`、`mtl`
  ——**没有 d3d11**；
- `grep -rl ID3D11Device vendor/skia/src vendor/skia/include` **零命中**（全仓唯一出现处是 ANGLE 的
  `third_party/externals/angle2/include/CL/cl_d3d11.h`，那是 OpenCL 互操作头，与绘制无关）；
- 我们写 `vendor/d3d_glue.cc` 时是照 Skia m124 自带的参考实现逐步骤来的：
  `tools/window/win/D3D12WindowContext_win.cpp` + `D3DTestUtils.cpp::CreateD3DBackendContext`
  （`TODO.md:7844`，阶段一百二十六）。

**即：D3D12 是 Skia 在 Windows 上的参考路径，也是唯一路径。** "Skia + D3D11"这个东西不存在。

剩下的 D3D11 可能性只有两条，都要额外付代价：

| 路径 | 代价 |
|---|---|
| GL（我们已有的 WGL 路径） | 不是 D3D11，但能在老系统上跑；**不能带 Stage3D**（§1.3） |
| ANGLE（GLES → D3D11） | 引入一整个大依赖 + 语义转换层；与「链接成熟库、生成可读 C」的取向更远；还要自己解决 GL 侧的 Stage3D |

### 1.2 Stage3D 跟着走，是为了共设备

```c
// vendor/stage3d_d3d.cc:1315
// The device and queue come from d3d_glue.cc when the window GPU backend is
// linked (so the composite and Stage3D share one queue), and are created here
// otherwise -- a headless app that only ever reads its render target back.
static int s3d_init_backend(S3DContext* c) {
  SkD3DDeviceFn devFn = (SkD3DDeviceFn)s3d_lookup_export("sk_d3d_shared_device");
  SkD3DQueueFn  qFn   = (SkD3DQueueFn)s3d_lookup_export("sk_d3d_shared_queue");
```

`vendor/d3d_glue.cc:685-686` 把 `ID3D12Device*` 与 `ID3D12CommandQueue*` 导出给 Stage3D 后端用。
收益是具体的：

- Stage3D 的后缓冲就是 Skia 能直接包的 `ID3D12Resource` → `GrBackendTexture` →
  `SkImages::BorrowTextureFrom`，**同设备同队列，零拷贝**；
- 不需要跨设备共享纹理（NT handle）+ 每帧整帧 copy + fence 配平；
- 不需要第二个 swapchain，也不需要两个 API 的呈现顺序协调。

若 3D 走 D3D11 而 2D 是 D3D12，上面三条**全部**要重新付一遍。反过来若 2D 走 GL、3D 走 D3D11，
同样要跨 API 互操作。

### 1.3 连带后果：Windows 上 GL 后端不能配 Stage3D

`src/air-app.ts:920` 是构建期**响亮拒绝**：

```
--gpu-backend gl has no Stage3D backend on Windows: stage3d_d3d.cc targets
D3D12 and stage3d_webgl.cc is wasm-only. Drop --gpu-backend to build the
D3D12 backend, or drop flash.display3D usage from this app.
```

即：**含 Stage3D 的应用在 Windows 上只能走 D3D12**。这不是懒，是「链一个 GL 后端却没有对应
`stage3d_*` 实现」会得到一个永不出像素的软件状态机（`AGENTS.md` §1.5 明令禁止的静默错误结果）。

## 2. 机制对照：D3D11 免费给的，D3D12 全要自己管

这张表是 §3 那笔账的根源。左两列是 API 事实，右列是我们在这条路径上的落点。

| 维度 | D3D11 | D3D12 | 我们的落点 |
|---|---|---|---|
| 抽象层次 | 设备 + **immediate context**（状态机式 setter） | 设备 + 队列 + 命令分配器 + 命令列表 | `d3d_glue.cc`（单帧串行）、`stage3d_d3d.cc`（每批一条 list） |
| 管线状态 | 着色器/光栅/混合/输入布局**分别绑定** | **PSO** 一次打包（+ root signature） | 每程序最多 16 个 PSO 变体（`S3D_MAX_PSOVAR`，LRU 淘汰），键是整条绘制状态的 256 字节字符串 |
| 资源使用期 | 驱动隐式跟踪 hazard | **显式 resource state + barrier** | 每批 `OMSetRenderTargets`/`ResourceBarrier` 手写 |
| 描述符 | 无（对象直接绑） | **描述符堆 + 句柄**（CBV/SRV/UAV、Sampler、RTV、DSV） | 纹理多级 SRV、`s3d_rtv_cpu`/`s3d_dsv_cpu` |
| CPU-GPU 同步 | 队列隐式顺序 + query | **fence**，且必须自己管「槽位」 | `fence_values[3]`、`s3d_wait_slot` |
| 内存/上传 | `UpdateSubresource` / `Map(WRITE_DISCARD)` 由驱动重命名 | committed/placed/reserved 资源 + **上传堆**，重命名要自己做 | `s3d_make_upload`、`S3D_CB_REGION` |
| 常量缓冲 | 覆盖写一般安全（驱动重命名） | **GPU 在 execute 时才读** ⇒ 同帧多次上传会互相覆盖 | 每次上传独占 4096 B 区域（阶段一百七十三） |
| 交换链 | DXGI，blt 或 flip | DXGI，flip 为主 | `CreateSwapChainForHwnd` + `FLIP_DISCARD` + 3 buffer |
| 最低系统 | Win7 SP1（+ 平台更新，FL 11_0） | **Win10 1507 + WDDM 2.0** | 默认构建在 Win7 必然起不来（§6） |
| 软件光栅 | `D3D_DRIVER_TYPE_WARP` 一等公民 | 也有 WARP 适配器，但要走 `EnumWarpAdapter`，不随 `EnumAdapters1` 出现 | 我们**两条路都没接**（§6） |
| 多线程录制 | 有 deferred context，但一般不用 | 一等公民（并行录制命令列表） | 我们不用（2D 单线程、3D 每批一条） |

## 3. 我们为 D3D12 手写掉的东西（逐条）

每条都写清「D3D11 那边是什么」，因为这正是「D3D11 省事」的具体含义。

| # | 我们手写的机制 | D3D11 的对应物 | 阶段 / 证据 |
|---|---|---|---|
| 1 | **三缓冲帧槽 + fence**：`SK_D3D_NUM_FRAMES 3`；Stage3D 侧 `S3D_FRAMES_IN_FLIGHT 3` 各带命令分配器/上传堆/fence 值 | 换缓冲由驱动重命名，应用基本无感 | 阶段一百二十六；`vendor/d3d_glue.cc:174` |
| 2 | **常量缓冲按 draw 版本化**：每次上传独占 4096 B 区域 | `UpdateSubresource` 一般可直接覆盖写 | 阶段一百七十三（12 个按钮被最后一个 mvp 变换） |
| 3 | **延迟释放绑到下一次提交**：不能按「最后一次已 signal 的 fence」提前释放 | 引用计数 + 驱动延迟销毁 | 阶段一百七十四（修前 171/171 次释放发生在 `listOpen=1`） |
| 4 | **PSO 键控缓存 + E_INVALIDARG 排错**：写掩码、裸 `SemanticName`、HLSL 字段顺序=stage 寄存器号 | 着色器与状态分开绑，没有整条 PSO 被判废这回事 | 阶段一百三十二（三次 `E_INVALIDARG`，靠 D3D12 调试层探针才定位） |
| 5 | **上传资源复用**：早期每次上传建一个新的 committed 资源，固定开销 ~100 µs/次 | `Map` 一个动态缓冲即可 | 阶段一百七十九（66k 对象时 4.4–6.5 ms/帧的平台期） |
| 6 | **设备丢失必须停帧**：每帧开头 `GetDeviceRemovedReason()` 闸门 + 三处失败入口统一 lost 路径 + `abandonContext()` + 250→4000 ms 退避重建 | 同样的概念存在，但没有「提交了就等于使用了失效资源」这一层耦合 | 阶段二百七十八（修前 623 条 `#1009` → Present 失败 → 386 ms 后 AV） |
| 7 | **混合状态 alpha 槽不能复用 `*_COLOR` 因子**：非法枚举会让**整条 PSO** 判废，该模式每次 draw 被静默丢掉 | 分开设置时错误面小得多 | 阶段一百七十五 |
| 8 | **`ResizeBuffers` 必须等所有 back buffer 引用归零，且要有上限**：`SK_D3D_DRAIN_MS 250`，超时跳帧而不是挂死 | 同样要等，但 blt 模型下的时序宽容得多 | `SK_D3D_DRAIN_MS` 注释里的实测：拖右下角把应用楔死（`IsHungAppWindow` = true） |

> 记账口径提醒：上表每一条都是**我们自己的实现缺陷**，不是 AIR 保真欠账——`adl` 走的是 **D3D11**
> 渲染器，这些路径在它上面**不存在**。所以按 `AGENTS.md` §1.5 的判据，它们不入「遗留待开发」的
> 保真表，只是在"补我们自己的正确性"。这一点在 `TODO.md:10472`、`:10540`、`:20203` 反复
> 标注过。

## 4. 性能：我们从未主张 D3D12 更快

- **没有做过 D3D11 vs D3D12 的同机 A/B**，以后也不该假定。
- 唯一一次同机对照是**呈现路径**：纯 Win32 + D3D12 flip 最小程序拖动 **4.9 ms**，同一程序的
  **D3D11 bitblt** 变体 **4.5 ms**（`TODO.md:10628`）。差 0.4 ms，且这个差主要来自 **flip vs blt
  两种交换模型**（flip 的 present 只有在合成器取走时才退休），**不是 API 代次**。
- 对我们这个负载（2D 显示列表 + 少量 Stage3D），瓶颈在 CPU 侧的批合并/图集/布局/`flush` 时机，
  不在 API 的提交开销。D3D12 真正的结构性优势（并行录制命令列表、显式内存、可预测的资源状态）
  在**单线程 2D UI** 上基本换不成帧时间；3D 侧我们是每批一条命令列表，也用不上并行录制。

结论：**D3D12 的收益我们没有拿到，也不曾声称；D3D11 的省事我们也没享受到，因为 Skia 没有那条后端。**

## 5. 生态：别人为什么是 D3D11

用户观察到的现象是真的，但那些项目的约束与我们的不同：

| 项目 | Windows 落点 | 为什么能这么做 |
|---|---|---|
| Qt 6 Quick | **默认 D3D11**（要 D3D12 得显式 `QSG_RHI_BACKEND=d3d12`） | 自研 RHI、多后端并行维护，不依赖某个第三方光栅库的 DC 形状 |
| Chromium / Electron | ANGLE → D3D11 | 反正要跨平台 GL，ANGLE 顺手把 D3D 也解决了 |
| Flutter (Windows) | ANGLE → D3D11 | 同上 |
| WinUI / D2D 系 | Direct2D（底层仍是 D3D11） | 只要 2D，且直接吃系统合成栈 |
| GPUI（Zed） | **直接 D3D11**，自建 8 类 primitive 管线 | 自己画，只做 8 种图元，不需要 Skia 级能力（见 [`gpui-windows-renderer.md`](gpui-windows-renderer.md)） |

共同点：**没有"链接一个只支持 D3D12 的第三方光栅库"这条约束，也没有"2D 合成与自家 3D 引擎共用
device"这个目标。** 两条我们全占。

一个可复用的旁证：GPUI 用 3 个 back buffer（`BUFFER_COUNT = 3`）——和我们 `SK_D3D_NUM_FRAMES 3`
**同一个理由**（2 个缓冲时合成器搬窗会同时扣住两个 back buffer，acquire 被拖到两个 vblank）。
不同 API、同一结论，说明这条不是 D3D12 特有。

## 6. 决策树：什么时候才该考虑 D3D11

只认**具体触发**，不认"生态上都用 D3D11"这种理由。

### 触发 A：要求 GPU UI 跑在 Win7/Win8 或不满足 WDDM 2.0 的机器上

- 现状：默认（D3D12）构建在 Win7 上**必然起不来**——`win32.md` §6.1 的导入表实测：默认 15 个 DLL，
  含 `d3d12.dll` 与 `d3dcompiler_47.dll`；`--gpu-backend gl` 构建 13 个 DLL，含 `OPENGL32`、**无**
  `d3d12.dll`。
- **正解不是 D3D11，是 GL 路径**（已存在）+ 可选补一个 GL Stage3D 后端填补 §1.3 那个洞。
- 加 D3D11 只在「GL 也不可用」时才轮得到（见触发 B）。

### 触发 B：GL 也不可用（虚拟机 / 远程桌面 / 无显卡驱动的装机）

- 现状：WGL 只给 `Microsoft Corporation | GDI Generic | 1.1.0` 时，`gl_glue.cc` 按 `win32.md` §6.2
  **明确报错退出**（不假装修复、不黑屏）。此时我们**没有任何 GPU 路径**。
- 这正是 D3D11+WARP 或 D3D12+WARP 的价值区。三条路的成本差得很远：

| 方案 | 改动 | 代价 | 状态 |
|---|---|---|---|
| **D3D12 WARP 适配器** | 在我们已有的 adapter 枚举里加一步 `IDXGIFactory4::EnumWarpAdapter` 作为末位兜底 | 最小；同一套渲染代码 | **未验证**（WARP 跑 Ganesh D3D12 的可行性、帧时间都未测） |
| D3D11 + WARP | 要新增一整个 D3D11 后端（2D 还得另解决，见 §7） | 大 | 不建议 |
| Mesa llvmpipe（`opengl32sw`） | 给 GL 路径塞一个软件 OpenGL | 外部大依赖；GL 语义 | 不建议 |

> **结论：触发 B 的最小正解是 D3D12 WARP，不是换 API。** 这也解释了为什么"要不要加 D3D11"
> 这个问题的答案长期是"不"——它要解决的需求，用现有 device 路径加二十行枚举就能碰到。

### 触发 C：Windows 侧维护面太大

`stage3d_d3d.cc` 2,799 行 + `d3d_glue.cc` 1,268 行，几乎全是 D3D12 特有样板。但换 API 不减少语义
工作量（`s3d_*` ABI 的行为契约不会因为换成 D3D11 而变少），**正解是补测试钉子与文档**，不是换 API。

### 反触发（明确不要做的事）

- ❌ 为了"更快"换 D3D11——没有证据，且瓶颈不在 API（§4）。
- ❌ 为了"和别的框架一致"换 D3D11——我们的约束不一样（§5）。
- ❌ 为了"少写代码"换——§1.1 决定 2D 那条路换不了，换一半只会多一个后端。
- ❌ 用 ANGLE 绕道 D3D11——多一层翻译，且 Stage3D 侧还要再做一遍。

## 7. 若真要加一个 D3D11 后端：诚实的改动面

写在这里是为了让"要不要做"有个真实标价，不是待办。

1. **2D 那一半** —— **否决项**。Skia 无 D3D11 后端，所以 D3D11 窗口只能承载：CPU 光栅 + 上传
   （丢掉 Ganesh 的 GPU 批/图集）、或 ANGLE GLES、或 D2D。三条都意味着**第二套 2D 光栅路径**要维护、
   要逐像素对齐、要各自跑一遍 `examples/` 视觉验收。
2. **3D 那一半** —— `vendor/stage3d_d3d11.cc`：`s3d_*` ABI 同形移植，HLSL 仍可复用（SM5 → D3D11 也吃），
   但 PSO→分项状态、描述符堆→直接绑定、fence→query、三缓冲槽→驱动重命名，**逐条都要删改**。
3. **接线** —— `src/air-app.ts` 新增 `--gpu-backend d3d11`（含 web/非 Windows 的拒绝分支）、构建清单
   `sources`/`link-libs`（`d3d11`/`dxgi`/`d3dcompiler`）、`ASC_RENDER_*` 宏、`Context3D.driverInfo`
   多一个标签、`docs/zh-cn/win32.md` 的核对表、`test/unit/backendparity` 的中性五名钉子、包体积与
   `win7-imports` 表。
4. **测试** —— 新后端要一套 `unit: stage3d/*` 钉子 + 真机 `examples/shmup-stage3d` 验收，且要
   和 D3D12 侧做 A/B 像素对照。

> 一句话：**这不是"换个 renderer"，是"再加一整个平台后端 + 一套 2D 光栅方案"。**

## 8. 未验证与诚实边界

- **D3D12 WARP 未实测**：可行性（Ganesh D3D12 在 WARP 上是否成）与帧时间都没有数据。
- **D3D11 vs D3D12 同机 A/B 未做**：§4 的 4.9/4.5 ms 是 flip vs blt 的对照，不能当 API 代次的结论。
- **Win7 无实机**：`win32.md` §6 的三条推论全部来自导入面 + subsystem + API 版本，不是运行结果。
- **`adl` 是 D3D11 渲染器**：因此 D3D12 侧的任何缺陷都不构成 AIR 保真欠账（§3 记账口径）；
  反过来也意味着——**D3D12 上的行为差异不能拿 `adl` 当 oracle 判对错**，只能判"是否违反已实测的
  AIR 语义"。
