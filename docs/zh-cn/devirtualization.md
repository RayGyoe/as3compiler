# 虚分派去虚化（叶子类与 `final` 直调）

> 本文是「把可证明无需动态分派的 AS3 实例成员调用，从 `->vtable->` 间接调用改为直调」的
> 设计与实施记录。**阶段 A（叶子类普通方法）已在阶段三百二十一 / v0.4.282 落地**；访问器、
> `final` 与 private 仍未实施。本文区分静态调用点与运行时执行次数，区分叶子类、`final`、
> private 与真正需要多态的路径；所有安全结论都以当前完整编译面和 `mxmlc`/`adl` 实测为准，
> 不凭 AIR SDK 元数据或成员名称推断。

---

## 1. 背景与定位：去虚化是「形态转换」，不是「前端做优化」

AGENTS.md §1.1 铁律：前端不做语义优化（不写窥孔、常量折叠、DCE、寄存器分配、内联），
那些是 `cc/clang -O2` 的职责。但 §1.4 同时授权一条**形态转换**：

> 「静态已知类型就不走动态分派……能在 C 层用原生 `int` 运算就不要 box 成 `double`。」

去虚化（devirtualization）属于这一类：在**类型与继承关系可证明**时，把
`obj->vtable->foo(obj)` 换成对解析后实现函数的直调，例如 `Base_foo(obj)`。转换不得改变成员
解析、接收者与参数求值、异常或任何其他可观察行为；内联、常量传播等后续优化仍由 `-O2`
完成，因此它是翻译形态，不是越界的手写优化 pass。

它与体积优化（`docs/zh-cn/size-optimization.md`）性质相同：那边把方法体标 `static`，让
`-O2` 做调用图剪枝；这边把可证明的调用点变成直接调用，让 `-O2` 自行决定是否内联。

**叶子类证明不是 AS3 规范对任意未来源码的永久承诺**，而是封闭编译面（closed-world）事实：
在这一次完整编译包含的全部类中，该类没有子类。若未来引入运行时 ABC 加载、独立模块或外部
子类注入，必须重新审查这一前提（§7、§8）。

## 2. 现状：主要静态实例成员路径无条件虚分派

### 2.1 方法体载体必须存在（不可省）

每个 AS3 方法/访问器的实现逻辑都有翻译出的 C 函数作为载体，例如：

```c
double Sprite_get_width(void* _this);
void   Sprite_set_width(void* _this, double value);
```

这是 §2.6 命名规范（`Foo_method(Foo* this)` 能对应回 AS 源码实体）的载体，也是「可读 C」的
骨架。去虚化只改调用点，**不删除、不展开方法体**。

### 2.2 静态已知类接收者的普通路径走 vtable

当前对**静态类型已知的普通实例方法与访问器的主要解析路径**，发射端不区分成员是否可能被
override，统一生成类 vtable 分派，例如（行号以当前源码为准，后续可能漂移）：

```c
(obj->vtable->set_foo(obj, v))   // src/emit.ts:2609
(obj->vtable->foo(obj, args))    // src/emit.ts:31185、34555、34583
(self->vtable->get_foo(self))    // src/emit.ts:32610、34507、35388
```

发射处注释说明了默认虚分派的原因（`src/emit.ts:2603`、`32607`）：子类可以 override，
基类静态类型的引用必须在运行时到达真实实现。

但「主要静态路径」不等于「所有实例成员表达式」。当前已有其他分派形态：

- `super.method()` 已按父类实现直调（`src/emit.ts:36784-36786`）；
- static 方法与 static setter 已直调；
- `Object` 方法调用走 `as_dyn_call`，属性读取走 `as_dyn_get`
  （`src/emit.ts:34451-34468`、`35302-35315`）；`*` 走 `emitAnyMethod` 等动态路径；
- 接口调用使用独立的 `{obj, vt}` 接口表，不是类 `vtable`；
- 方法值 thunk 仍经 vtable 取实现（`src/emit.ts:7533-7539`）；
- private 成员有自己的可见性与绑定规则，不能套用 public/protected 的统一描述。

阶段 A 后，上述普通方法路径由 `instanceMethodCallCode()` 统一选择形态：静态接收者是当前
封闭编译面的叶子类时直调 `m.owner` 的实现，否则仍走 vtable。显式 `obj.method()`、隐式
`this.method()` 与 sealed `with` 中解析到同一普通方法的调用均已接入；方法值 bound thunk 不改。
动态、接口、`super`、static、Proxy、private 与访问器路径均不改写。

## 3. `final` 信息的现状与校验缺口

`final` 修饰符已被解析并进入符号表：

- 方法级 `MethodInfo.isFinal`；
- 类级 `ClassInfo.isFinal`；
- parser 消费 `final` 修饰符（`src/parser.ts:327-335`、`361-365`）。

当前相关消费如下：

| 消费点 | 用途与边界 |
|---|---|
| `src/symbols.ts:8606` | `final` 类禁止被继承 |
| `src/symbols.ts:8651-8658` | **普通方法**的 `final` override 编译期检查 |
| `src/emit.ts:1687`、`2632-2633`、`4353-4677` | `describeType` 的 `isFinal` 反射数据 |

普通方法与访问器的分派发射均未使用 `isFinal`。同时必须记录一个实施前置缺口：
`src/symbols.ts:8651-8658` 只检查 `methods`，后续 getters/setters 合并处**没有对应的 final
override 检查**。因此不能笼统声称「所有 final 成员不可能 override 已由编译器保证」。

结论分两层：

1. 叶子类去虚化不依赖 `final`，可独立评估与实施；
2. `final` 普通方法去虚化可复用现有校验，但 `final` getter/setter 在去虚化前必须补齐
   override 校验与负例，否则不得把访问器的 `isFinal` 当成安全证明。

## 4. 真实应用静态盘点（TalkMED Meeting 桌面端）

> 2026-10-30，对一份 402,883 行 / 29 MB 的生成 C 做类继承图与 `->vtable->` 文本扫描。
> 这些数据描述**该快照的静态结构**，不是运行时 profile，也不能直接换算可去虚化比例。

| 指标 | 数值与口径 |
|---|---|
| 生成 C 规模 | 402,883 行 / 29 MB |
| 类总数（vtable） | 1,545 |
| 有父类的类 | 1,083 |
| 有子类的类 | 90（5.8%） |
| 无子类的叶子类 | 1,455（94.2%） |
| `->vtable->` 文本出现总数 | 22,291（含 `->vtable` 取地址等非调用用法） |
| 其中调用形态 `->vtable->name(` | 18,707（按出现次数计，非行数） |
| 其中 getter/setter 文本分派 | 8,626（39%，旧文本扫描口径） |
| 全文件 `this/self->vtable->` 自分派 | 7,774 |

注意：7,774 是**全文件自分派总数**，不是「叶子类方法体自分派」的子集；当前统计没有给每个
调用点标注接收者静态类型、解析后的成员 owner 与叶子/final 状态。

继承深度分布为 `{"0":462,"1":370,"2":256,"3":109,"4":29,"5":11,"6":14,"7":251,…}`。
按成员名称统计，静态文本出现次数较多的是：

```text
get_stage(1753)  addEventListener(1112)  removeEventListener(613)
addChild(568)    dispatchEvent(482)      get_parent(297)
```

这些只是**静态调用点频次**，不是运行时热点。更不能按名字把它们全部判为「真多态」：必须沿
接收者类型、成员解析结果和继承链检查实际 override 后，才能分类。

「94.2% 的类是叶子类」也不等于「94.2% 的方法或调用点可去虚化」：类占比、成员占比、静态
调用点占比与动态执行占比是四种不同指标。

### 4.1 调用点分类实测（2026-10-30，探针 `temp/devirt-measure.cjs`）

在上述同一份 C 快照上做了进一步测量：解析每个 `struct Foo_vtable` 的槽位布局与
`static Foo_vtable Foo_vt = {…}` 初始化器，得到「类 → 槽位 → 实现函数」的精确映射，再对
18,707 个调用形态出现点分类。成功解析 1,078 个带完整初始化器的类（1,103 个 vtable 布局中，
其余为预烘焙内建等无匹配初始化器的形态），其中叶子类 989 个。

| 分类 | 调用点数 | 占 18,707 的比例 | 证明方式 |
|---|---|---|---|
| 槽位在全程序只有**唯一实现** | 6,864 | 36.7% | 与接收者类型无关：任何类 vtable 经该槽位分派都到达同一函数，可直调 |
| **叶子类方法体内的 `this` 自分派** | 6,710 | 35.9% | 封闭编译面内 `this` 的运行时类型就是该叶子类，可直调自身 vtable 解析结果 |
| 两类**并集** | **13,574** | **72.6%** | 两种廉价静态证明已可覆盖的调用点 |

补充口径：非叶子类方法体内的 `this` 自分派 922 点；未能按函数名归属到类的自由函数/闭包内
自分派 548 点。叶子类自分派的 6,710 点全部能在自身 vtable 初始化器中解析到实现函数。

多实现槽位中静态出现次数最高的几个（仍需接收者类型/final 分析或保留虚分派）：

```text
get_stage(1753点/6实现)  addEventListener(931/8)  removeEventListener(527/6)
addChild(451/4)          dispatchEvent(386/5)     get_height(198/27)
get_width(186/26)        dispose(149/83)
```

对这组数字的解读必须守住三条边界：

1. 这是**静态调用点覆盖率**，不是动态执行次数占比，更不是加速比；
2. 72.6% 不是理论上界——它尚未计入「静态接收者为叶子类的外部调用」、`final` 与 private
   等额外机会，只是两种最廉价证明的并集；
3. 它来自对生成 C 的结构化解析（槽位→实现映射是精确的），不是按成员名字的猜测；但实施时
   仍应在语义发射层重做同样分类（§9.4），以接收者静态类型为准。

### 4.2 阶段 A 落地后的同 HEAD 对照（2026-10-30）

用同一份 TalkMED 源码、同一 macOS 描述符、同一 SWC 与相同编译参数，分别由「当前 HEAD」和
「HEAD + 阶段 A 补丁」生成原生应用。两份 C 都是 408,776 行；调用点减少全部来自本补丁，不是
旧版本快照与应用源码漂移的混合比较。

| 指标 | HEAD 基线 | 阶段 A | 变化 |
|---|---:|---:|---:|
| 调用形态 `->vtable->name(` | 18,707 | 12,129 | **-6,578（-35.2%）** |
| 全部 `->vtable->` 文本出现 | 22,291 | 15,713 | -6,578 |
| 生成 C 字节数 | 30,614,788 | 30,370,810 | -243,978（-0.80%） |
| 原生二进制字节数 | 23,343,536 | 23,343,520 | -16（约 0%） |
| 单次完整构建墙钟 | 97.20 s | 91.35 s | 单次读数，不作性能结论 |

阶段 A 的 35.2% 低于 §4.1 的 72.6% 是预期结果：前者只实现普通方法，后者是「唯一实现槽位 ∪
叶子类自分派」的静态机会并集，包含访问器与尚未实施的其他证明。二者口径不同，不能写成
「只兑现了机会的一半」或据此推算运行时收益。

## 5. 去虚化机会与保留边界

### 5.1 叶子类接收者：第一阶段的主要候选

若接收者的静态类 `C` 在本次完整编译面中没有任何子类，则运行时对象只能是 `C`（不考虑
`null`，其守卫与异常行为保持不变）。对已在 `C` 的继承链上完成 nearest-wins 解析的普通
成员，可直调解析结果中的实现，无需再经 vtable。

例如 `Leaf extends Base` 且没有覆盖 `Base.foo`：

```as3
var x:Leaf = ...;
x.foo();
```

可去虚化为 `Base_foo(x)`，**不是**虚构一个 `Leaf_foo(x)`。「叶子类」只证明可以直调；具体
调哪个函数，仍由现有成员解析得到的 `m.owner` / `g.owner` / `s.owner` 决定。

该机会不需要 `final`。类图统计只需一次 O(类数) 的符号表遍历，但统计集合必须覆盖本次实际
编译的内建类、用户类及 SWC/Embed 合成类，不能只扫描源码目录。

### 5.2 `final` 与 private：分别验证，不套用未经验证的示例

`final` 普通方法、`final` 类与叶子类都可提供静态证明，但证明来源不同，校验覆盖也不同。
尤其不能再用 `width`、`height`、`parent`、`numChildren`、`stage` 作为「AIR final getter」
示例：2026-10-30 用本机 mxmlc 51.4.1 编译探针
（`temp/devirtualization-review/FinalProbe.as`），这五个 getter **全部允许 override**。
项目内建实现也有 TextField/Video 覆盖 width/height 的既有记录。

内建类的 `isFinal` 不能照抄 SDK 元数据。`src/symbols.ts:3548-3554` 已记录反例：AIR SDK 报
`FileReference` 为 final，但 mxmlc 51.4.1 实测允许继承；本项目自身也有
`File extends FileReference`。任何 final 补标都必须以「mxmlc 是否实际拒绝继承/override」
为准，并保留正、负例。

private 成员是另一个可单独评估的静态绑定候选，因为它不参与 public/protected 的普通继承
多态。但必须按声明 owner、命名空间与可见性规则单独实现和验收，不能简单并入第一阶段，
也不能把 private 描述成「当前一律 vtable」。

### 5.3 不能证明时分派必须保留

以下情况保持现有路径：

- 接收者静态类型不是叶子类，且解析成员没有足够、已校验的 final/静态绑定证明；
- 基类引用需要到达子类 override；
- `*`、`Object`、接口、Proxy 及其他动态分派路径；
- 任何会使成员解析结果、异常、求值顺序或单次求值发生变化的改写。

「保留 vtable」不等于已经证明该成员在运行时一定多态，只表示当前编译器没有足够证明可安全
直调。后续若做全程序 override 集合分析，应另立设计与测量，不在本第一阶段顺手扩大范围。

## 6. 性能收益：静态覆盖与限定场景 A/B 已实测，未观察到稳定加速

### 6.1 直接调用省小钱，解锁后端优化才可能放大

一次 `->vtable->foo(obj)` 的直调化可省一次 vtable 读取与一次间接跳转。更大的潜在收益是
`-O2` 能看到直接调用，并自行决定内联及后续数据流优化。但这些收益必须用同一应用、同一
输入与同一编译参数做 A/B，不能由 C 文本形态直接推断。

直调还可能因内联增加代码体积或编译时间，所以二进制体积与编译耗时也属于验收指标，而不是
只测运行速度。

### 6.2 静态调用点覆盖实测为 72.6%，但不能换算成加速比

此前「可消除 60–80% / 1.3 万–1.8 万个调用点」的说法没有分类数据支撑，已撤回。§4.1 的
实测现在给出了有依据的静态数字：两种可证明安全的分析（唯一实现槽位 + 叶子类自分派）的并集
覆盖该应用 **13,574 / 18,707 = 72.6%** 的静态调用点。旧估算恰好落在实测附近纯属巧合，
方法上仍以实测为准。

但静态覆盖率不等于收益：**动态执行占比仍未测量**。一个只占静态点 30% 的
多态槽位集合完全可能占据绝大多数运行时调用（如 `get_stage`、`addEventListener` 都在多实现
桶里）。阶段 A 的限定场景 A/B 见 §6.3，不能用它外推整个应用。

实施时应在发射端或等价语义分析层记录「接收者静态类型 + 解析成员 owner + 叶子/final 状态」
重做分类，与 §4.1 的 C 层测量互相校验。

去虚化定位是稳态吞吐优化，不自动替代 `gc_find_block()`、固定每帧成本等既有性能调查。
实施顺序应按最新 TODO 与同条件实测决定，而不是沿用静态调用点覆盖率。

### 6.3 登录窗口启动后空闲 15 秒的 CPU A/B

在 §4.2 的两个同 HEAD 二进制上交替运行三轮，每轮启动应用并保持窗口空闲 15 秒，记录进程
user+sys CPU。两臂都完成启动并保持存活；运行期间应用自身的网络请求与响应不完全相同，因此
这只是一个受限场景，不是确定性的计算基准。

| 臂 | 三次 CPU 读数（秒） | 均值 |
|---|---|---:|
| HEAD 基线 | 1.321961 / 1.242744 / 1.245939 | 1.270215 |
| 阶段 A | 1.342204 / 1.285500 / 1.292283 | 1.306662 |

阶段 A 样本均值高约 2.9%，三轮存在波动，**没有观察到可宣称的加速**；这组数据也不足以证明
普遍性能回退。结论仅限于该机器、该登录窗口与该空闲场景。后续若继续性能工作，应改用无网络、
固定输入、可重复的方法调用/渲染基准，并报告多轮分布，而不是把 35.2% 的静态消除换算成速度。

## 7. 实施设计与分期

### 7.1 共同前提

1. 在本次完整编译面的符号收集完成后，从 `superClass` 链接计算 `hasSubclasses`；成本为一次
   O(类数) 遍历，无额外 AST 全树扫描。
2. 编译面必须包含内建类、实际引入的用户类、SWC/Embed 合成类；`--air-app` 使用裁剪后的真实
   emitted 类集合，而不是磁盘上全部 `.as`。
3. 直调判定至少依赖「接收者静态类」和「nearest-wins 解析后的成员 owner」；直调目标必须是
   owner 的实现函数。
4. 保留原有 `as_req_obj` 等 null 守卫、参数与接收者求值顺序、单次求值及异常行为。不能把
   去虚化写成会重复求值接收者的文本替换。

### 7.2 建议分期

- **阶段 A（最小安全切片，已实现）**：仅处理静态已知接收者为叶子类的**普通方法调用**，
  覆盖显式调用、隐式 `this` 与 sealed `with`；动态、接口、`super`、static、Proxy、private、
  访问器与方法值 bound thunk 保持不变。
- **阶段 B（访问器补面）**：在行为夹具齐备后扩展叶子类 getter/setter，并覆盖普通读取、
  读取后立即调用、复合赋值、`||=`、`++/--` 等路径。`setterCallCode()` 等助手若缺少接收者
  静态类型，必须显式补齐上下文，不能只替换返回字符串。
- **阶段 C（独立证明）**：分别评估 `final` 普通方法、`final` 类、private 静态绑定。
  `final` getter/setter 必须先补 override 编译期校验和负例，再考虑去虚化。

还需清点方法值 bound thunk、隐式 `this.method()` 等入口，决定各阶段是否覆盖；未覆盖的入口
保持原行为，不得只改主路径后宣称「所有实例调用已去虚化」。

实现集中在 `src/emit.ts`：符号收集完成后一次 O(类数) 遍历得到 `leafClasses`，普通方法三处
入口共用 `instanceMethodCallCode()`；未修改 lexer/parser，也未新增手写优化 pass。

## 8. 风险边界

| 情形 | 处置 | 依据 |
|---|---|---|
| 静态接收者为当前编译面的叶子类，成员已解析 | 可直调解析后的 owner 实现 | 封闭编译面内无子类，运行时类型不可能再派生 |
| `final` 普通方法 | 后续独立评估 | 现有普通方法 override 校验可提供证明 |
| `final` getter/setter | 校验补齐前不得仅凭 `isFinal` 直调 | 当前缺少访问器 final override 检查 |
| `final` 类 | 可作为独立证明，也可由类图覆盖 | 仍需保证编译面封闭及 final 继承校验有效 |
| 基类引用需要多态 | 保留 vtable | 必须到达运行时 override |
| `*` / `Object` / 动态接收者 | 保留 `as_dyn_*` / `emitAnyMethod` 等路径 | 不是「box + vtable」，也不参与第一阶段 |
| 接口接收者 | 保留独立接口表分派 | 不使用类 vtable |
| `super` / static | 保持现有直调 | 本方案不改变其绑定 |
| private / Proxy | 保持原路径，另行设计 | 可见性与动态钩子不能被套用普通规则 |

本方案不做「赌它大概率是某类」的投机式去虚化。所有直调都必须有明确的静态证明，并以行为
差分验证。任何未来打破封闭编译面的功能（运行时 ABC、外部模块子类等）都是本设计需要重新
审查的边界。

---

## 9. 验收口径

1. **行为夹具 + `adl` 差分**：新增覆盖叶子继承、实现声明在祖先 owner、基类引用、真实
   override、getter/setter、`super`、接口、动态接收者与 Proxy 的示例，逐项对照输出、异常
   和求值次数；不能只检查生成 C 是否「看起来直调」。
2. **结构钉**：在 `test/unit/` 分别断言叶子普通方法直调到正确 owner、需多态的基类调用仍走
   vtable、动态/接口/`super` 路径不变；后续阶段再为访问器和 final 增加独立钉子与负例。
3. **全量回归**：`node test.ts` 全绿。开发期只跑相关局部组，收尾按项目规范跑全量。
4. **静态量化**：在语义发射层统计可直调/需保留/非本方案路径，报告静态调用点，不再由
   叶子类占比或成员名推算比例。
5. **动态性能 A/B**：同一真实应用、同一输入、同一后端与编译参数，比较修改前后运行时
   profile 与端到端指标；静态文本频次不能代替动态热点。
6. **非性能回退**：同时记录生成 C/二进制体积和编译时间；若直调解锁内联导致明显回退，必须
   如实报告并重新评估收益。

---

## 10. 边界与不做的事

- **不手写内联**：只改调用形态，由 `-O2` 决定是否内联，不展开方法体。
- **不发 `__attribute__` / 内联汇编**：直调只是普通 C 函数调用，无平台耦合。
- **不做投机式去虚化**：不根据 profile 猜具体类型，只使用可证明的信息。
- **不改动态/接口/`super`/static/Proxy 语义**：非本阶段路径原样保留。
- **不把 private、final 访问器混入第一阶段**：它们各有独立校验与验收前提。
- **不改 GC / 装箱 / 分配器**：这些是独立性能课题，不与去虚化混在同一改动里。
- **不预设性能数字**：未测量前不承诺调用点消除比例或加速比。

---

**一句话结论**：阶段 A 已把叶子类普通方法改为 owner 直调，并在真实应用同 HEAD 对照中消除
6,578 / 18,707（35.2%）的 vtable 调用形态；动态、接口、访问器与 bound thunk 等边界保持不变。
限定空闲场景未观察到稳定加速，故不把静态覆盖当作性能收益；访问器、`final` 与 private 仍按
后续独立阶段处理。
