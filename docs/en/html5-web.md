# HTML5 / Web Rendering — Implementation and Usage

> This document answers: **how to compile an AS3 program into an HTML5 rendering view in the browser, and the
> implementation constraints behind it.**
> Target combination: `--target wasm --package web`. Positioning: the browser-side complement to `compile.md`
> (multi-target builds) and `skia.md` (rendering backend).
>
> Status: **implemented and end-to-end verified** (blue rectangle + `TextField` text + runtime font injection,
> rendering correctly inside the browser canvas with no runtime crash; a complete AIR demo measures
> **`FPS:120` / 0.11 ms per frame (GPU raster, 1.35% of the frame budget)** on a 120 Hz panel, see §3.2 and
> `temp/web-fps/EVIDENCE.md`). **Stage3D has landed**: `examples/air-starling-demo` (142 AS3 sources, with the
> entire rendering going through `Context3D`) compiles to web and renders all 12 scenes correctly in the
> browser, with content consistent with the AIR `adl` reference (the web-side Stage3D = WebGL2 backend, see
> §3.3; 120 fps / 0 drops / 2.88 ms per frame).

---

## 1. Target and Artifacts

`--target` sets the machine-code ABI, `--package` sets the distribution form, the two being orthogonal. The
browser target is expressed as `--target wasm --package web`, compiled with Emscripten `emcc`, producing a
three-piece set:

| Artifact | Note |
|---|---|
| `<base>.html` | page entry: `<canvas>` + a font-injection bootstrap script (generated by `index.ts`, not emcc's default shell) |
| `<base>.js` | Emscripten JS glue (loads the wasm, provides the `Module` runtime) |
| `<base>.wasm` | wasm32 machine code (Skia CPU raster + generated C + web glue layer) |

Compared with other combinations:

| target | package | Backend | Artifact |
|---|---|---|---|
| wasm | raw (default) | wasi clang `--target=wasm32-wasip1` | a bare `.wasm` (WASI command-line module) |
| wasm | **web** | emcc (Emscripten) | `.wasm` + `.js` + `index.html` |
| native | raw | cc | a bare executable |
| native | xcode-project | generate an Xcode project | a macOS `.app` project |

`web` hard-requires `target=wasm` (validated when `src/index.ts` dispatches); `--target wasm --package raw`
stays as-is (a WASI command-line module, which `examples/wasm-native/`'s shim loads).

**Artifacts come as a set (a failed build does not roll back intermediate artifacts already written)**: a
successful web build writes `.html`/`.js`/`.wasm` (plus `<base>.data` when the app directory is pre-packaged
into the FS) as **one batch**. If the failure is at the **link stage** (e.g. the backend is missing an `s3d_*`
entry point: `undefined symbol`), the already-written `.c`/`.data` stay on disk while `.wasm` is still the
**last successful** version ⇒ the page becomes "all assets fail to decode, white screen stuck on loading" (the
old wasm reads assets at the new `.data` offsets). After seeing a build error, **re-run to success**; do not
keep using the old page. Also: **the browser silently reuses an old `.js`/`.wasm`** (without re-validating) —
when checking a new build, switch the port or add a query string, otherwise what you see may be last month's
artifact.

**Relative asset URLs are based on the page's directory**: the font/asset entries in the manifest generated by
`--air-app` (`assets/fonts/Ubuntu-R.ttf`, `assets/textures/2x/…`) and the app's
`File.applicationDirectory.resolvePath("assets/…")` are both resolved against **the page's directory**, so such
projects must be built **in place** (`-o` pointing at the app directory); moving the artifacts elsewhere causes
asset/font 404s, the typical symptom being "the button skin is there but the text is all gone". `--air-app`
also `preload`s the whole app directory into `<base>.data` (fonts are separately excluded via
`preload-excludes`, see §6.1).

## 2. Quick Start

```bash
# requires the Emscripten SDK (provides emcc) + the wasm build of Skia (vendor/skia/lib/wasm/)
export EMSDK_HOME=/path/to/emsdk

as-aot examples/web/hello-web.as \
  --manifest examples/web/hello-web.build.json
```

The artifacts are generated under `examples/web/`: `hello-web.html` + `hello-web.js` + `hello-web.wasm`.
A browser cannot load wasm directly via `file://`, so it needs an HTTP server (`python3 -m http.server` etc.);
open `hello-web.html` to see the blue rectangle + `TextField` text.

> ⚠️ **The server must mark `.wasm` as `application/wasm`** (`python3 -m http.server` 3.9+ does so
> correctly). When marked as `application/octet-stream` (some simple static servers, and the AgentPilot
> built-in preview panel), Chrome refuses `WebAssembly.instantiateStreaming` and two red error lines appear in
> the console: `wasm streaming compile failed: … Incorrect response MIME type. Expected 'application/wasm'.`
> and `falling back to ArrayBuffer instantiation`. **These two lines are benign** — emscripten immediately
> falls back to ArrayBuffer compilation and the page runs normally (the app's own `trace()` output follows
> directly after those two lines). The only cost is that the wasm is downloaded twice and streaming
> compilation is lost. This repo's acceptance server `temp/netprobe2_server.py` sets that MIME explicitly, so
> its run log has neither line.

AIR projects (`--air-app`) also support the web target, compiling from `app.xml` to the browser in one command
with no hand-written manifest:

```bash
as-aot --air-app examples/air-native/air-native-app.xml --target wasm --package web
```

The `--air-app` adapter automatically switches to the web backend (`web_glue.cc` + the wasm build of Skia,
dropping SDL2/`objc`/Cocoa frameworks). Fonts come from app.xml's `<embedFonts>` (reading each
`<font><fontPath>` to generate `font-urls`, falling back to `fonts/Arial.ttf` by default), and the artifacts
are `air-native.html` + `.js` + `.wasm`.

`<initialWindow><renderMode>` controls the GPU/CPU rendering split (web target):

| renderMode | Build-manifest define | Rasterization backend | Presentation path |
|---|---|---|---|
| `auto` (default) | none | CPU (`SkSurfaces::Raster`) | `putImageData` |
| `cpu` | none | CPU (`SkSurfaces::Raster`) | `putImageData` |
| `direct` | `ASC_RENDER_GPU=1` | **GPU (Ganesh `GrDirectContext` + WebGL2)** | `GrDirectContext::flush` |
| `gpu` | `ASC_RENDER_GPU=1` | **GPU (Ganesh `GrDirectContext` + WebGL2)** | `GrDirectContext::flush` |

Both `direct`/`gpu` go through full GPU rasterization (efficiency first, not aligning with AIR's official
"direct = CPU compositing + GPU blit" split): the Skia surface switches from `SkSurfaces::Raster` to the Ganesh
backend, rendering directly into the WebGL2 default framebuffer (FBO 0), with the whole frame composited on
the GPU (glyph atlases, gradients, filters all become GPU textures/draws), so present is just
`GrDirectContext::flush()`, with no more CPU↔JS per-pixel copy. This removes the CPU software-rasterization
bottleneck — which previously locked web at ~60 fps.

Key points of the example manifest (`examples/web/hello-web.build.json`):

```json
{
  "target": "wasm",
  "package": "web",
  "sources": ["../../vendor/skia_glue.cc", "../../vendor/web_glue.cc"],
  "include-paths": ["../../vendor/skia"],
  "link-libs": ["skia", "skparagraph", "skshaper", "skunicode", "skcms",
    "wuffs", "png", "jpeg", "webp", "webp_sse41", "freetype2", "harfbuzz", "icu"],
  "link-paths": ["../../vendor/skia/lib/wasm"],
  "defines": ["ASC_USE_SKIA=1", "ASC_USE_WINDOW=1"],
  "font-urls": ["fonts/Arial.ttf"]
}
```

Field differences (against a native manifest):

- **No `zlib` linking**: the web link uses `-s USE_ZLIB=1`, and Emscripten provides both the zlib headers and
  the symbols; an explicit `-l zlib` may actually conflict.
- **New `font-urls`**: a list of font byte-stream URLs, see §4.

## 3. Implementation Architecture

It reuses `vendor/skia_glue.cc`'s `extern "C"` flat interface (the generated C calls only `sk_*` symbols, and
the pixel-rendering logic is exactly the same as native). The browser-side differences are concentrated in two
glue files:

| Concern | native | web |
|---|---|---|
| Graphics rasterization | `SkSurfaces::Raster` (CPU offscreen) | same as left; with `renderMode=direct/gpu` it uses Ganesh (`GrDirectContext` + WebGL2) |
| Font backend | `SkFontMgr_New_CoreText()` (enumerates macOS system fonts) | `SkFontMgr_New_Custom_Data()` + runtime injection (§4) |
| Window / presentation | SDL2 `SDL_PollEvent` blocking loop | `vendor/web_glue.cc`: cpu mode `putImageData` blit; direct/gpu mode `GrDirectContext::flush` |
| Frame driving | SDL event loop (when self-driving, `SDL_Delay` until the deadline) | `emscripten_set_main_loop` + **rAF whole-tick pacing** (§3.2) |
| Input | SDL events | `emscripten_set_mousedown_callback`/`mouseup`/`wheel` |
| Stage3D | `vendor/stage3d_glue.mm` (Metal + MSL shaders) | `vendor/stage3d_webgl.cc` (WebGL2 + GLSL ES shaders, §3.3) |
| Network (`flash.net`) | libcurl (opt-in `ASC_HAVE_CURL`) | browser `fetch` (opt-in `ASC_HAVE_FETCH`, see §3.4); honest `ioError` with no backend |

`vendor/web_glue.cc` keeps the same `extern "C"` signatures as `window_glue.cc`
(`sk_window_*` / `sk_surface_peek_pixels` etc.), so the generated `.c` can switch between the native and web
backends **with no changes at all**.

### 3.1 Presentation: premultiplied alpha blitted directly to canvas

`present_frame` uses `EM_ASM` + `putImageData`, taking pixels from `sk_surface_peek_pixels` and blitting them
directly to the canvas. The pixels are premultiplied alpha: **opaque pixels are exact**; semi-transparent
pixels have a color shift (canvas semantics vs Skia's premultiplied), a known limitation (§6).

### 3.2 Frame driving and pacing

The browser has no `SDL_PollEvent`-style event loop that can block and wait; frames are driven by
`emscripten_set_main_loop(main_loop, 0, 1)`, with the actual tick coming from **requestAnimationFrame**.
Three corollaries that differ from the native backend:

1. **rAF follows the refresh rate of the panel the window is on**. This is a hard cap: on a 50 Hz screen no
   rendering backend can reach 120 fps. With multiple displays of different refresh rates (this machine: a
   built-in XDR at 120 Hz + an external MateView at 50 Hz), the rAF rate depends on **which screen the window
   is on at the time**, independent of the code.
2. **One rAF callback = one vsync**. The compositor only recognizes ticks, not timestamps.
3. **`sk_window_get_display_refresh()` returns 0 on web** (the browser has no counterpart to
   `SDL_GetDisplayMode`), so the refresh rate is **measured** by `main_loop` itself: the **median** of
   consecutive callback intervals (a 16-slot ring). Using the median rather than the mean/EMA is so that one
   long callback (a GC pause, first-frame font rasterization, a tab switch, a window drag) cannot skew the
   estimate — the mean would be dragged for over a second, choosing the wrong divisor the whole time.

Pacing is expressed in **whole ticks**: letting the refresh period be `rp` (the measured median interval) and
the target frame interval `interval = 1000 / Stage.frameRate`, then

```c
skip = (int)(interval / rp + 0.5);   // present one frame every skip vsyncs
if (skip < 1) skip = 1;              // target above the refresh rate -> draw every vsync
```

The frame interval is therefore always an integer multiple of that panel's refresh period; a rate the panel
cannot produce (e.g. 24 fps on a 60 Hz screen needs 2.5 vsyncs) takes the nearest feasible divisor, and a
request is never more than half a vsync early. This is consistent with the native SDL2 backend (whose present
is likewise vsync-constrained, see `emit.ts`'s `ASC_window_on_frame_delay`: a frameRate above the refresh rate
is clamped to the refresh rate).

> **Do not** pace by "has the timestamp passed the deadline" (`if (now < next_tick) return;`). rAF timestamps
> jitter around the real vsync — measured on this machine's 120 Hz panel at p50 8.30 ms / p95 9.30 ms against a
> period of 8.333 ms. As soon as one callback arrives a few hundred microseconds early the test fails and that
> tick is dropped, and the next callback is only adopted a full vsync later (long past the deadline), so drops
> and takes alternate and the **rate halves**: measured rAF gives 120/s but the pacer presents only **66 fps**,
> dropping 54.5 callbacks per second (the user-reported "FPS cannot reach 120").

**Frame-rate diagnostics (a compile-time knob)**: there is no env in the browser (native's `ASC_FRAME_STATS`
is a runtime `getenv` knob), so the web-side counterpart is a compile-time define, not compiled into the
artifact by default:

```bash
as-aot --air-app <app.xml> --target wasm --package web -D ASC_FRAME_STATS=1
```

When enabled, it sends a summary to `window.__ascFrameStats` once per second: `frames` (frames actually
presented = achieved fps), `loopcalls` (rAF callbacks received), `skips` (pacer-initiated drops), `renderMs`
(the time for `on_frame + on_redraw + present`), `rafPeriodMs` (the measured refresh period), `skip` (the
chosen divisor). `loopcalls` / `frames` / `skips` together decompose "why it did not reach the target":
`loopcalls≈frames` → rAF itself is slow (the refresh-rate cap); large `skips` → a pacing problem;
`renderMs/frames` approaching `rafPeriodMs` → a real rendering bottleneck. The companion measurement script is
`temp/web-fps/fps_probe.mjs` (which pins the window to a specified display before sampling).

### 3.3 Stage3D (WebGL2) backend

**Why it must exist**: Starling's rendering **all** goes through `Context3D` (`drawTriangles` → an offscreen
render target → a final `present` blitting the render target to the stage). Without a Stage3D backend, all
`as_s3d_*` wrappers degrade to no-ops (`ASC_RENDER_STAGE3D` undefined) and `Context3D_present` blits an empty
image — a blank page but no error. So "compile the Starling demo to web" = "the web-side Stage3D backend must
be implemented".

**Files and switches**:

| Concern | Note |
|---|---|
| Backend implementation | `vendor/stage3d_webgl.cc` (~700 lines, WebGL2/GLES3), implementing **exactly the same `s3d_*` flat C API** as `stage3d_glue.mm` |
| Shader language | selected at build time by `ASC_AGAL_TARGET`: Metal uses MSL (target 0), web uses GLSL ES (target 1, `ASC_S3D_GLSL`) |
| Build manifest | `ASC_RENDER_STAGE3D=1` + `ASC_S3D_GLSL=1` (linking `vendor/stage3d_webgl.cc`); when the app descriptor contains `<depthAndStencil>`, add `ASC_RENDER_DEPTH_STENCIL=1` |
| Detection | `src/air-app.ts`'s `detectStage3D(files)` scans the source, and **both native and web targets** decide whether to mount the backend based on it |
| Sharedness | the `Context3D` state machine, the `as_s3d_*` wrappers, and the AGAL translator call sites in the generated C are **exactly the same on both ends** (the backend difference is only in these two glue files) |

**Semantic differences between WebGL and AS3/Metal (must be handled explicitly)**:

1. **Y-axis direction**: GL's render-target row 0 is at the **bottom**, while AS3/Metal/`BitmapData` row 0 is
   at the **top**. The fix is to uniformly apply `gl_Position.y = -gl_Position.y;` at the end of the GLSL
   vertex stage — this keeps texture sampling at `v=0` = top (consistent with AS3), and the row order read back
   by `glReadPixels` also aligns directly with the Skia canvas. The winding order flips accordingly, so GL
   keeps the default `GL_CCW` as front-facing (corresponding to AS3's `Clockwise`).
2. **Pixel byte order**: AS3's `uint32` pixel word is `0xAARRGGBB` (straight alpha), and GL's `RGBA8` needs a
   BGRA↔RGBA swap on upload/read-back.
3. **Per-register constant uniforms**: following the existing GLSL translator's declaration form, `vc0..vcN`/
   `fc0..fcN` are each a `uniform vec4`, uploaded by register with `glUniform4fv` each frame.
4. **Attribute slots**: before linking, do `glBindAttribLocation(prog, i, "va<i>")` for each prog, making
   `setVertexBufferAt(stream i)` == GL's attribute i, with no query needed.
5. **Depth/stencil**: the offscreen FBO (RGBA8 color + an optional `DEPTH24_STENCIL8` renderbuffer) is created
   lazily as needed (corresponding to the Metal side's "mount D32S8 only when needed"), with the stencil using
   `glStencilFuncSeparate`/`glStencilOpSeparate` per `frontAndBack`.
6. **Sampler state**: GL stores filter/wrap state on the **texture object**, so it is cached per texture object
   (key = GL texture name) to avoid repeating six `glTexParameteri` calls every draw.
7. **Coexisting with Ganesh**: **a single shared WebGL2 context** (Emscripten's GL calls all go to the current
   context), with every `s3d_*` entry point that touches GL calling `sk_gr_reset_context()` (`resetContext()` is
   just a dirty-bit flag, very cheap), otherwise Ganesh would reuse GL state we changed.
8. **WebGL2 lacks `glGetTexLevelParameteriv`**: `GL_TEXTURE_WIDTH` is unavailable, so the render-target
   texture dimensions are tracked by the `S3DRtTex{id,width,height}` registry itself (`s3d_destroy_texture`
   removes it in sync).
9. **The full-mask form of AGAL comparison instructions** (stage eighty-nine / thirty-two): the MSL side uses
   `select(float4(0.0), float4(1.0), a >= b)`, but GLSL ES 1.00 has no `select`, and the only usable form is
   `mix(vec4(0.0), vec4(1.0), vec4(greaterThanEqual(a, b)))` — `mix(genType, genType, genType)` is a legal
   overload per ES 1.00 §8.3, and `vec4(bvec4)` (a per-component bool→float constructor) is explicitly
   allowed by §5.4.2; conversely `mix(vec4, vec4, bvec4)` is an **ES 3.00-only overload** and does not compile
   under our GLSL (no `#version`, compiled as ES 1.00). ⚠️ In implementation you **must not** write the two
   targets as "one `sprintf` + a ternary format string": the two branches have different `%s` counts (MSL 4,
   GLSL 5) while the varargs are the same fixed list, so it silently misaligns into
   `v0(greaterThanEqual(v0, vec4))` (`vec4` as a bare identifier) → `')' : syntax error`, and four opcodes
   (`sge`/`slt`/`seq`/`sne`) all fail on web (Starling's "Switch Filter" crash is exactly this, stage
   eighty-nine / thirty-two); you must write a separate `sprintf` for each.

**Presentation path (GPU direct, stage eighty-nine / thirty-one)**: `Context3D_present`, under
`#if defined(ASC_RENDER_METAL) || defined(ASC_RENDER_GPU)`, takes the render-target handle
(`ASC_stage3d_tex = as_s3d_get_render_target`); Metal uses `as_skia_mtl_draw_texture`, and GL uses
`sk_gl_draw_texture(canvas, texId, w, h, dx, dy, dw, dh)` — the latter wraps the render target's GL texture as
a `GrBackendTexture` using `GrBackendTextures::MakeGL` (`GL_TEXTURE_2D` / `kRGBA_8888`), then after
`SkImages::BorrowTextureFrom` (`kTopLeft_GrSurfaceOrigin` / `kPremul`) does `drawImageRect` directly into the
Skia canvas, **no longer `glReadPixels`-ing back to memory**. The read-back path
(`as_s3d_readback_render` + `as_skia_canvas_draw_bgra`) is retained as a fallback when `ASC_RENDER_GPU` is
undefined.

An unavoidable pitfall: **Ganesh resets the sampler state on a texture object when it samples an external
texture**, while `stage3d_webgl.cc`, to avoid repeating six `glTexParameteri` calls every draw, caches
filter/wrap state per texture object. So `skia_glue.cc` exposes `sk_gr_set_texture_dirty_hook`, calling back
`s3d_sampler_cache_invalidate()` after `drawImageRect` to clear every live context's `texStateN`/
`samplerStateSet` — otherwise the next frame's draw thinks "already set" and skips setting the GL parameters.

### 3.4 `flash.net`'s web backend: `fetch` + frame-boundary pump

The GL backend lives in `vendor/`, the network backend does not — it is entirely inside `src/runtime.ts`'s
`RUNTIME_PREAMBLE` (the `ASC_HAVE_FETCH` branch, EM_JS/EM_ASM glue), because it is **runtime behavior** rather
than a rendering library.

The shape is **pull/poll** rather than callback: `as_web_fetch_go` (EM_JS) starts `fetch()` and pushes an entry
into `globalThis.__ascHttpQ`; `as_web_fetch_pump()` drains the queue at **the top of `as_async_tick`**.
This shape was chosen because it needs no change to `EXPORTED_FUNCTIONS` and no C-side callback export, and a
≤1-frame delay is **unobservable** — `flash.net`'s terminal events must be dispatched at the frame boundary
anyway.

The queue is a **single ordered queue** (chunk < done < error), ensuring body chunks always land before the
terminal state; job identity is **`(pointer, sequence)`** (`as_job_find`) — a malloc address can be reused
(ABA), and using only the pointer would deliver an old entry to a new loader. Every finished fetch also counts
as a `progress` watermark for local replay.

Conversely, **on web you cannot use a blocking spin to wait for results** (the `tickTimers()` approach starves
browser promises and `fetch` never resolves): AS3 code must be event-driven, letting `main()` return and
handing control to the rAF frame loop.

Two contracts that **must be verbatim-aligned with native** (added in stage eighty-nine / fifty-six, previously
inconsistent between the two ends):

- **`URLRequest.contentType` must really be sent as the `Content-Type` request header**. On native,
  `as_http_perform` always did so; on web it must be set explicitly — `fetch` adds Content-Type automatically
  only for `string`/`Blob` bodies, and **never for the `Uint8Array` this backend passes**. The symptom of
  omitting it is "the server complains the request body is missing a field": measured with the same JSON login
  body, without this header the answer was
  `{"code":200002,"message":"platform field is required"}`, and with it the accessToken was returned — it fails
  **very much like the app's own bug**, when it is actually a missing header at the transport layer. Its
  condition matches native (when the request has a body), and a same-named header in `requestHeaders` takes
  precedence.
  **Since stage eighty-nine / sixty-nine both ends share one rule** (`as_http_effective_ctype(j)`,
  `runtime.ts`): no body → do not send; a non-empty body with no declaration (or a declaration of `""`) → send
  urlencoded — note this is the **send** default, and `req.contentType` itself is always `null` in adl (see
  `flash-net.md` §6.7.7); the native side must also suppress the same-named header libcurl adds to every POST.
- **Remote images (`Loader.load(http(s)://…)`) also go through this seam**: the JS side only `fetch`es the
  bytes, with decoding done in the frame-boundary pump (the browser has no worker thread to hide it in, at the
  cost of a few ms per frame, one image per job), producing pixels and encoded bytes **item-by-item identical**
  to native's curl branch.

### 3.5 Page debugging channels: `window.__ascStdout` / `__ascStderr` / `__ascErrors`

A wasm page has no stdout — `trace()` output and load/runtime JS exceptions, if they only go to the console,
are unreadable for a human (not on the same screen as the picture) and unavailable to automation. So the
generated `index.html` wires both into globals up front:

```js
window.__ascStdout = [];   // Module.print  → one line per trace()
window.__ascStderr = [];   // Module.printErr
window.__ascErrors = [];   // window 'error' + 'unhandledrejection'
```

These three are the same data for both the user and automation (`temp/run_webprobe.sh` relies on
`__ascStdout` to read a web build's assertion results, because the page runs in the browser and the harness
cannot read its terminal directly).

### 3.6 Localizing a wasm trap to a source function: named rebuild + an error hook before the script loads

Without `-g`, emscripten gives only `Uncaught RuntimeError: null function` plus a bare offset
(`at 01a3921a:0x4ff0aa`) for a trap — the address cannot be mapped back to a C function, which amounts to no
stack. Both are needed:

1. **Named rebuild**: `-g` must go into emcc. Note **`--opt` takes only one argument** (`--opt "-O2 -g"` is
   treated as a single argument `-O2 -g` passed to emcc, reporting
   `invalid optimization level: -O2 -g`), so point `EMSDK_HOME` at a wrapper that appends `-g` at the
   `upstream/emscripten/emcc` location (`upstream/bin` symlinked back to the real SDK) — no need to change
   `build.ts`. The build will show
   `warning: running limited binaryen optimizations because DWARF info requested` — this is `-g`'s expected
   cost.
2. **The hook must be installed before the page script**: the trap happens in the main loop after `main()`,
   while the generated `__ascErrors` stores only `ev.message`. Use CDP's
   `Page.addScriptToEvaluateOnNewDocument` (`temp/dbg_stack.sh`, internally going through
   `temp/cdp_eval.mjs --pre=`) to first install a listener that captures `ev.error.stack`, and only then do you
   get the full symbolized stack; installing it afterwards is too late.

Reading it: `null function` and `table index is out of bounds` are the same thing (an illegal `call_indirect`
index). A common source is **an indirect call through a function pointer stored in an object** (`FILE`'s
`close`, Skia's GL function table, our own vtable/thunk). If the top of the stack lands on a seemingly
unrelated libc function (stage eighty-nine / seventy's `fclose`), that is usually not libc's problem but the
**object passed in having been freed or corrupted** — at that time `as_job_retire` was closing an already
`close()`d `FILE*` again.

## 4. Fonts: Network Loading + Runtime Injection

The wasm sandbox has no system fonts to enumerate, so the `CoreText` backend is unavailable. The web font
chain:

1. The page JS, in `Module.onRuntimeInitialized`, `fetch`es the byte stream of each `font-urls` entry;
2. `Module._malloc` allocates wasm memory and `HEAPU8.set` writes the bytes;
3. `Module._sk_fontmgr_register_data(ptr, len)` injects into Skia;
4. Only after all injections are complete does `Module._main()` run (fonts must be in place before the first
   render).

On the Skia side (`skia_glue.cc`'s `#ifdef __EMSCRIPTEN__` branch):

- The global `g_font_datas` accumulates the injected `SkData`; `sk_fontmgr_register_data` clears
  `g_fontmgr_cache` after each injection, rescanning the next time a manager is constructed.
- `sk_platform_fontmgr()`: with no fonts → `SkFontMgr_New_Custom_Empty()`; with fonts →
  `SkFontMgr_New_Custom_Data(g_font_datas)`, using FreeType to scan each font's data, building the
  family→typeface table, from which `matchFamilyStyle` / SkParagraph find injected fonts by name.
- `sk_fontmgr_register_data` is exported to JS with `EMSCRIPTEN_KEEPALIVE`.

> Injection-order constraint: `sk_default_typeface()` / `sk_textlayout_collection()` are function-local static
> caches, fixed on first call. Fonts must be injected before their first call — the HTML bootstrap script
> guarantees this (inject first, `_main()` after).

> **Failure mode: no fonts = all text silently disappears**. There is no enumerable system font in the sandbox;
> when `font-urls` is empty, step 3 of the chain does not happen, `sk_platform_fontmgr()` stays at
> `SkFontMgr_New_Custom_Empty()`, and `drawString` draws not a single glyph. The manifestation is that a
> TextField's **background is drawn as usual while all glyphs are missing** — it looks like "the layout is
> there but the text is gone", and both compilation and running succeed, making it a **silent error**.
> `--air-app` automatically scans the app directory's `.ttf/.otf/.ttc` into `font-urls` (`air-app.ts`'s
> `findAppFonts`, no descriptor change needed); if an app uses `flash.text` yet cannot resolve a single font,
> `--air-app` prints a warning naming the symptom and two fixes (drop in a font yourself, or specify one via
> the descriptor's `<embedFonts>`). **native/adl is unaffected** (CoreText enumerates installed fonts), so this
> is a **web-only** pitfall: the same `url-test` shows text normally under adl/native, and only in the web
> preview is it a blank box (measurement in §6 item 1).

## 5. Key Implementation Constraints (compile/link time)

These are inherent requirements of "linking the wasm build of Skia", already baked into `build.ts`'s web
compile logic, with nothing for the user to hand-write:

### 5.1 `SK_TRIVIAL_ABI` must match libskia.a

The wasm `libskia.a` is compiled with `is_trivial_abi=true` (`gn/BUILDCONFIG.gn`'s default), so `sk_sp` carries
`[[clang::trivial_abi]]`. The C++ glue layer (`skia_glue.cc`/`web_glue.cc`) must be compiled with the same
define `-D SK_TRIVIAL_ABI=[[clang::trivial_abi]]`, otherwise every Skia call's ABI mismatches — wasm-ld reports
a `function signature mismatch` warning, and **at runtime it crashes with `unreachable`, with no compile-time
error**. `build.ts` already adds that define for C++ sources automatically.

### 5.2 `EXPORTED_FUNCTIONS` must export the font-injection entry points

The page JS needs to call `_malloc`/`_free`/`_sk_fontmgr_register_data`/`_main`. Emscripten by default exports
only `_main` and `EMSCRIPTEN_KEEPALIVE` symbols, and `_malloc`/`_free` are not among them; once you explicitly
write `EXPORTED_FUNCTIONS` it **overrides** the default exports (`_main` disappears). So `build.ts` exports
them all at once:

```
-s EXPORTED_FUNCTIONS=["_main","_malloc","_free","_sk_fontmgr_register_data"]
```

Missing `_malloc`/`_free` makes font injection silently fail (`Module._malloc is not a function`) and text
render blank; missing `_main` means nobody starts main under `INVOKE_RUN=0`.

### 5.3 The Number→int coercion must go through `as_to_int32` (under wasm `(int)NaN` traps)

AS3's `int(x)` and the implicit `Number→int` coercion are ECMA-262 §9.5's `ToInt32`: `NaN`/`±Infinity` map to
0, and a finite value is truncated and wrapped to 32 bits. Generating C's `(int)x` directly is **undefined
behavior** for `NaN`/`Infinity` — native (x86) happens to give a garbage value (e.g. `-16`), while under wasm it
triggers an `unreachable` trap that crashes the whole program (the `Timer.repeatCount = NaN` assertion in the
full `air-native` demo crashes for exactly this reason).

Fix: `runtime.ts` provides `as_to_int32(double)` / `as_to_uint32(double)` helpers (`isnan`/`isinf` → 0, `fmod`
wrapping by 2^32), and `emit.ts`'s `convert`/`toInt32Expr`/`toUint32Expr` use these two helpers for any
`number` source, replacing all `(int)`/`(unsigned int)` coercions. This guarantees native/wasm/web agree on the
`Number→int` result for the same AS3 (e.g. `t.repeatCount = NaN` uniformly stored as 0).

### 5.4 The generated page must swallow `emscripten_set_main_loop`'s `'unwind'` sentinel

`main()` ends with `emscripten_set_main_loop(main_loop, 0, 1)` (`simulateInfiniteLoop=1`), which **throws the
string `'unwind'`** to unwind the wasm stack (Emscripten internally expresses "does not return" as an
exception). Emscripten's own `run()`/`callMain()` swallow this sentinel, but the generated page calls
`Module._main()` directly inside `async function onRuntimeInitialized()`, so it floats to the top and becomes
`Uncaught (in promise) unwind` — every web build gets one extra false error in the console.
So `src/index.ts`'s `writeWebIndex` wraps the call:

```js
try { Module._main(); } catch (e) { if (e !== 'unwind') throw e; }
```

(only this one sentinel is swallowed; everything else is rethrown, so real errors remain visible. Note
`_emscripten_throw_longjmp` throws `Infinity` rather than `'unwind'`, which is not the same thing.)

**A corollary of the same fact (easy to trip over)**: since `main()` is **stack-unwound**, **AS3 statements
written after `showWindow(...)` never execute**. The startup chain (registering listeners, sending requests)
must be written before `showWindow`, with `showWindow` as the last statement. This seems counter-intuitive
(on native, statements after `showWindow` returns do continue executing), but it is the direct consequence of
"the frame loop is driven by the browser".

## 6. Known Limitations

1. **Depends on the network and font size**: fonts are `fetch`ed at runtime, so offline/intranet is
   unavailable; a full-package CJK font is large, and the first render must wait for the download + FreeType
   scan to finish (scanning a large `.ttc` set is slower; the example uses a 773KB Arial to demo English, and
   CJK scenarios should swap in a smaller character set as needed).
   - **Font coverage = the range of text that can be displayed**: a missing glyph is per-character and does not
     error. `url-test` prints the login response's JSON as-is into a TextField, containing Chinese
     (`住友制药`/`视频通话`/`我的会议`…), so it carries a 7.9 MB `MiSans-Regular.ttf` (measured: Arial's and
     Ubuntu-R's cmap hit 0/8 for these characters, MiSans 8/8). With only a Western font, those Chinese
     characters render as ▯, **without erroring**.
   - **Fonts are downloaded only once (since stage eighty-nine / fifty-eight)**: a font's actual source is the
     page's `fetch` + `_sk_fontmgr_register_data` injection, and the copy in the wasm FS is never read
     (measured: replacing a page's `.data` with a font-free version and having the font come only over HTTP,
     text still renders). But `--air-app`'s `preload-paths` packs the whole app directory, so
     `assets/fonts/*.ttf` once also went into `.data` — `url-test`'s `.data` therefore grew from 4.5 KB to
     7.9 MB, roughly doubling the page's total download. The generator now also lists these fonts in
     `preload-excludes` (→ link-time `emcc --exclude-file`), excluding **only** fonts, not others: bitmap fonts
     (`.fnt` + atlas) must be read by the app via `File` and stay in the FS. Measured: `url-test.data` back to
     4572 B, Starling reduced by exactly `Ubuntu-R.ttf`'s 359668 B, with no change to text or asset loading on
     either end.
2. **Semi-transparent presentation has a color shift**: premultiplied alpha blitted directly to canvas is
   exact for opaque pixels and shifted for semi-transparent ones (§3.1).
3. **The frame-rate ceiling = the refresh rate of the panel the window is on**: rAF follows the display's
   refresh rate, which software cannot exceed — on a 50 Hz screen it is 50 fps. To get 120 fps the window must
   be on a 120 Hz panel (especially to confirm with multiple displays of different refresh rates, see §3.2 and
   `temp/web-fps/fps_probe.mjs`).
4. **The frame rate is quantized to an integer fraction of the refresh rate**: pacing is expressed in whole
   vsyncs (§3.2), so the frame interval can only be `skip` times the refresh period. For example, on a 60 Hz
   screen `frameRate=24` has only the candidates 30/20, taking the nearest 20 fps (native going through
   `SDL_Delay` + vsync is subject to the same constraint, so the two ends agree).
5. **`emscripten_set_main_loop` blocks**: like the SDL event loop, the frame loop is driven by the browser, and
   the program does not return from `stage.showWindow` before the page is closed.
6. **The WASI combination is unchanged**: `--target wasm --package raw` is still a WASI command-line module
   with no rendering; browser rendering only goes through `--package web`.
7. **Stage3D presentation is now GPU direct** (§3.3, stage eighty-nine / thirty-one): `sk_gl_draw_texture`
   wraps the render target's GL texture as a `GrBackendTexture` and draws it directly into the canvas, **no
   longer `glReadPixels`-ing back to memory every frame**. Measured single-frame `renderMs` drops from 3.21 ms
   to 0.12–0.15 ms (**about 23×**), and the cost no longer grows linearly with the target area (the previous
   1280×2160 `Canvas3D` = 11 MB/frame ≈ 13 ms is no longer a problem). The read-back path is retained as a
   fallback when `ASC_RENDER_GPU` is undefined (pixel-identical on both ends, differing only by a `showStats`
   overlay).
   ⚠️ The one mandatory accompaniment: Ganesh changes sampler state when sampling an external texture, so
   `sk_gr_set_texture_dirty_hook` must invalidate `stage3d_webgl.cc`'s per-texture sampler cache after the
   draw (otherwise filter/wrap are missed).
8. **Unsupported AGAL translation instructions are consistent on both ends**: `sgn`/`tld` remain loud errors
   (**never silently produce an empty image**); a translation failure is thrown via
   `as_throw(Error_new(info_log))`, so shader problems appear in the page console.
9. **WebGL2 browser support is required**: the build fixes `-s MAX_WEBGL_VERSION=2` (NPOT textures,
   `DEPTH24_STENCIL8`, upfront `glBindAttribLocation`, the separated stencil API all depend on WebGL2); on a
   browser without WebGL2, `getContext('webgl2')` fails → a context-creation error, rather than a silent
   degradation.
10. **`flash.net`'s web backend is constrained by the browser sandbox** (effective with `ASC_HAVE_FETCH`;
    details in [`flash-net.md`](flash-net.md) §5-E/§6.5):
    - **CORS**: a cross-origin request needs the other side to return `Access-Control-Allow-Origin`; when
      refused it throws an honest `ioError` whose text names the browser failure and CORS (**does not pretend
      success**).
    - **Images are likewise CORS-constrained, and the other side must allow it**: a cross-origin image can be
      **displayed** in the browser (`<img>` does not need CORS), but its **pixels cannot be read** (the canvas
      gets tainted, `getImageData` throws) — and rendering to Skia needs the pixels, so a remote `Loader.load`
      is essentially a read that requires CORS. Measured: the response of
      `https://meeting.talkmed.com/img/*.png` has **no** `Access-Control-Allow-Origin` (only
      `timing-allow-origin: *`), so those two URLs get only an honest CORS `ioError` on web, while
      native/`adl` works normally (curl is not bound by the same-origin policy). To display them, the CDN must
      add `Access-Control-Allow-Origin`, or the page must fetch images through a **same-origin proxy**.
    - **Restricted request headers**: the browser manages `User-Agent`/`Cookie`/`Origin` etc. itself, so the
      controllable range of custom values is smaller than native.
    - **Redirects are unobservable with `followRedirects=false`**: `fetch(redirect:'manual')` yields an
      **opaque redirect** (status 0, headers/body unreadable), so it honestly reports a "redirected but could
      not follow" error rather than fabricating a status-0 success.
    - **Response header names are normalized to lowercase** (browser behavior), faithfully reflected in
      `responseHeaders`.
    - **No `file://`**: relative/file paths have no counterpart in the web sandbox, so a non-http URL errors
      honestly.
11. **`navigateToURL` on web can only do `window.open`**: not a system browser process, with the popup-blocking
    policy decided by the browser; a WASI target with no launcher honestly reports `Error #2032` (see
    `flash-net.md` §6.6).
12. **The web rendering backend is fixed to WebGL2, not WebGPU** (re-verified 2026-10-08, conclusion
    maintained). The wasm build of Skia only compiled Ganesh/WebGL (`out/wasm/args.gn`:
    `skia_use_webgpu=false`, `skia_enable_graphite=false`, `skia_use_dawn=false`, `skia_use_webgl=true`), and
    `vendor/skia/lib/wasm/libskia.a` has **0 Dawn symbols**; the Stage3D backend is `stage3d_webgl.cc`
    (WebGL2 + GLSL ES), with the build fixing `-s MAX_WEBGL_VERSION=2`. **This is not a performance
    compromise**: the bottleneck is rAF / the panel refresh rate, and the GPU path takes only **1.35%** of the
    frame budget (headroom ≈74×; Stage3D presentation via GPU direct gives `renderMs` 0.12–0.15 ms), so WebGPU
    buys no fps. To really adopt it you would have to swap the Skia engine (Ganesh has **no** WebGPU backend ⇒
    migrate to **Graphite + Dawn**) + pull Dawn and rebuild for wasm32 + upgrade Emscripten (currently
    3.1.44) + add a third Stage3D backend; and WebGPU uses **WGSL**, on a different path from native shader
    pass-through toward GLSL ES on the web side. The basis for the determination and the quantified restart
    trigger condition are in `TODO.md` stage eighty-nine / twenty-nine (the WebGPU determination re-review).
