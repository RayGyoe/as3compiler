# HTML5 / Web Rendering — Implementation and Usage

> This document answers: **how to compile an AS3 program into an HTML5-rendered view in the browser, and the
> implementation constraints behind it.** Target combination: `--target wasm --package web`. Positioning: the
> browser-specific supplement to `compile.md` (multi-target build) and `skia.md` (rendering backend).
>
> Status: **implemented and verified end-to-end** (blue rectangle + `TextField` text + runtime font injection,
> rendering correctly inside the browser canvas, no runtime crash).

---

## 1. Target and Artifacts

`--target` sets the machine-code ABI and `--package` sets the distribution form; the two are orthogonal. The
browser target is expressed as `--target wasm --package web`, compiled with Emscripten `emcc`, producing a
three-piece set:

| Artifact | Notes |
|---|---|
| `<base>.html` | Page entry: `<canvas>` + font-injection bootstrap script (generated by `index.ts`, not emcc's default shell) |
| `<base>.js` | Emscripten JS glue (loads wasm, provides the `Module` runtime) |
| `<base>.wasm` | wasm32 machine code (Skia CPU raster + generated C + web glue layer) |

Comparison with other combinations:

| target | package | Backend | Artifact |
|---|---|---|---|
| wasm | raw (default) | wasi clang `--target=wasm32-wasip1` | bare `.wasm` (WASI command module) |
| wasm | **web** | emcc (Emscripten) | `.wasm` + `.js` + `index.html` |
| native | raw | cc | bare executable |
| native | xcode-project | generated Xcode project | macOS `.app` project |

`web` hard-requires `target=wasm` (validated when `src/index.ts` dispatches); `--target wasm --package raw`
keeps the current behavior (WASI command module, loaded by the shim in `examples/wasm-native/`).

## 2. Quick Start

```bash
# Requires the Emscripten SDK (provides emcc) + the wasm build of Skia (vendor/skia/lib/wasm/)
export EMSDK_HOME=/path/to/emsdk

as-aot examples/web/hello-web.as \
  --manifest examples/web/hello-web.build.json
```

Artifacts are generated under `examples/web/`: `hello-web.html` + `hello-web.js` + `hello-web.wasm`. Browsers
cannot load wasm directly via `file://`; serve it over HTTP (`python3 -m http.server`, etc.) and open
`hello-web.html` to see the blue rectangle + `TextField` text.

AIR projects (`--air-app`) also support the web target — one command compiles from `app.xml` to the browser
without a hand-written manifest:

```bash
as-aot --air-app examples/air-native/air-native-app.xml --target wasm --package web
```

The `--air-app` adapter automatically switches to the web backend (`web_glue.cc` + the wasm build of Skia,
dropping SDL2/`objc`/Cocoa frameworks). Fonts come from `app.xml`'s `<embedFonts>` (reads each
`<font><fontPath>` to generate `font-urls`, falling back to `fonts/Arial.ttf` when absent); the artifacts are
`air-native.html` + `.js` + `.wasm`.

`<initialWindow><renderMode>` controls the GPU/CPU rendering split (web target):

| renderMode | Build manifest define | Rasterization backend | Presentation path |
|---|---|---|---|
| `auto` (default) | none | CPU (`SkSurfaces::Raster`) | `putImageData` |
| `cpu` | none | CPU (`SkSurfaces::Raster`) | `putImageData` |
| `direct` | `ASC_RENDER_GPU=1` | **GPU (Ganesh `GrDirectContext` + WebGL2)** | `GrDirectContext::flush` |
| `gpu` | `ASC_RENDER_GPU=1` | **GPU (Ganesh `GrDirectContext` + WebGL2)** | `GrDirectContext::flush` |

`direct`/`gpu` both use full GPU rasterization (efficiency-first, not aligning with AIR's official "direct =
CPU compositing + GPU blit" split): the Skia surface switches from `SkSurfaces::Raster` to the Ganesh backend
and renders directly into the WebGL2 default framebuffer (FBO 0), compositing the whole frame on the GPU (glyph
atlas, gradients, filters all become GPU textures/draws); presentation is just `GrDirectContext::flush()`, with
no more per-pixel CPU↔JS copies. This removes the CPU software-rasterization bottleneck — which previously
locked the web target at ~60 fps.

Example manifest (`examples/web/hello-web.build.json`) key points:

```json
{
  "target": "wasm",
  "package": "web",
  "sources": ["../../vendor/skia_glue.cc", "../../vendor/web_glue.cc"],
  "include-paths": ["../../vendor/skia"],
  "link-libs": ["skia", "skparagraph", "skshaper", "skunicode", "skcms",
    "wuffs", "png", "jpeg", "webp", "webp_sse41", "freetype2", "harfbuzz", "icu"],
  "link-paths": ["../../vendor/skia/lib/wasm"],
  "defines": ["ASC_USE_SKIA=1", "ASC_USE_WINDOW=1"],
  "font-urls": ["fonts/Arial.ttf"]
}
```

Field differences (vs. the native manifest):

- **Do not link `zlib`**: web linking uses `-s USE_ZLIB=1`; Emscripten provides both the zlib headers and
  symbols; an explicit `-l zlib` may actually conflict.
- **New `font-urls`**: the font byte-stream URL list, see §4.

## 3. Implementation Architecture

Reuses the `extern "C"` flat interface of `vendor/skia_glue.cc` (the generated C only calls `sk_*` symbols; the
pixel-rendering logic is identical to native). The browser-side differences are concentrated in two glue files:

| Concern | native | web |
|---|---|---|
| Graphics rasterization | `SkSurfaces::Raster` (CPU offscreen) | same; with `renderMode=direct/gpu`, uses Ganesh (`GrDirectContext` + WebGL2) |
| Font backend | `SkFontMgr_New_CoreText()` (enumerates macOS system fonts) | `SkFontMgr_New_Custom_Data()` + runtime injection (§4) |
| Window / presentation | SDL2 `SDL_PollEvent` blocking loop | `vendor/web_glue.cc`: cpu mode `putImageData` blit; direct/gpu mode `GrDirectContext::flush` |
| Frame driving | SDL event loop | `emscripten_set_main_loop` (internally throttled by `emscripten_get_now`) |
| Input | SDL events | `emscripten_set_mousedown_callback`/`mouseup`/`wheel` |

`vendor/web_glue.cc` keeps the same `extern "C"` signatures as `window_glue.cc` (`sk_window_*` /
`sk_surface_peek_pixels`, etc.), so the generated `.c` needs **no changes** to switch between the native and
web backends.

### 3.1 Presentation: Premultiplied Alpha Blitted Directly to Canvas

`present_frame` uses `EM_ASM` + `putImageData`, taking pixels from `sk_surface_peek_pixels` and blitting them
directly onto the canvas. The pixels are premultiplied alpha: **opaque pixels are exact**; semi-transparent
pixels have a color shift (a difference between canvas semantics and Skia's premultiplied) — a known limitation
(§6).

## 4. Fonts: Network Loading + Runtime Injection

The wasm sandbox has no system fonts to enumerate, and the `CoreText` backend is unavailable. The web font
chain:

1. The page JS, in `Module.onRuntimeInitialized`, `fetch`es each `font-urls` entry as a byte stream;
2. `Module._malloc` allocates wasm memory, `HEAPU8.set` writes the bytes;
3. `Module._sk_fontmgr_register_data(ptr, len)` injects them into Skia;
4. `Module._main()` runs only after all injection is done (fonts must be in place before the first render).

Skia side (the `#ifdef __EMSCRIPTEN__` branch of `skia_glue.cc`):

- A global `g_font_datas` accumulates the injected `SkData`; `sk_fontmgr_register_data` clears
  `g_fontmgr_cache` after each injection, so the manager is rebuilt from scratch the next time it is
  constructed.
- `sk_platform_fontmgr()`: no fonts → `SkFontMgr_New_Custom_Empty()`; with fonts →
  `SkFontMgr_New_Custom_Data(g_font_datas)`, using FreeType to scan each font data and build the
  family→typeface table, from which `matchFamilyStyle` / SkParagraph find the injected fonts by name.
- `sk_fontmgr_register_data` is exported to JS with `EMSCRIPTEN_KEEPALIVE`.

> Injection-order constraint: `sk_default_typeface()` / `sk_textlayout_collection()` are function-local `static`
> caches fixed on first call. Fonts must be injected before their first call — the HTML bootstrap script
> guarantees this (inject first, then `_main()`).

## 5. Key Implementation Constraints (Compile/Link Time)

These are the inherent requirements of "linking the wasm build of Skia", already baked into `build.ts`'s web
compile logic; the user need not write them by hand:

### 5.1 `SK_TRIVIAL_ABI` Must Match libskia.a

The wasm `libskia.a` is compiled with `is_trivial_abi=true` (the default in `gn/BUILDCONFIG.gn`); `sk_sp`
carries `[[clang::trivial_abi]]`. The C++ glue layer (`skia_glue.cc`/`web_glue.cc`) must be compiled with the
same define `-D SK_TRIVIAL_ABI=[[clang::trivial_abi]]`, otherwise every Skia call has an ABI mismatch —
wasm-ld emits a `function signature mismatch` warning, and **at runtime it crashes with `unreachable`, with no
compile-time error**. `build.ts` already adds this define to C++ sources automatically.

### 5.2 `EXPORTED_FUNCTIONS` Must Export the Font-Injection Entry Points

The page JS needs to call `_malloc`/`_free`/`_sk_fontmgr_register_data`/`_main`. Emscripten by default only
exports `_main` and `EMSCRIPTEN_KEEPALIVE` symbols; `_malloc`/`_free` are not among them. But writing
`EXPORTED_FUNCTIONS` explicitly **overrides** the default exports (`_main` disappears). Therefore `build.ts`
exports all of them at once:

```
-s EXPORTED_FUNCTIONS=["_main","_malloc","_free","_sk_fontmgr_register_data"]
```

Omitting `_malloc`/`_free` makes font injection fail silently (`Module._malloc is not a function`), and text
renders empty; omitting `_main` means nobody starts main under `INVOKE_RUN=0`.

### 5.3 Number→int Coercion Must Go Through `as_to_int32` (Under wasm, `(int)NaN` Traps)

AS3's `int(x)` and implicit `Number→int` coercion are ECMA-262 §9.5's `ToInt32`: `NaN`/`±Infinity` map to 0,
finite values truncate and wrap to 32 bits. Directly generating C's `(int)x` is **undefined behavior** for
`NaN`/`Infinity` — native (x86) coincidentally yields garbage (e.g. `-16`), while wasm triggers an
`unreachable` trap that crashes the whole program (the `Timer.repeatCount = NaN` assertion in the full
`air-native` demo crashed for exactly this reason).

Fix: `runtime.ts` provides `as_to_int32(double)` / `as_to_uint32(double)` helpers (`isnan`/`isinf` → 0, `fmod`
wrap 2^32), and `emit.ts`'s `convert`/`toInt32Expr`/`toUint32Expr` always use these two helpers for `number`
sources, replacing all `(int)`/`(unsigned int)` casts. This guarantees that native/wasm/web all produce the
same `Number→int` result for the same AS3 (e.g. `t.repeatCount = NaN` uniformly stores 0).

## 6. Known Limitations

1. **Depends on network and font size**: fonts are `fetch`ed at runtime, unavailable offline/intranet; a full
   CJK font is large, and the first render waits for the download + FreeType scan to finish (large `.ttc`
   collections scan slowly; the example uses a 773KB Arial to demo English — for CJK, replace with a smaller
   glyph subset as needed).
2. **Semi-transparent presentation has a color shift**: premultiplied alpha blitted directly to canvas — opaque
   is exact, semi-transparent has a shift (§3.1).
3. **`emscripten_set_main_loop` blocks**: same as the SDL event loop, the frame loop is driven by the browser,
   and the program does not return from `stage.showWindow` until the page is closed.
4. **WASI combination unchanged**: `--target wasm --package raw` is still a WASI command module without
   rendering; browser rendering only goes through `--package web`.
