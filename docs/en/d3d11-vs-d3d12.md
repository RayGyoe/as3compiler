# D3D11 vs D3D12: why we landed on D3D12, and when D3D11 might be worth touching

> **Status: decision record + mechanism comparison. No code changed, no version bump.**
>
> **Triggers**: two questions — ① "Why does GPUI use D3D11?" (see [`gpui-windows-renderer.md`](gpui-windows-renderer.md));
> ② "Why did we choose D3D12 over D3D11 at the time? I also notice a lot of other apps use D3D11."
>
> This document answers **three things**, in this order (the order matters):
>
> 1. **Why D3D12?** — Not performance. Two hard constraints: Skia has exactly one Direct3D backend on
>    Windows and it is D3D12; and Stage3D must **share the same device and queue** as the 2D compositor (§1).
> 2. **How much of what D3D11 gives for free did we hand-write?** — Itemized, each with its D3D11
>    counterpart and our stage/evidence (§3). This is the concrete content of "D3D11 is less work".
> 3. **Under what conditions should we add D3D11 after all?** — Three specific triggers, two of which
>    are **not** solved by D3D11 (§6).
>
> One-line conclusion: **D3D12 is the only option available to us, not the best option we picked; and
> D3D11's advantages are exactly the part we have already paid for by other means.**

---

## 0. Summary

| Question | Answer | Evidence |
|---|---|---|
| Can Skia use D3D11? | **No.** Ganesh's only Direct3D backend is D3D12: `GrD3DBackendContext` holds `ID3D12Device`/`ID3D12CommandQueue`, and `ID3D11Device` appears nowhere in the source | §1.1 |
| So 2D must be D3D12? | Yes — unless we move to GL (WGL, `--gpu-backend gl`) or pull in ANGLE to translate GLES onto D3D11 | §1.1 |
| Why is Stage3D D3D12 too? | To **share device + queue**: the 3D back buffer is an `ID3D12Resource` Skia wraps directly — zero copy, zero cross-device sync | §1.2 |
| Do we ever claim D3D12 is faster? | **Never.** The one same-machine comparison is 4.9 ms (D3D12 flip) vs 4.5 ms (D3D11 bitblt), and that gap comes from **flip vs blt**, not the API generation | §4 |
| Why do others use D3D11? | They lack our two constraints: they either draw themselves (GPUI), go through ANGLE (Chromium/Flutter), or own a multi-backend RHI (Qt 6) | §5 |
| What D3D11-like capability should we add first? | Not D3D11 — **a software-rasterizer fallback** (we simply fail in VMs/RDP). The smallest fix is a D3D12 **WARP** adapter, not an API swap | §6 |

## 1. The two hard constraints

### 1.1 Skia m124 has exactly one Direct3D backend, and it is D3D12

```c
// vendor/skia/include/gpu/d3d/GrD3DBackendContext.h:28
struct SK_API GrD3DBackendContext {
    gr_cp<IDXGIAdapter1> fAdapter;
    gr_cp<ID3D12Device> fDevice;            // <- D3D12
    gr_cp<ID3D12CommandQueue> fQueue;       // <- D3D12
    sk_sp<GrD3DMemoryAllocator> fMemoryAllocator;
    GrProtected fProtectedContext = GrProtected::kNo;
};
```

- Under `vendor/skia/src/gpu/ganesh/` the graphics backend directories are `d3d` (all `GrD3D*`, i.e. D3D12),
  `gl`, `vulkan`, `mtl` — **there is no d3d11**;
- `grep -rl ID3D11Device vendor/skia/src vendor/skia/include` returns **nothing** (the only hit anywhere in the
  tree is ANGLE's `third_party/externals/angle2/include/CL/cl_d3d11.h`, an OpenCL interop header unrelated to drawing);
- `vendor/d3d_glue.cc` was written by following Skia m124's own reference implementation step by step:
  `tools/window/win/D3D12WindowContext_win.cpp` + `D3DTestUtils.cpp::CreateD3DBackendContext`
  (`TODO.md:7844`, stage 126).

**So D3D12 is Skia's reference path on Windows, and its only path.** "Skia + D3D11" does not exist.

Only two D3D11-adjacent possibilities remain, and both cost extra:

| Path | Cost |
|---|---|
| GL (our existing WGL path) | Not D3D11, but works on older systems; **cannot host Stage3D** (§1.3) |
| ANGLE (GLES → D3D11) | Pulls in a large dependency plus a translation layer; moves us further from "link mature libraries, emit readable C"; and we would still have to solve Stage3D on the GL side |

### 1.2 Stage3D follows along, to share the device

```c
// vendor/stage3d_d3d.cc:1315
// The device and queue come from d3d_glue.cc when the window GPU backend is
// linked (so the composite and Stage3D share one queue), and are created here
// otherwise -- a headless app that only ever reads its render target back.
static int s3d_init_backend(S3DContext* c) {
  SkD3DDeviceFn devFn = (SkD3DDeviceFn)s3d_lookup_export("sk_d3d_shared_device");
  SkD3DQueueFn  qFn   = (SkD3DQueueFn)s3d_lookup_export("sk_d3d_shared_queue");
```

`vendor/d3d_glue.cc:685-686` exports the `ID3D12Device*` and the `ID3D12CommandQueue*` for the Stage3D backend.
The payoff is concrete:

- The Stage3D back buffer is an `ID3D12Resource` Skia wraps directly → `GrBackendTexture` →
  `SkImages::BorrowTextureFrom`: **same device, same queue, zero copy**;
- No cross-device shared texture (NT handle) + full-frame copy + fence pairing per frame;
- No second swapchain, and no cross-API present ordering to coordinate.

If 3D ran on D3D11 while 2D is D3D12, all three would have to be paid again. Same if 2D ran on GL with 3D on D3D11.

### 1.3 Consequence: the GL backend cannot carry Stage3D on Windows

`src/air-app.ts:920` refuses loudly at build time:

```
--gpu-backend gl has no Stage3D backend on Windows: stage3d_d3d.cc targets
D3D12 and stage3d_webgl.cc is wasm-only. Drop --gpu-backend to build the
D3D12 backend, or drop flash.display3D usage from this app.
```

In other words: **on Windows, an app that uses Stage3D can only use D3D12.** That is not laziness — linking a GL
window backend with no corresponding `stage3d_*` implementation yields a software state machine that never
produces pixels, which is the silent wrong result `AGENTS.md` §1.5 forbids.

## 2. Mechanism comparison: what D3D11 gives free, D3D12 makes you manage

This table is the root of the bill in §3. The first two columns are API facts; the right column is where we land.

| Dimension | D3D11 | D3D12 | Where it lands for us |
|---|---|---|---|
| Abstraction | Device + **immediate context** (state-machine setters) | Device + queue + command allocator + command list | `d3d_glue.cc` (single-threaded per frame), `stage3d_d3d.cc` (one list per batch) |
| Pipeline state | Shaders/raster/blend/input layout bound **separately** | **PSO** bundles it (+ root signature) | Up to 16 PSO variants per program (`S3D_MAX_PSOVAR`, LRU-evicted); the key is the whole draw state as a 256-byte string |
| Resource lifetime | Driver tracks hazards implicitly | **Explicit resource states + barriers** | Hand-written `OMSetRenderTargets`/`ResourceBarrier` per batch |
| Descriptors | None (objects bind directly) | **Descriptor heaps + handles** (CBV/SRV/UAV, Sampler, RTV, DSV) | Mip-chained SRVs, `s3d_rtv_cpu`/`s3d_dsv_cpu` |
| CPU–GPU sync | Queue ordering + queries | **Fences**, and you own the slot scheme | `fence_values[3]`, `s3d_wait_slot` |
| Memory / upload | `UpdateSubresource` / `Map(WRITE_DISCARD)`, driver renames | Committed/placed/reserved resources + **upload heaps**; you do the renaming | `s3d_make_upload`, `S3D_CB_REGION` |
| Constant buffers | Overwriting is generally safe (driver renames) | **GPU reads them at execute time** ⇒ several uploads in one frame overwrite each other | One 4096-byte region per draw (stage 173) |
| Swapchain | DXGI, blt or flip | DXGI, flip in practice | `CreateSwapChainForHwnd` + `FLIP_DISCARD` + 3 buffers |
| Minimum OS | Win7 SP1 (+ platform update, FL 11_0) | **Win10 1507 + WDDM 2.0** | The default build cannot start on Win7 (§6) |
| Software raster | `D3D_DRIVER_TYPE_WARP`, a first-class citizen | Also has a WARP adapter, but only via `EnumWarpAdapter` — it never shows up in `EnumAdapters1` | We wire **neither** (§6) |
| Multi-threaded recording | Deferred contexts exist but are rarely used | First-class (parallel command-list recording) | We do not use it (2D single-threaded, 3D one list per batch) |

## 3. What we hand-wrote for D3D12 (itemized)

Each row states what D3D11 has instead, because that is the concrete meaning of "D3D11 is less work".

| # | The mechanism we hand-wrote | D3D11 counterpart | Stage / evidence |
|---|---|---|---|
| 1 | **Three frame slots + fences**: `SK_D3D_NUM_FRAMES 3`; on the Stage3D side `S3D_FRAMES_IN_FLIGHT 3`, each with its own allocator / upload heap / fence value | Buffer renaming is the driver's job; apps barely notice | stage 126; `vendor/d3d_glue.cc:174` |
| 2 | **Constant buffer versioning per draw**: each upload owns a 4096-byte region | `UpdateSubresource` can generally be overwritten in place | stage 173 (all 12 buttons got the last button's mvp) |
| 3 | **Deferred release bound to the next submit**: cannot release on "the last signaled fence" | Refcounting + driver-deferred destruction | stage 174 (before the fix: 171/171 releases happened at `listOpen=1`) |
| 4 | **Keyed PSO cache + `E_INVALIDARG` triage**: write masks, bare `SemanticName`, HLSL field order = stage register number | Shaders and state bind separately; a whole PSO cannot be rejected | stage 132 (three `E_INVALIDARG`s, only found with a D3D12 debug-layer probe) |
| 5 | **Upload resource reuse**: early code created a fresh committed resource per upload, ~100 µs fixed cost each | `Map` a dynamic buffer and go | stage 179 (the 4.4–6.5 ms/frame plateau at 66k objects) |
| 6 | **Device loss must stop the frame**: per-frame `GetDeviceRemovedReason()` gate + one lost path for all three failure entries + `abandonContext()` + 250→4000 ms backoff rebuild | The same concept exists, without the "submitted means it touched a dead resource" coupling | stage 278 (before: 623 × `#1009` → Present failed → AV 386 ms later) |
| 7 | **Blend alpha slots must not reuse a `*_COLOR` factor**: an illegal enum rejects the **whole PSO**, silently dropping every draw in that mode | Set separately; far smaller error surface | stage 175 |
| 8 | **`ResizeBuffers` must wait until every back-buffer reference is gone, with a cap**: `SK_D3D_DRAIN_MS 250`, skip the frame instead of hanging | Same wait, but blt-model timing is far more forgiving | the measurement recorded next to `SK_D3D_DRAIN_MS`: dragging the bottom-right corner wedged the app (`IsHungAppWindow` = true) |

> Accounting note: every row above is **our own implementation defect**, not AIR fidelity debt — `adl` uses a
> **D3D11** renderer, so these paths **do not exist** there. By the `AGENTS.md` §1.5 test they do not belong in the
> fidelity table; they only "fix our own correctness". This is called out repeatedly at `TODO.md:10472`,
> `:10540`, `TODO.md:20203`.

## 4. Performance: we never claimed D3D12 is faster

- **No same-machine D3D11 vs D3D12 A/B has ever been run**, and none should be assumed.
- The only same-machine comparison is a **present-path** one: a minimal pure-Win32 + D3D12 flip program drags at
  **4.9 ms**, while its **D3D11 bitblt** variant drags at **4.5 ms** (`TODO.md:10628`). 0.4 ms apart, and that gap
  comes mostly from **flip vs blt** (a flip-model present only retires when the compositor takes it), **not** from
  the API generation.
- For our workload (2D display lists + a little Stage3D) the bottleneck is CPU-side batching, atlases, layout and
  `flush` timing — not API submission cost. D3D12's genuine structural advantages (parallel command-list recording,
  explicit memory, predictable resource states) do not turn into frame time on a **single-threaded 2D UI**, and on
  the 3D side we record one list per batch, so parallel recording is moot.

Conclusion: **we never got D3D12's benefits and never claimed them; nor did we get D3D11's convenience, because
Skia has no such backend.**

## 5. Ecosystem: why others are on D3D11

The user's observation is correct, but those projects have different constraints:

| Project | Windows backend | Why they can do that |
|---|---|---|
| Qt 6 Quick | **D3D11 by default** (D3D12 requires `QSG_RHI_BACKEND=d3d12`) | Own RHI, multiple backends maintained in parallel; no dependency on a third-party rasterizer's DC shape |
| Chromium / Electron | ANGLE → D3D11 | They need cross-platform GL anyway; ANGLE solves D3D for free |
| Flutter (Windows) | ANGLE → D3D11 | Same |
| WinUI / D2D family | Direct2D (still D3D11 underneath) | 2D only, and they ride the system compositor |
| GPUI (Zed) | **D3D11 directly**, own 8-primitive pipeline | Draws everything itself, needs only 8 primitives, not Skia-level capability (see [`gpui-windows-renderer.md`](gpui-windows-renderer.md)) |

Common denominator: **none of them carry "link a third-party rasterizer whose only Direct3D backend is D3D12",
and none of them target "share a device with our own 3D engine".** We carry both.

A useful corroboration: GPUI uses 3 back buffers (`BUFFER_COUNT = 3`) — for the **same reason** as our
`SK_D3D_NUM_FRAMES 3` (with 2 buffers, DXGI can hold both while the compositor is busy moving the window, and the
acquire wait stretches to two vblanks). Different API, same conclusion — so that one is not D3D12-specific.

## 6. Decision tree: when D3D11 is worth considering

Only **concrete triggers** count; "the ecosystem uses D3D11" does not.

### Trigger A: GPU UI must run on Win7/Win8 or machines below WDDM 2.0

- Today: the default (D3D12) build **cannot start on Win7** — the import-table measurement in `win32.md` §6.1:
  the default build imports 15 DLLs including `d3d12.dll` and `d3dcompiler_47.dll`; the `--gpu-backend gl` build
  imports 13, including `OPENGL32` and **no** `d3d12.dll`.
- **The answer is not D3D11, it is the GL path** (already there), optionally plus a GL Stage3D backend to close the
  hole in §1.3.
- D3D11 only comes up when GL is unavailable too (trigger B).

### Trigger B: GL is unavailable too (VMs / RDP / machines with no GPU driver)

- Today: when WGL only offers `Microsoft Corporation | GDI Generic | 1.1.0`, `gl_glue.cc` **errors out clearly**
  per `win32.md` §6.2 (no fake fallback, no black window). At that point we have **no GPU path at all**.
- This is exactly where D3D11+WARP or D3D12+WARP earns its keep. The three options differ enormously in cost:

| Option | Change | Cost | Status |
|---|---|---|---|
| **D3D12 WARP adapter** | Add `IDXGIFactory4::EnumWarpAdapter` as a last-resort step in our existing adapter enumeration | Smallest; same rendering code | **Unverified** (whether Ganesh D3D12 runs on WARP, and its frame times, are both untested) |
| D3D11 + WARP | A whole new D3D11 backend (and 2D still unsolved, §7) | Large | Not recommended |
| Mesa llvmpipe (`opengl32sw`) | Ship a software OpenGL for the GL path | Large external dependency; GL semantics | Not recommended |

> **Conclusion: the smallest correct answer to trigger B is D3D12 WARP, not an API swap.** This also explains why
> "should we add D3D11?" has long answered "no" — the need it would serve can be reached with about twenty lines of
> enumeration on the existing device path.

### Trigger C: the Windows-side maintenance surface is too big

`stage3d_d3d.cc` is 2,799 lines and `d3d_glue.cc` is 1,268, nearly all of it D3D12-specific boilerplate. But swapping
APIs does not reduce the semantic work (the `s3d_*` ABI's behavioural contract does not shrink under D3D11).
**The answer is more pins and better docs, not a different API.**

### Anti-triggers (things explicitly not to do)

- ❌ Swap to D3D11 "for speed" — no evidence, and the bottleneck is not the API (§4).
- ❌ Swap "to match other frameworks" — our constraints differ (§5).
- ❌ Swap "to write less code" — §1.1 rules out the 2D half, so a half-swap just adds a backend.
- ❌ Detour through ANGLE to reach D3D11 — one more translation layer, and Stage3D would need redoing anyway.

## 7. If we ever do add a D3D11 backend: an honest price tag

This section exists so "should we" has a real number attached. It is not a TODO.

1. **The 2D half — a blocker.** Skia has no D3D11 backend, so a D3D11 window could only host: CPU raster + upload
   (losing Ganesh's GPU batching and atlases), or ANGLE GLES, or D2D. Each means a **second 2D rasterization path**
   to maintain, to align pixel by pixel, and to re-run the visual acceptance in `examples/`.
2. **The 3D half** — `vendor/stage3d_d3d11.cc`: port the `s3d_*` ABI isomorphically (HLSL stays reusable, SM5 is fine
   on D3D11), but PSO→separate state, descriptor heaps→direct binding, fences→queries, three frame slots→driver
   renaming — every one is a rewrite.
3. **Wiring** — a new `--gpu-backend d3d11` in `src/air-app.ts` (with its web / non-Windows refusal branches),
   manifest `sources`/`link-libs` (`d3d11`/`dxgi`/`d3dcompiler`), an `ASC_RENDER_*` macro, another
   `Context3D.driverInfo` label, a `docs/zh-cn/win32.md` checklist row, the `test/unit/backendparity` neutral-name pins,
   plus binary size and the `win7-imports` table.
4. **Testing** — a fresh `unit: stage3d/*` pin set plus real-hardware acceptance of `examples/shmup-stage3d`, with an
   A/B pixel comparison against the D3D12 side.

> One line: **this is not "swap the renderer", it is "add an entire platform backend plus a second 2D rasterization
> strategy".**

## 8. Unverified and honest limits

- **D3D12 WARP is untested**: no data on feasibility (does Ganesh D3D12 run on WARP at all) or on frame time.
- **No D3D11 vs D3D12 same-machine A/B**: the 4.9/4.5 ms in §4 is a flip-vs-blt comparison and must not be read as
  an API-generation result.
- **No Win7 hardware**: all three conclusions in `win32.md` §6 come from import tables + subsystem version + API
  surfaces, not from execution.
- **`adl` is a D3D11 renderer**: therefore no D3D12-side defect constitutes AIR fidelity debt (§3 accounting). The
  flip side matters too — **`adl` cannot be the oracle for D3D12-specific behaviour**; it can only judge "does this
  violate an AIR semantic we actually measured".
