# spectralnorm — 谱范数（Vector.<Number> 密集矩阵-向量乘基准）

## 说明
计算矩阵 `A(i,j) = 1/((i+j)(i+j+1)/2 + i + 1)` 的谱范数近似（幂迭代 10 轮）。
`N = 1000`，测量 `Vector.<Number>` 索引读写与 `double` 内积性能。

## 规模与结果
- `N = 1000`；幂迭代 10 轮（每轮 2 次矩阵-向量乘）
- 输出为谱范数的整数校验和（`floor(result × 1e6)`）
- 校验结果（四路一致）：`result=1274224`

## 性能（纯计算时间，3 批 × 各 3 次，取中位数；越低越好）

| 实现 | 耗时 (ms) | 相对 C |
|------|----------:|-------:|
| C (cc -O2) | 48 | 1.00× |
| JavaScript (Node v24) | 61 | 1.27× |
| **as3compiler** (→ C → cc -O2) | **38** | **0.79× 快** |
| 原生 AS3 (AIR/mxmlc) | 689 | 14.35× |

## 分析

### 1. 0.79×：本项 AOT 反超 C，来源仍是 `-ffp-contract=off`
`Vector.<Number>` 单态化为连续 `double` 数组，索引读写是直接访存；本项也是全套件中 AOT
**相对 C 表现最好**的数值项。但需注意：**这 0.79× 不是「同一份算术跑得更快」**——
同一份生成 C、同一台机器的 A/B：

| 同一份生成 C（`spectralnorm.as` 编译产物） | 耗时 |
|---|---:|
| `cc -O2`（clang 默认，contract **on**，即 C 基线的编译方式） | 45 ms |
| `cc -O2 -ffp-contract=off`（**本项目实际口径**） | **34 ms** |
| C 参考基线（`run.py` 裸 `cc -O2`） | 45 ms |

即：去掉 FMA 收缩后本项反而快 **24%**（循环内是两次乘法 + 归约依赖链，指令选择与
FMA 的交互与 `mandelbrot` 相反），而 C 基线仍停在 contract-on 的 45 ms。
因此在含浮点乘加的基准上，`AOT vs C` 已不是等价算术的比较（详见 `README.md`）。
三批读数 **38 / 38 / 38 ms**，跨批次高度稳定。

### 2. 其余数字
- **原生 AS3 14.35×** 是本套件中差距最大的一项：AVM2 的 `Vector` 索引每次都走
  方法分派 + 边界检查，密集内层循环无法被有效 JIT 优化。反面参照是 `array`（5.95× 于
  原生），可见 AVM2 的瓶颈随容器类型差异极大。
- **JS 批间波动较大**（历史批次曾见 62 / 81 / 65 ms），主要受 V8 JIT 预热与去优化时机影响，
  按单批读数解读该比值并不可靠。本轮三批 61 / 61 / 62 ms，相对稳定。
- `Vector.<Number>` 元素负载已迁入 GC（v0.3.120），但本基准只复用 2 个长生命周期向量、
  不产生垃圾，故与 GC 策略无关 —— v0.4.3 那轮 `binarytrees`/`strings` 因自动回收变慢，本项不受影响。

## 计时口径
- 四路均内部计时纯计算（C: `clock_gettime` / JS: `hrtime` / as3compiler: `Date.getTime` / 原生 AS3: `getTimer`）。
- 原生 AIR 的 `adl` 启动开销（约 2.6s）不计入。
