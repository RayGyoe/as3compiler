# binarytrees — 递归二叉树分配/遍历（对象分配基准）

## 说明
按深度递归构造完全二叉树并遍历计数，测量对象分配与递归遍历性能。
`maxDepth = 14`（约 320 万节点），规模为原生 AS3 与 GC 压力之间的折中。

## 规模与结果
- `maxDepth = 14`；输出三部分：`stretch` 计数、循环 `sum`、`longLived` 计数
- 校验结果（四路一致）：`result=65535,3123888,32767`

## 性能（纯计算时间，3 批 × 各 3 次，取中位数；越低越好）

| 实现 | 耗时 (ms) | 相对 C |
|------|----------:|-------:|
| C (cc -O2) | 73 | 1.00× |
| JavaScript (Node v24) | 30 | 0.41× |
| **as3compiler** (→ C → cc -O2) | **97** | **1.33×** |
| 原生 AS3 (AIR/mxmlc) | 345 | 4.73× |

## 分析

### 1. 293 → 97 ms：离屏自动回收的下限由 1 MiB 抬到 8 MiB（阶段八十九·四十七）

v0.3.137（阶段八十九·四十一）为**非 GUI 程序**补上了 `gc_alloc` 内的分配阈值自动触发，
但下限固定 **1 MiB**；上一轮实测本项因此从 80 ms 涨到 293 ms（+266%），登记进遗留表。
本轮先做**逐相位计时分解**（临时探针，`ASC_GC_STATS` 门控，测完即删）再定方案：

| 相位 / 单次 | 1 MiB | 4 MiB | 16 MiB | 64 MiB |
|---|---:|---:|---:|---:|
| 回收次数 | **154** | 45 | 24 | 20 |
| `drain`（`gc_mark_drain`，标记存活集） | **1.08 ms** | 1.04 | 1.02 | 1.03 |
| `sweep` | 0.34 | 0.51 | 0.75 | 0.85 |
| `prep`（`gc_new` 归位 + `gc_all` 置白） | 0.20 | 0.25 | 0.34 | 0.37 |
| `stack`（保守栈扫描）**总计** | **0.3 ms / 154 次** | 0.1 | 0.1 | 0.0 |
| **GC 总计** | **247–258 ms** | 81 | 50 | 45 |

关键结论：**一次回收的开销 65% 花在「重新标记存活集」上，而它与「上次回收后累积了多少垃圾」
无关**（本项存活集恒为 ~1 MB，故 `drain` 单次在四个间隔下都是 1.02–1.08 ms）。
于是**总 GC 时间 ≈ 次数 × 常数**，唯一杠杆是「少收」。此前怀疑的保守栈扫描
（`gc_mark_stack` 逐字扫活栈）**合计只占 0.3 ms / 154 次，完全不是瓶颈**。

修法（`src/runtime.ts`）：下限按路径二分，帧路径保持 1 MiB、**离屏路径 `GC_NONGUI_FLOOR` = 8 MiB**
（两条路径目标相反：帧路径要每帧停顿有界，离屏无帧时限、要摊薄单次固定开销）。改后：

| 离屏下限 | 回收次数 | 耗时 (ms) | 峰值 RSS |
|---------:|---------:|----------:|---------:|
| 1 MiB（改前） | 154 | 287 | 9 MB |
| **8 MiB（选定）** | **24** | **97** | **15 MB** |
| 16 MiB | 24 | 88 | 23 MB |

8 MiB 已拿到 96% 的可得收益（12 MiB 后饱和于 88 ms），内存开销只有 16 MiB 方案的一半。
另有一处同源开销一并消除：`gc_trigger()` 需汇总 24 个 `gc_dbg_type_*` 计数，而 `gc_alloc`
**每次分配**都要判定一次——**上一轮记录为「批次波动」的 293 vs 277 ms 其实就是它**
（`ASC_GC_THRESHOLD` 会短路该求和，故其读数更快 11 ms）。现缓存在 `gc_trigger_next`，
仅在 `gc_finish_cycle` 失效重算。

### 2. 剩下的 97 ms 里，GC 只有 ~51 ms，且大部分是基准自身显式 `System.gc()` 的成本

改后相位分解：`n=24`，`prep` 8.0、`drain` 24.9、`sweep` 17.9、`stack` 0.1（单位 ms，
`ASC_GC_STATS` 开启时有额外打印开销），**GC 总计 ≈51 ms / 总耗时 97 ms**。
那 24 次里有 **20 次是基准自己写入的显式 `System.gc()`**，自动触发只剩 4 次
（即自动回收在此负载上已基本让位）。对照「完全关闭自动回收」的 81–82 ms，
可见本项的最优已接近纯显式回收。

### 3. 为什么不干脆完全关掉自动回收

因为它是「无帧程序不退化到 O(N²)」的唯一防线（`strings` 上一轮的 712 ms / 453 MB 就是反例），
且 8 MiB 下限已把重复劳动压到 4 次。完全关闭只能买到 ~15 ms，代价是失去对无显式 GC 程序的保护。

### 4. JS（0.41×）快于 C 不是 C 的缺陷

V8 的分代 GC 让分配几乎免费，而 C 版为算法完整性显式写了递归 `freeTree`。
这是「手动内存管理的成本」与「分代回收的收益」的对照。

### 5. 相对原生快 3.56×

AVM2 的对象分配 + 标记清除 GC 开销同样显著（345 ms）。本项仍有提升空间的方向是
**分代/复制式回收**（把「每次回收重标整个存活集」的常数成本降下来），但那超出当前 Mark-Sweep 架构。

## 计时口径
- 四路均内部计时纯计算（C: `clock_gettime` / JS: `hrtime` / as3compiler: `Date.getTime` / 原生 AS3: `getTimer`）。
- 原生 AIR 的 `adl` 启动开销（约 2.6s）不计入。
- 计数器构建、阈值扫描与对照数据由**临时变体**测得（改 `ASC_GC_THRESHOLD` / 注入计数器后重编），
  测量后即删，不随基准提交。
