# stringbuild — 循环字符串累加（`s += "ab"`）

## 说明
每轮从空串开始，向同一个串**追加 2000 次**两字节片段，收尾读 `length` 与
`indexOf("ba")`；共 150 轮。这条形态对应真实程序里最常见的字符串构建方式（拼 JSON / CSV /
HTML / 日志缓冲 / 字符串模板），而它的成本由**`+` 是否拷贝**决定：

- 拷贝实现（每次 `+=` 复制整个左侧）⇒ 总工作量 O(n²)；
- 惰性 cons（rope）实现（把「左 + 右」存成节点，只在真正读取时摊平）⇒ O(n)。

四路**都不写显式 `System.gc()`**：AOT 侧按 8 MiB 阈值自动增量回收，AIR 侧走 AVM2 自己的 GC，
两边都只承受各自默认回收策略的成本，避免把手工回收算进差异。

## 规模与结果
- 轮数 150 × 每轮 2000 次追加 = **300,000 次 `+=`**，每次产出 2 字节
- 校验结果（四路一致）：`result=600150`

## 性能（本机 macOS arm64，clang，每路内部 3 次取中位数；越低越好）

| 实现 | 耗时 (ms) | 每次追加 |
|------|----------:|---------:|
| C (cc -O2，realloc 容量加倍) | **< 1**（us 计时 0.39 / 0.52 / 0.55） | ≈1.5 ns |
| JavaScript (Node v24，V8 rope) | 3 | ≈10 ns |
| 原生 AS3 (AIR 51.4.1 / mxmlc) | **18** | **≈60 ns，与长度无关** |
| **as3compiler**（→ C → cc -O2） | **125 ~ 131** | ≈420 ns，**随串长线性增长** |

> C 列稳定落在 1 ms 计时分辨率以下（同机微秒计时 393 / 521 / 552 µs），故本项**不以 C 为归一化
> 基准**：差异不在常数倍，而在复杂度（C 的追加是摊还 O(1)，我们是每次全量拷贝）。
> AIR 的 60 ns/次在 1000 字符与 4000 字符两档上**完全相同**（另测：50 µs vs 200 µs，见下），
> 即每次追加成本与已累积长度无关。

## 分析

### 1. 差距是 **O(n²) vs O(n)**，不是常数因子

同一台机器、同一形态、只改累积长度（`temp/tfperf/strperf.as` 与 `adl/` 下的同源 AIR 探针）：

| 单轮追加长度 | as3compiler | 原生 AIR | 倍数 |
|---|---:|---:|---:|
| 1000 字符 | 125 µs | 50 µs | 2.5× |
| 4000 字符 | **2260 µs** | **200 µs** | **11.3×** |

AIR 从 1000 → 4000 字符是 **4×4 = 线性**（每次追加恒 50 ns），我们是 **125 → 2260 = 18×**
（≈ 二次）。长度继续增大，倍数只会继续扩大——这正是「大段文本拼接在真机上突然卡住」的形态。

### 2. 成本几乎全在 `memcpy`，不在分配器

本项总复制量可手算：每轮追加到 4000 字节，累计拷贝 ≈ 2000²/2 × 2 B = 4 MB，150 轮 ⇒ **600 MB**。
实测 125 ms ⇒ **≈0.2 ns/字节**，正是顺序 `memcpy` 的量级。也就是说这 125 ms 里绝大部分是
「同一段前缀被反复复制」，与 GC、分配器、装箱都无关——`benchmarks/strings` 里已修掉的那两笔
（字符串零填充、审计门）在此**不再是主因**。

对照 `src/runtime.ts` 的 `as_str_concat`：它对两侧各做一次 `strlen`，分配 `la+lb+1`，
再 `memcpy` 两段。`s += x` 在 `src/emit.ts` 里直接发射成 `(s = as_str_concat(s, x))`，
所以第 i 次追加要复制 i×2 字节 ⇒ Σ = O(n²)。

### 3. AIR 为什么是线性

AVM2 在 `+` 上用的是 **cons string（rope）**：结果不立刻物化，只记「左、右、总长」；真正的
摊平发生在读取（`length` 之外还要 `indexOf`、比较、送进文本引擎…）时，并且摊平结果可以缓存。
因此循环里的 2000 次 `+=` 只建 2000 个节点，收尾一次读取摊平一次。

## 后续（不在本基准内）

修法是把 `+` 改成惰性 cons + 首次读取时摊平，属**独立立项**的规模：它要动 GC 类型账目
（新增 `GCT_*` 要明确扫描/叶子语义、写屏障）、并给所有「需要 NUL 结尾缓冲区」的消费者加一层
`as_str_chars()` 入口（漏一个就是读到节点结构体字节）。本基准是那条工作的**前置护栏**：
改之前 125 ms、改之后应当接近 AIR 的 18 ms 量级。

## 计时口径
- C：`clock_gettime(CLOCK_MONOTONIC)`；AS3(AOT)：`Date.getTime`；AIR：`getTimer`（1 ms 粒度）。
- C 的 `time=` 打印整数毫秒，故稳定显示 `0`；上表的 us 数字来自同源码的微秒变体
  （`temp/bench/stringbuild/sb_us.c`，仅测量时使用，不随基准提交）。
- 基准自身的计时区域包含四路各自的默认 GC 行为（见「说明」末段），不含进程启动。
