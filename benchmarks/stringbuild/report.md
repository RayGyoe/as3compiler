# stringbuild — 循环字符串累加（`s += "ab"`）

## 说明
每轮从空串开始，向同一个串**追加 2000 次**两字节片段，收尾读 `length` 与
`indexOf("ba")`；共 **2000 轮**。这条形态对应真实程序里最常见的字符串构建方式（拼 JSON / CSV /
HTML / 日志缓冲 / 字符串模板），而它的成本由**`+` 是否拷贝**决定：

- 拷贝实现（每次 `+=` 复制整个左侧）⇒ 总工作量 O(n²)；
- 惰性 cons（rope）实现（把「左 + 右」存成节点，只在真正读取时摊平）⇒ O(n)。

四路**都不写显式 `System.gc()`**：AOT 侧按 8 MiB 阈值自动增量回收，AIR 侧走 AVM2 自己的 GC，
两边都只承受各自默认回收策略的成本，避免把手工回收算进差异。

## 规模与结果
- 轮数 2000 × 每轮 2000 次追加 = **4,000,000 次 `+=`**，每次产出 2 字节
- 校验结果（四路一致）：`result=8002000`

## 性能（本机 macOS arm64，clang，每路内部 3 次取中位数；越低越好）

| 实现 | 耗时 (ms) | 每次追加 |
|------|----------:|---------:|
| C (cc -O2，realloc 容量加倍) | **2** | ≈0.5 ns |
| JavaScript (Node v24，V8 rope) | 25 | ≈6 ns |
| 原生 AS3 (AIR 51.4.1 / mxmlc) | **199 ~ 200** | **≈50 ns，与长度无关** |
| **as3compiler**（v0.4.417，阶段四百四十二之后） | **7 ~ 8** | **≈2 ns，与长度无关** |
| *as3compiler（v0.4.416 及以前）* | *2423* | *≈600 ns，随串长线性增长* |

> **本项的口径在阶段四百四十二被抬高过**：旧口径 150 轮时，修好后的 AOT 侧读到 `0 ms`
> （`getTimer` 只有 1 ms 分辨率），护栏失效——和阶段四百三十八的 `textmetrics` 是同一个问题。
> 现口径 2000 轮让修好后的读数落在 8 ms（同机 A/B 实测），旧口径读数可按 ×13.3 换算回新口径
> （追加成本对轮数是线性的），上表最后一行即换算后的同口径基线。
> C 列在新口径下仍然只有 2 ms，故本项**不以 C 为归一化基准**：差异在复杂度而不在常数倍。
> AIR 的 ≈50 ns/次在 1000 字符与 4000 字符两档上**完全相同**（另测：50 µs vs 200 µs，见下），
> 即每次追加成本与已累积长度无关；我们现在也是这个形态。

## 分析（阶段四百四十二**之前**的诊断，保留原文）

### 1. 差距是 **O(n²) vs O(n)**，不是常数因子

同一台机器、同一形态、只改累积长度（`temp/tfperf/strperf.as` 与 `adl/` 下的同源 AIR 探针）：

| 单轮追加长度 | as3compiler | 原生 AIR | 倍数 |
|---|---:|---:|---:|
| 1000 字符 | 125 µs | 50 µs | 2.5× |
| 4000 字符 | **2260 µs** | **200 µs** | **11.3×** |

AIR 从 1000 → 4000 字符是 **4×4 = 线性**（每次追加恒 50 ns），我们是 **125 → 2260 = 18×**
（≈ 二次）。长度继续增大，倍数只会继续扩大——这正是「大段文本拼接在真机上突然卡住」的形态。

### 2. 成本几乎全在 `memcpy`，不在分配器

本项总复制量可手算：每轮追加到 4000 字节，累计拷贝 ≈ 2000²/2 × 2 B = 4 MB，150 轮 ⇒ **600 MB**。
实测 125 ms ⇒ **≈0.2 ns/字节**，正是顺序 `memcpy` 的量级。也就是说这 125 ms 里绝大部分是
「同一段前缀被反复复制」，与 GC、分配器、装箱都无关——`benchmarks/strings` 里已修掉的那两笔
（字符串零填充、审计门）在此**不再是主因**。

对照 `src/runtime.ts` 的 `as_str_concat`：它对两侧各做一次 `strlen`，分配 `la+lb+1`，
再 `memcpy` 两段。`s += x` 在 `src/emit.ts` 里直接发射成 `(s = as_str_concat(s, x))`，
所以第 i 次追加要复制 i×2 字节 ⇒ Σ = O(n²)。

### 3. AIR 为什么是线性

AVM2 在 `+` 上用的是 **cons string（rope）**：结果不立刻物化，只记「左、右、总长」；真正的
摊平发生在读取（`length` 之外还要 `indexOf`、比较、送进文本引擎…）时，并且摊平结果可以缓存。
因此循环里的 2000 次 `+=` 只建 2000 个节点，收尾一次读取摊平一次。

## 阶段四百四十二：改成了什么（已落地）

结论先说：**没有做 rope，也不需要 rope**。这条形态里真正要解决的只是「每次 `+=` 都把左侧
整个重拷一遍」，而那个拷贝只在**同一个变量被反复追加**时才发生。所以修法落在发射层，不动
字符串表示：

**只被 `s = expr` / `s += expr` / `s = s + expr` 写过的 String 局部（或脚本级变量）改用一个
可增长缓冲区 `as_sb`**：

```c
as_sb as_sb_s = as_sb_new();                 /* C 局部，栈上有指针 ⇒ 保守扫描保活 */
(as_sb_reset(&as_sb_s, s));                  /* var s:String = "" 的种子 */
as_sb_append(&as_sb_s, "ab");                /* 语句位：不交出去，缓冲区可原地继续长 */
trace(as_sb_read(&as_sb_s));                 /* 读点：交出字节，并标记 handed */
```

正确性靠**两条**契约，缺一不可：

1. **C 变量在两次追加之间是陈旧的**。所有读点都走 `as_sb_read`（`emitVarLexical` 的两个分支，
   以及整体赋值的右值），没有别的地方能读到它；
2. **`as_sb_read` 一旦把字节交出去就置 `handed`，下一次 append 必须另开新块**。所以
   `var t:String = s; s += "X";` 之后 `t` 仍是快照——否则就是「缓冲区原地长，别名被改坏」。

`handed` 是承重的：把它从 `reuse` 判定里去掉，`unit: emit/StringAccumulator` 立刻红
（已实测该变异）。同理，语句位若改成「追加后顺手读出」（值位形态）就会每轮冻结一次、
把 O(n) 打回 O(n²)——这一步的实测落差是 1305 ms → 0 ms（旧口径）。

### 被否掉的两种改法

- **① 运行时按 `char**` 槽位挂私有缓冲区**：无法证明没有别名（`t = s` 之后追加会改坏 `t`）。
- **② `as_str_concat` 复用左块的空余容量**：同一个别名问题——`as_str_concat` 看不到调用点，
  不知道结果会不会被别的变量持有。

两者都需要一个**不存在的别名证明**，所以只能在发射层做：只有发射层知道「这个变量只有这几种
写法」，也只有发射层能把读点改道。

### 测得的收益（交错 A/B，同机、同源、逐轮交替 9 轮取中位）

| | 中位 (ms) | 最小 (ms) |
|---|---:|---:|
| 基线（HEAD，阶段四百四十一） | 2423 | 2409 |
| 本阶段 | **7** | **6** |
| 变化 | **−99.7%** | −99.7% |

`run.py` 四路（新口径，3 次中位）：C 2 / JS 25 / **asc 7** / AIR 200 ⇒ 我们比 AIR **快 28×**，
比 V8 的 rope **快 3×**（V8 的 rope 每次读 `length` 也要维护，且它的 25 ms 里含 GC）。

### 仍然不覆盖的形态（有意保留）

- `s = x + s`（顺序相反）、`s = a + b`（非自引用）仍是整体赋值 + `as_str_concat`，一次 O(n)；
- 被闭包捕获、或在 `with` 体内被赋值的名字**不参与**（陈旧变量过闭包 cell / with 语义会读错）；
- 在 `+=` 之外还有 `++` / `-=` / `for-in` 变量的名字不参与；
- 这两条边界都是「宁可不优化，也不能读错」，`findSbVars` 的遍历是对 AST 的**反射式全量走查**
  （不是按 kind 的白名单），漏一种写法的后果是读到陈旧值，比不优化严重得多。

## 计时口径
- C：`clock_gettime(CLOCK_MONOTONIC)`；AS3(AOT)：`Date.getTime`；AIR：`getTimer`（1 ms 粒度）。
- 新口径 2000 轮下 C 侧仍是 2 ms、AOT 8 ms，都在 1 ms 分辨率之上，不再需要微秒变体。
- 基准自身的计时区域包含四路各自的默认 GC 行为（见「说明」末段），不含进程启动。
