# strings — 字符串 split/join/indexOf/toUpperCase/lastIndexOf（字符串分配基准）

## 说明
对固定句子循环 300,000 次执行 `split(" ").join("-")`、`indexOf("fox")`、
`toUpperCase().length`、`split("quick").join("slow").lastIndexOf("o")` 并累加校验和。
测量字符串分配与常用字符串操作性能。

> 注：本基准需要「替换全部」语义；as3compiler 的字符串版 `String.replace` 只替换第一个匹配，
> 故四路统一用 `split().join()`（与原生 AS3 参考版一致）。

## 规模与结果
- 循环次数：300,000；每次迭代执行 3 组字符串操作
- 校验结果（四路一致）：`result=29700000`

## 性能（纯计算时间，3 批 × 各 3 次，取中位数；越低越好）

| 实现 | 耗时 (ms) | 相对 C |
|------|----------:|-------:|
| C (cc -O2) | 80 | 1.00× |
| JavaScript (Node v24) | 99 | 1.24× |
| **as3compiler** (→ C → cc -O2) | **229** | **2.86×** |
| 原生 AS3 (AIR/mxmlc) | 894 | 11.18× |

## 分析

本项是「高分配量 + 无帧」负载，因此与 `binarytrees` 一起受**离屏回收下限**支配：272 ms
（v0.4.0，1 MiB 下限）→ **229 ms**（v0.4.3，8 MiB 下限）。

### 1. 差距由装箱税主导（固有）
`split().join()` 会先产生中间 `Array`（元素经 `as_value` 24 B 装箱）再遍历拼接。
这层装箱是 AS3 语义固有：除非做「模式融合」窥孔优化（把一个 `split` 的输出直接喂给
`join`、消除中间数组），否则无法消除 —— 而那属于前端做优化，违反项目铁律
（`AGENTS.md` §1）。所以 2.86× 是这条路线下**诚实**的数字。

### 2. 272 → 229 ms：离屏回收下限抬高（阶段八十九·四十七）

相位分解（临时探针，`ASC_GC_STATS` 门控，测完即删）显示本项与 `binarytrees` **形状相反**：

| 相位总计 (ms) | 1 MiB（n=454） | 8 MiB（n=30） |
|---|---:|---:|
| `prep`（`gc_new` 归位 + `gc_all` 置白） | 25.3 | ~16 |
| `drain`（`gc_mark_drain`，标记存活集） | **0.0** | **0.0** |
| `sweep` | 48.5 | ~29 |
| **GC 总计** | **74.4** | **~45** |
| 端到端 | 258 | 229 |

本项**存活集≈0，故 `drain` 恒为 0** —— 没有「重标存活集」的成本，开销全在 `sweep`（∝ 垃圾量）
与 `prep`。所以它的收益机制是「**更少的次数 × 每次扫更多垃圾**」，比 `binarytrees` 的
「次数 × 常数」收益更缓（-29 ms vs -190 ms），但方向一致。

`st_nogc` 变体（**去掉显式 `System.gc()`**，只靠自动触发）的下限扫描：

| 离屏下限 | 耗时 (ms) | 峰值 RSS |
|---------:|----------:|---------:|
| 1 MiB（改前） | 256 | 2 MB |
| **8 MiB（选定）** | **222** | **9 MB** |
| 16 MiB | 215 | 17 MB |
| 256 MiB | 352 | 262 MB |
| 关闭 | **732** | **453 MB** |

**不回收会回到 O(N²)（732 ms / 453 MB），规范回收把它压到 215–256 ms（快 2.9–3.4×）**。
选择 8 MiB 而非 16 MiB 的理由：只差 7 ms，但峰值 RSS 差近一倍（9 → 17 MB）。

### 3. 「回收总是净成本还是净收益」是伪二分
本轮相位分解给出更精确的规律：**收益来自「把堆压小」（避免 O(N²) 的分配规模效应），
成本来自「每次回收的固定动作」**（本项是 `sweep`+`prep`，`binarytrees` 是 `drain`）。
最优落在二者平衡点：次数太多则固定开销吃掉收益（1 MiB 时的本项、以及上一轮把 `binarytrees`
推到 293 ms），次数太少则规模效应回来（256 MiB / 关闭）。8 MiB 落在该点附近。

### 4. 不回收时的 quadratic 增长（机理，仍有效）
| N（无回收） | 内部耗时 (ms) | 峰值 RSS | 每次迭代 |
|--:|--------------:|---------:|---------:|
| 50,000 | 45 | 76 MB | 0.90 µs |
| 100,000 | 190 | 151 MB | 1.90 µs |
| 200,000 | 744 | 301 MB | 3.72 µs |
| 300,000 | 1640 | 450 MB | 5.47 µs |

峰值内存严格线性（≈1.51 KB/次迭代），但**每次迭代耗时随 N 线性上升**，总耗时 **O(N²)**。
分配总量是线性的，故增长来自「堆越大、单次分配越贵」的规模效应（首次适配的小块空闲链
在无回收/无合并下不断变长）。这正是自动回收下限的**存在理由**：它是这条 O(N²) 的唯一防线。

### 5. 与原生 AS3 对比
AOT 229 ms vs AVM2 894 ms，仍快 **3.90×**。AVM2 每次字符串操作都产生新对象且同样有 GC 压力，
但它的 `split/join` 走原生实现，故差距主要来自 AOT 侧 `as_value` 装箱的中间数组。

## 计时口径
- 四路均内部计时纯计算（C: `clock_gettime` / JS: `hrtime` / as3compiler: `Date.getTime` / 原生 AS3: `getTimer`）。
- 原生 AIR 的 `adl` 启动开销（约 2.6s）不计入。
- 扫描表与对照数据由**临时变体**测得（去掉 `System.gc()` 行或改 `ASC_GC_THRESHOLD` 后重编），
  测量后即删，不随基准提交。基准本身的计时区域包含其源码中写入的 6 次显式 `System.gc()`。
