# strings — 字符串 split/join/indexOf/toUpperCase/lastIndexOf（字符串分配基准）

## 说明
对固定句子循环 300,000 次执行 `split(" ").join("-")`、`indexOf("fox")`、
`toUpperCase().length`、`split("quick").join("slow").lastIndexOf("o")` 并累加校验和。
测量字符串分配与常用字符串操作性能。

> 注：本基准需要「替换全部」语义；as3compiler 的字符串版 `String.replace` 只替换第一个匹配，
> 故四路统一用 `split().join()`（与原生 AS3 参考版一致）。

## 规模与结果
- 循环次数：300,000；每次迭代执行 3 组字符串操作
- 校验结果（四路一致）：`result=29700000`
- **每轮迭代约 16 次 GC 分配**（2 个 `Array` + 14 个 `String`，见 §1）

## 分析

### 1. 差距 96% 是 **split/join 的分配**，不是字符串操作、不是 GC 回收

**变体归因**（同一份生成 C，按行区间切块替换；`temp/bench/invest/strings_attr2.py`）：

| 变体 | 耗时 | 结论 |
|---|---:|---|
| v0 原样 | 241 ms | 基线 |
| v1 去显式 `System.gc()`（6 次） | 232 ms | 显式 GC 仅 **~9 ms** |
| v4 零分配下限（只剩 `indexOf`/`strlen`/`lastIndexOf` 扫描） | **0 ms** | **字符串扫描本身免费**（G38 之前的口径，见 §3e） |
| v3 去 split/join（保留 `toUpperCase`） | 10 ms | `toUpperCase` 配一次分配 ≈ 10 ms |
| v6 只保留第一轮 split+join | 136 ms | 第一轮（`split(" ")`+`join("-")`）≈ 136 ms |

即 **~231/241 ms（96%）在 `split().join()`**，其中第一轮 11 次分配占 136 ms、第二轮 4 次分配
占 ~95 ms。字符串比较/查找（`indexOf`/`lastIndexOf`/`strlen`）**≈ 0 ms**。

### 2. 拆到分配器：GC 分配 ≈ 93 ms，GC 回收 ≈ 50 ms

**（a）GC 分配器每次调用的开销（~93 ms，38%）**
把 `as_str_alloc` 改走 arena bump 分配（同样的字节数、无 free-list、无 memset、无计数）：

| 变体 | 耗时 |
|---|---:|
| v0 字符串走 GC 堆 | 248 ms |
| v7 字符串走 **arena bump**（GC 仍在） | **152–159 ms** |

⇒ **~90 ms 是 GC 分配器的每次调用开销**。计数探针实测 **5,700,645 次 `gc_alloc`**
（`temp/bench/invest/strings_alloc.py`），其中字符串分配 ≈ 420 万次 ⇒ **≈ 21 ns/次**。

**（b）GC 回收本身（~50 ms，20%）**
给 `gc_collect` 加计时（`strings_gc.py`）：全程 **60 次回收、累计 49.8 ms**（≈0.83 ms/次）。
注意自动触发的回收（54 次）远多于源码里写死的 6 次显式 `System.gc()` —— 所以「本项受回收支配」
的说法要限定在**自动回收**上。

### 3. 为什么这 ~93 ms 值得单独看：**free-list first-fit 随表长线性退化**

关掉回收会让本项 **慢 3×（733 ms）**，而不是变快。原因不是「回收有净收益」那么笼统：
关掉回收后空闲块不再被复用，`gc_alloc` 的**首次适配空闲链遍历长度随堆线性增长**，单次分配
成本被拉高（旧报告 §4 的 O(N²) 表格是同一现象的另一侧）。这说明单次分配成本的**主因是
free-list 遍历**，而它**可以**被改掉（按 size class 分级空闲链 / 分离小对象链），
属于运行时实现优化，**不触碰任何 AS3 语义、也不是前端做优化**（`AGENTS.md` §1 不适用）。

### 3b. 已落地：空闲链按尺寸分级（阶段一百二十，v0.4.93）⇒ **−15%**

按上面的判据重构 `gc_alloc`/`gc_free` 的空闲链：`gc_free_small[16]`（32 B 一级，上限 512 B）
+ `gc_free_mid` + `gc_free_big`，`gc_find_block` 从请求尺寸所属的类**向上爬**到第一个能放下的块；
**块尺寸不取整**（精确尺寸，`free_bytes` 段账目与 `gc_release_empty_segs` 的判定逐字不变）。

**受控 A/B（同一份生成的 C，只改分配器；`temp/sc/`，每行 ≥3 次读数）**：

| 变体 | strings (ms) |
|---|---:|
| 老的两分链（`free_small` + `free_big`） | 248 / 251 / 273 |
| **尺寸分级** | **211 / 211 / 212** |
| 反向实验：分级但**只搜精确类**（不爬类） | —（该变体在 `binarytrees` 上是 7m23s / 4300×，见 `binarytrees/report.md`） |

即 ~37 ms 直接从「单链 first-fit 的线性退化」里拿回来（570 万次分配 ⇒ 每次约省 6–7 ns）。
**这是 `AGENTS.md` §1.4 的「语义等价时选快的那条路」**：箱子语义、回收时机、`free_bytes`
账目全部不变，只换了空闲链的组织方式。

> 旧报告曾断言 3.01× 是「装箱税主导（固有）」、无合法头部空间。该结论**过于悲观**：
> `split()` 必须返回 `String` 数组（语义要求，无法「模式融合」消除），但**每次分配的成本**
> 是纯实现选择，上面 38% 就在这一项里 —— v0.4.93 已把其中一半拿回来（§3b）。

### 3c. 已落地：分配热路径上的两笔「白付的钱」（阶段一百四十一，v0.4.112）⇒ **−11%**

上面 §2(a) 的「~21 ns/次」里，有两笔是**纯浪费**，与 `split`/`join` 的语义无关：

**① `gc_alloc` 对 `GCT_STRING` 的零填充。** 清零对象体是为了「未初始化的数组槽在标记期读到
 tag 0 而不是野指针」，但 `GCT_STRING` 在 `gc_scan` 里是 **leaf**（`case GCT_STRING: break;`）——
 marker **从不扫描它的字节**，零填充对 GC 没有任何作用；而 `as_str_alloc` 的契约本来就是
「调用方自己写结尾 NUL」（**57 处调用点已逐一复核**：memcpy+显式 NUL、或 snprintf/strcpy，
机械审计 0 例外）。本项 16 次分配里 **14 次是字符串**，所以这笔白工被放得很大。

**② 审计门（`gc_audit_gate`）在关闭态仍被调用。** 它默认关闭，但调用点无条件调用——
**每次分配一次**（`gc_alloc` 入口）+ **每访问一个空闲链节点一次**（`gc_find_block` 内层循环）。
关闭时每次调用只做几个判断就返回，但**调用本身**（序言、字符串实参、重查缓存标志）就是开销，
在 570 万次分配规模上放大成两个百分点级。

**修法**：① `gc_alloc` 对 `GCT_STRING` 跳过 memset；② 三处 `gc_audit_gate` 调用点改成
**就地判缓存标志** `if (gc_audit_mode_cache != 0)`（这正是同文件 `gc_mark_ptr` 早就用的形态），
`-1`（尚未解析）仍会穿过并在门内解析 ⇒ 开启审计（`ASC_GC_AUDIT=1`）时行为逐字不变
（已用 `gc_barrier`/`gc_strings`/`gc_incremental` 三例开启态跑通）。

**受控 A/B（同一份生成的 C，长跑 5×300k，交替 n=10 取 min/median）**：

| 变体 | 长跑（5×300k）ms | 换算单轮 |
|---|---:|---:|
| 基线（两项都不改） | 1242 | 248 ms |
| 只改 memset | 1201 | 240 ms |
| 再改审计门 | **1163** | **233 ms** |

即 memset **−10.4 ms/轮**、审计门 **−11.4 ms/轮**，合计 **−22 ms/轮（≈ −9%）**；
单批基准 222 → **198 ms**（AOT/C 2.91 → **2.44**）。

**顺手证伪了一个想当然的修法**：调大 GC 阈值（「少收」）在本项上**只会更慢**——
`ASC_GC_THRESHOLD` 8 MiB → 226 ms、16 MiB → 253 ms、32 MiB → 313 ms、128 MiB → 895 ms。
本项存活集≈ 0，开销在**分配路径**而非回收次数，所以阶段八十九·四十七 的「少收更省」
结论**只适用于 `binarytrees` 那副形状**。
**另一处已量出但未改**：`gc_alloc` 里 `gc_seg_find(h)` 的段计费（`free_bytes -= ...`）
值 ~10.6 ms/轮，但它**不能删**——它是段归还判定的唯一账本（漏计会让「该段已空」误真、
把活对象的内存还给 OS，即历史上「第二次跑基准 SIGSEGV」那个 bug）；
每类型记账（`gc_dbg_type_bytes[24]`/`count[24]`）值 ~5 ms/轮（2%），但它同时是 `gc_trigger()`
自适应阈值的 O(1) 数据源且 `ASC_GC_STATS` 的类型分解靠它 ⇒ **本轮不动**。

### 3d. 已落地：split/join 的**扫描**趟压实（阶段四百四十，v0.4.415）⇒ **−8.3%**

到 v0.4.414 为止，本项 ~280 ms 里仍有一块纯扫描的浪费，两处都在「量一遍再拷一遍」的形状上：

**① `as_str_split` 每个分片重算一次分隔符长度，且单字节分隔符也走 `strstr`。**
旧循环是 `while ((q = strstr(p, sep))) { …; p = q + strlen(sep); }`——`strlen(sep)` 每分片一次，
`strstr` 对单字节分隔符（`" "` / `","` / `"\t"`，即绝大多数）走的是两字节步进的双串扫描。
改成：源串结束位置只算**一次**（`const char* end = s + strlen(s)`），单字节分隔符走
`memchr(p, sep[0], end - p)`（libc 的向量化搜索），多字节仍走 `strstr`；尾段从 `[p, end)` 拷贝，
不再二次 `strlen`。

**② `as_array_join` 的元素被 stringify + `strlen` 两遍。**
旧形状「第一趟量总长、第二趟拷贝」，两趟都要 `as_v_str_val(元素)` + `strlen`——对字符串元素是
两次 `strlen`，对数字/布尔则是**两次格式化 + 两次分配**（第一次的结果直接丢掉）。
改成：量长趟把分片 `(指针, 长度)` 记下来（栈上 16 槽，超过 16 个元素改用堆表），拷贝趟不再重算。

**受控 A/B（同一份 `.as`，HEAD 基线与本阶段产物交错跑 15 轮）**：

| 变体 | min | 中位 | mean | max |
|---|---:|---:|---:|---:|
| 基线（HEAD `src/runtime.ts`） | 286 | 302 | 305.7 | 337 |
| **本阶段** | **257** | **277** | **275.8** | 294 |

⇒ 中位 **−8.3%**、min **−10.1%**。同一轮 `run.py` 自身读数 281 → 251–267（批间噪声 ±10%，
所以阶段增量只引交错 A/B 的数）。

**一个被证伪的「顺手优化」**：给 split 先数一遍分片数、让结果数组**恰好一次**扩容
（`as_array_new` 的空表按需 0 → 8 → 16，一个 9 分片的 split 要分配两次值缓冲）。实测
交错 A/B：min 242 / 中位 265（预数）vs min 251 / 中位 264（不预数）——**多出来的一趟扫描
正好抵掉省下的那次分配**，所以没有保留。

**边界不变、只换实现**：结果、顺序、空分片、错误全部逐字不变（`examples/split-join-compact.as`
的 23 条断言，期望值取自 `adl 51.4.1` 跑同一份程序；源码形状由 `test/unit/emit.ts` 的
`unit: emit/SplitJoinCompact` 钉住，含「join 的分片缓存只许存数组自己引用的 tag-3 元素」
这条 **GC 安全不变量**——新分配出来的临时字符串只被 C 局部引用，结果缓冲的 `gc_alloc`
可能触发采集，缓存下来就是悬垂指针）。

### 3e. 198 → ~300 的漂移已定位到提交：两笔**有意兑换**，不是回归

逐点重建（每个提交一趟编译，交错 3–6 轮取 min/中位；C 列同期 78–81，未漂）：

| 点 | 提交 | strings (ms) |
|---|---|---:|
| v0.4.112 | `5615d59` | 199–212 |
| v0.4.358 之前 | `0a7a962` | 198–224 |
| **v0.4.358** | `3c79812` | **236–244（+19%）** |
| v0.4.361 之前 | `f83b586` | 232–264 |
| **v0.4.361** | `5c79f1d` | **267–330（+18%）** |
| v0.4.412 | `76c4404` | 278–307 |

- **`3c79812`（v0.4.358）**：`gc_find_block` 加了「同尺寸类最多 8 个探针，然后从 rounded-up
  类起扫」的前缀。它治的是另一副形状的病态（小块洪泛下 30000 次分配 12.9 s，即 §3 的
  free-list 线性退化极端版），代价是本项这种「小块反复分配」的负载每次可能要白扫 8 个节点。
- **`5c79f1d`（v0.4.361）**：String 索引改成 **UTF-16 码元**（G38 语义修复，`examples/
  string-utf16-index.as`）。代价是 `indexOf`/`lastIndexOf`/`.length` 每次调用都要做
  码元 ↔ 字节翻译；§1 表里「字符串扫描本身免费」是这次修复**之前**的口径。

两笔都是有意的兑换（正确性 / 病态防护），所以**本项不再以 198 为基线**，也不把它们记成回退。
下一阶段可回收的部分（已量出方向、未实施）：给码元翻译加 **ASCII 快路径**——一次字级高位置
探测即可判定「码元索引 == 字节偏移」，命中就跳过整趟前缀计数。**注意**：只把
`as_str_indexOf` 的 `as_u16_unit_of` 换成直接返回字节偏移，实测**没有任何改善**
（271/277 vs 基线 269，交错 5 轮），所以成本不在 `strstr` 那条路，而要先把
「零分配下限」按 G38 之后的口径重新归因（`indexOf` / `lastIndexOf` / `.length` 各占多少），
再决定改哪一支——这一项已登记进 `TODO.md` 的遗留表。

### 3f. 已落地：码元翻译的 ASCII 快路径（阶段四百四十一，v0.4.416）⇒ **−12.3%**

§3e 把漂移的第二笔归给 G38 的码元索引，并留了一条待办：「先按 G38 之后的口径重做归因，再决定改哪一支」。
照着做了——**归因结果推翻了原来的假设**。用 `sample` 采一份 30×300k 轮的剖析（自耗时，共 4013 个样本）：

| 帧 | 自耗时样本 | 占比 |
|---|---:|---:|
| `gc_alloc` | 1013 | 25% |
| `gc_sweep_step` | 803 | 20% |
| `gc_collect` | 559 | 14% |
| `main`（AS3 主体 + 被内联的助手） | 452 | 11% |
| `memmove` | 248 | 6% |
| `strlen` / `as_str_len` / `strstr` / `strncmp` / `memchr` | 152 / 110 / 96 / 30 / 48 | 11% |

也就是说本项的账面是 **~59% 在 GC**（分配 + 清扫 + 回收），码元翻译那一层只占约 11%，
`as_u16_unit_of` / `as_u16_locate` 甚至**没进前 20 名**（被内联进 `main`）——§3e 那句
「G38 +18%」在本项上并不落在翻译的**前缀计数**上，而落在 `.length` 变成码元计数之后
多出来的一次全串探测（`as_str_len`）与 `toUpperCase` 的重新分配上。

**三笔改动**（都只换实现，答案逐字不变）：

1. `as_u16_prefix_ascii`：8 字节一字的高位置探测，判定前缀是否纯 ASCII；
2. `as_u16_unit_of` / `as_u16_locate`：命中探测即「码元索引 == 字节偏移」，跳过前缀计数
   （`unit_of` 还改成**从游标续走**，单调扫描的调用方只付「距上次命中」的距离）；
3. `as_str_lastIndexOf_from`：命中探测就走**反向字节扫描**——旧实现只能正向逐字符走，
   因为倒着走每个候选都要付一次字节→码元翻译。

**逐项归因（交错 A/B，10 轮，同一份 `.as`）**：

| 变体 | 中位 | 相对基线 |
|---|---:|---:|
| 基线（HEAD） | 257 | — |
| 三笔全开 | **224** | **−13.0%** |
| 只关 `lastIndexOf` 的反扫 | 251 | −2.3% |
| 只关 `unit_of`/`locate` 的探测 | 224 | −12.6% |

⇒ 本项上 **11 个点是 `lastIndexOf`**，`indexOf` 那侧的探测只值 0.4%（噪声级）——因为
本项的串只有 43 字节，前缀本来就短。**这条探测不是没用，是本项看不见**：另立
`benchmarks/bigscan`（180 KB 纯 ASCII 文本上的 indexOf/charAt/lastIndexOf）后，
同一笔改动的交错 A/B 是 **38 → 10 ms（−73.7%）**，而 `strings` 只有 −12.3%。

**一个被证伪的「顺手优化」**（§3e 已记过，这里给最终结论）：把 `as_str_indexOf` 的
`as_u16_unit_of` 换成无条件直返字节偏移**没有任何改善**——成本不在 `strstr` 那条路，
在「翻译要不要做」「做几遍」。所以最终落地的不是「跳过翻译」，而是**先证明不需要翻译**。

### 4. 其余组成（v0.4.416 后的账）
v0.4.93 后的 210 ms ≈ **split/join 本体 ~100 ms（48%）** + **分配 ~60 ms（29%）** +
**回收 ~50 ms（24%）**；v0.4.112 把分配那项再砍掉 ~22 ms（§3c）⇒ 198 ms；此后 §3e 的两笔
有意兑换把它抬到 ~290 ms，v0.4.415 的扫描压实（§3d）再拿回 ~25 ms、v0.4.416 的 ASCII 快路径
（§3f）再拿回 ~33 ms ⇒ **224 ms**。
本体部分原本是 `as_array_join` 两遍扫（先量长再拷贝，每个元素 2 次 `strlen`）、
`as_str_split` 的逐段 `strstr` + 每分片 `strlen(sep)`、`as_array_push` 的按需扩容——前两项
已按 §3d 压实（现在是单趟量长 + `memchr`）；与 C 参考版（78 ms，3 次 `malloc`）比，
AOT 侧多出来的是每次分配的价格（16 次/轮 vs 3 次）与 GC 回收，回收部分（60 次、累计 49.8 ms）
历轮**未动**。

### 5. 与原生 AS3 对比
AOT 224 ms vs AVM2 894 ms，快 **3.99×**（v0.4.112 口径下是 4.59×：AVM2 侧同时也在变，
但主因是 §3e 的两笔兑换抬高了 AOT 侧）。AVM2 每次字符串操作都产生新对象且同样有 GC 压力，
差距主要来自 AOT 侧更省的装箱/分配路径。

## 历史（GC 下限策略，仍有效）
本项与 `binarytrees` 一起受**离屏回收下限**支配：272 ms（v0.4.0，1 MiB 下限）→ **229 ms**
（v0.4.3，8 MiB 下限）→ 241 ms（v0.4.69）。相位分解显示本项**存活集≈0，`drain` 恒为 0**，
开销全在 `sweep`（∝ 垃圾量）与 `prep`，故其收益机制是「更少的次数 × 每次扫更多垃圾」。
`st_nogc` 下限扫描（去显式 `System.gc()`）：1 MiB 256 ms / **8 MiB 222 ms（9 MB RSS）** /
16 MiB 215 ms（17 MB RSS）/ 256 MiB 352 ms / 关闭 732 ms（453 MB）。选 8 MiB 是因只差
7 ms 而峰值 RSS 近乎翻倍。v0.4.92 的 243 与 v0.4.69 的 241 的差属批次波动；
**v0.4.93 的 210 ms 不是波动**（同 C 的受控 A/B 同期实测 −15%，见 §3b），
**v0.4.112 的 198 ms 更不是**（同样同 C 层 A/B，−9%，见 §3c；且 C 列同期还涨了 3%）。
**v0.4.415 的 277 ms 也不是**（交错 A/B，中位 −8.3%，见 §3d）。

## 计时口径
- 四路均内部计时纯计算（C: `clock_gettime` / JS: `hrtime` / as3compiler: `Date.getTime` / 原生 AS3: `getTimer`）。
- 原生 AIR 的 `adl` 启动开销（约 2.6s）不计入。
- 基准本身的计时区域包含其源码中写入的 6 次显式 `System.gc()`。
- 变体归因脚本与产物留 `temp/bench/invest/`（`strings_attr2.py` / `strings_alloc.py` /
  `strings_gc.py`），测量后不随基准提交。
- **阶段增量一律用交错 A/B**（同一份 `.as` 编译出的两个二进制逐轮交替），因为 `run.py`
  的批间噪声有 ±10%；绝对读数仍以 `run.py` 三批中位数为准。
