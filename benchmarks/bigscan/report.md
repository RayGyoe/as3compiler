# bigscan — 大 ASCII 文本上的 `indexOf` / `charAt` / `lastIndexOf`

## 说明
一个 **≈180 KB 的纯 ASCII 文本**（4000 行 × 44 字节），每轮做：

- 40 次 `indexOf("lazy", p + 1)` 的**逐命中推进**（`p` 从 −1 起，每次从上次命中之后继续）；
- 1 次中段 `charAt(90000)`；
- 1 次带 `from` 的 `lastIndexOf("fox", 100000)`。

共 200 轮。这正是日志 / JSON / CSV 解析里最常见的扫描形态：**命中之后继续搜**，而不是每次都从头。

`result=27141000`，四路一致。

## 这条基准补的是 `strings` 的盲区
`strings` 里被反复扫的串只有 43 字节（`"the quick brown fox …"` 之类的短句），所以
「码元 ↔ 字节翻译」的前缀本来就短，看不见翻译成本随串长增长。把同一层拉开到 176000 字节后：

| 实现 | 存储 | 索引空间 | 需要翻译？ |
|---|---|---|---|
| C | UTF-8 | **UTF-16 码元**（刻意与本项目同语义） | 要（直白实现：每次命中后数一遍前缀 + 游标不续走） |
| JavaScript (Node v24) | UTF-16 | UTF-16 码元 | **不需要** |
| as3compiler | UTF-8 | UTF-16 码元 | 要（快路径：ASCII 探测 + 游标续走） |
| 原生 AS3 (AIR) | UTF-16 | UTF-16 码元 | **不需要** |

## 性能（本机 macOS arm64，`run.py` 每路 3 次取中位数；越低越好）

| 实现 | 耗时 (ms) | 相对 as3compiler |
|------|----------:|----------------:|
| C (`cc -O2`) | 23 | 2.3× |
| JavaScript (Node v24) | **0**（< 1 ms） | — |
| **as3compiler** | **10** | 1.00× |
| 原生 AS3 (AIR/mxmlc) | 1 | 0.1× |

> JS 与 AIR 的 0–1 ms 是「**零翻译**下界」：它们的字符串内部就是 UTF-16，`indexOf` 直接返回
> 码元索引；C 列的 23 ms 则是「同样的 UTF-8 + 码元语义，但翻译写得直白」（每次命中后从字节 0
> 数一遍前缀、`lastIndexOf` 每个候选都翻译一次）。as3compiler 落在两者之间：3 笔快路径
> （ASCII 前缀探测、游标续走、`lastIndexOf` 反向字节扫描）把翻译压到接近零。

## 阶段四百四十一的增量（交错 A/B）
同一份 `.as`、同一次编译，HEAD 基线与本阶段产物逐轮交替跑 10 轮：

| 变体 | min | 中位 | mean |
|---|---:|---:|---:|
| 基线（v0.4.415） | 37 | 38.0 | 38.1 |
| **本阶段（v0.4.416）** | **10** | **10.0** | **10.2** |

⇒ 中位 **−73.7%**。同一笔改动在 `benchmarks/strings` 上只有 −12.3%——那儿的串太短，
正是本条基准存在的理由。逐项归因（关掉哪一笔）见 `benchmarks/strings/report.md` §3f。

## 计时口径
- 四路都只计**纯计算**（C `clock_gettime` / JS `hrtime` / AOT `Date.getTime` / AIR `getTimer`），
  不含进程启动；AIR 的 `adl` 启动约 2.6 s 不计入。
- 文本构建（4000 次 `+=`）在计时**之外**：本项测的是扫描，不是拼接（拼接由
  `benchmarks/stringbuild` 负责）。
- `charAt(90000)` 的 `.length` 恒为 1（ASCII），四路一律计 1，不引入口径差。
