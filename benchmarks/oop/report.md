# oop — 多态虚方法派发 + 对象字段访问（面向对象核心基准）

## 说明
定义 `Figure` 基类与 `Circle`/`Square`/`Rect` 三个子类，各自 `override` 虚方法 `area()`；
把 192 个异构对象装入 `Array`，循环 2000 万次通过基类引用调用 `area()` 并累加校验和。
测量 **虚方法派发（vtable）+ 对象字段访问 + 装箱数组元素解引用** 这一面向对象核心路径。

## 规模与结果
- 规模：3 层类继承 × 3 种子类，192 个对象，2000 万次虚派发
- 校验结果（四路一致）：`result=913853951`

## 性能（纯计算时间，v0.4.93 轮单批 × 内部 3 次取中位数；越低越好）

| 实现 | 耗时 (ms) | 相对 C |
|------|----------:|-------:|
| C (cc -O2) | 48 | 1.00× |
| JavaScript (Node v24) | 59 | 1.23× |
| **as3compiler** (→ C → cc -O2) | **91** | **1.90×** |
| 原生 AS3 (AIR/mxmlc) | 598 | 12.46× |

## 分析

v0.4.93 实测 **91 ms（1.90× C）**，可由三段相加精确分解（分解值是 v0.4.92 轮的受控 A/B 读数，
比例不变）：

| 组成 | 耗时 | 性质 |
|---|---:|---|
| 生成 C 本体（结构体 + vtable + 函数指针派发，与手写 C 等价） | ~48 ms | 与 C 持平 |
| 顶层脚本变量是全局（`g_sum`/`g_j`/`g_s`） | ~7 ms | v0.3.130 的语义修复 |
| **`#1034` 对象解箱校验** | ~43 ms | v0.4.92 的语义补全（见 §2） |
| 合计 | 98 ms | ← v0.4.92 读数 |

> v0.4.93 的 91 ms 与 v0.4.92 的 98 ms 相差 −7%：**同期 C 列也漂了 −6%（51 → 48）**，
> 故这一差不作归因（落在机器状态量级内）；本项本轮**未改任何相关代码**
> （阶段一百二十 动的 `unboxAny` 强转家族与 `array` 基准兼容，本项热路径只做对象解箱）。
>
> 历史：v0.4.69（及之前）本项为 **55 ms（1.12×）** —— 那是**跳过了 §2 那次类型检查**的读数。

### 1. ~7 ms：顶层脚本变量是全局（v0.3.130 的语义修复）
本基准的 AS3 版写成**顶层脚本**（`var sum:int`、`var j:int` 直接写在文件顶层）。
v0.3.130（阶段八十九·三十四「顶层整树 `var` 提升」）修正了顶层变量的语义：按 AVM2
的 **script trait** 规则，脚本顶层 `var` 是**全局对象上的槽位**，不是脚本函数的局部变量。
生成 C 因此用文件作用域全局（`g_sum` / `g_j` / `g_s`）：

```c
while ((g_j < g_N)) {
    g_s = ((Figure*)as_v_req_inst(as_array_get(g_shapes, as_int_rem(g_j, 192)), &Figure_vt, "Figure"));
    (g_sum = (g_sum + (g_s->vtable->area(g_s))));
    ...
    (g_j++);
}
```

热循环每次迭代都要访存这些全局槽位，`-O2` 无法把它们长期驻留寄存器
（`as_array_get` / `as_v_req_inst` / 虚调用 `area` 都会触碰内存）。**这是语义正确的代价**，
不是 codegen 退化。**量化**：把热循环原样移进一个函数（`function run():int { ... }`，
使变量成为局部）后，同一版本编译结果为 **48 ms**（与 C 的 51 ms 基本持平，`result` 一致）。

> 参考实现为什么没有这个代价：C 版把 `j`/`sum`/`shapes` 写在 `main` 里（栈局部），
> AIR 版把整个循环包在类的方法里（也是局部）。三者结构不同，故 AOT 侧多背了一层全局访存。
> 若写成等价的函数封装，AOT 与 C 持平。

**实践建议**：热循环应放进函数/方法，而不是顶层脚本 —— 这也是 AS3 的常规写法。

### 2. ~43 ms：动态值 → 具名类槽的 `#1034` 校验（v0.4.92 新增）
热循环里有一次**动态值 → 具名类变量**的赋值：

```as3
var s:Figure = shapes[j % 192];     // shapes:Array ⇒ 元素静态类型是 *
```

按 AVM2 语义，把 `*` 赋进 `Figure` 槽是一次**运行时强制转换**，类型不符须抛 `#1034`。
本轮在 `unboxAny` 的 `object` 分支补上了该检查 —— 此前发射的是**未检查**的
`((Figure*)as_v_obj_val(...))`，即遗留表第 1 项「静默把装箱指针当对象解引用」：

```c
/* v0.4.69：未检查（语义错误，55 ms） */
g_s = ((Figure*)as_v_obj_val(as_array_get(g_shapes, as_int_rem(g_j, 192))));
/* v0.4.92：vtable 祖先链校验，不符抛 #1034（98 ms） */
g_s = ((Figure*)as_v_req_inst(as_array_get(g_shapes, as_int_rem(g_j, 192)), &Figure_vt, "Figure"));
```

`as_v_req_inst`（定义在 `src/emit.ts`）依次做：`null`/`undefined` 放行 → `as_heap_kind(p) ==
GCT_CLASS` 安全门（防把静态 `as_class` 等非堆对象读成 vtable）→ `as_is(p, target_vt)` 祖先链
校验 → 否则 `as_throw_1034`。

**AIR 确证该检查必需**（`temp/pkgA/arrcoerce`，adl 51.4.1 双端探针 **0/6 行差**）：

| `Array` 元素 | 赋给 `Sprite` 槽 |
|---|---|
| `new Sprite()` | ok |
| `new MovieClip()`（子类） | ok ⇒ **必须走祖先链，不能只比较 vtable** |
| `5` / `"x"` / `{}` | `#1034` |
| `null` | ok |

**成本归因**（同一份生成 C 的变体 A/B，脚本与产物留 `temp/bench/oopattr/`，每行 ≥3 次读数）：

| 变体 | 改动 | oop AOT (ms) |
|---|---|---:|
| v0 | 现状 | 97–98 |
| v1 | 去掉 `as_heap_kind(p) == GCT_CLASS` 安全门（保留 `as_is` 链校验） | 89–90 |
| v2 | 循环内解箱换回**未检查**的裸 `as_v_obj_val`（＝v0.4.69 口径） | **54–56** |
| v3 | `as_int_rem(g_j, 192)` 换成裸 `%` | 96–98 |
| v5 | `as_v_req_inst` 换成平凡函数体（保留同样的调用形态） | 53–55 |
| v6 | 先做「vtable 精确匹配」快路径，再走安全门 + 链校验 | 98 |

四条结论：① 43 ms **全部**来自这次检查本身，**不是**调用/内联形态所致（v5：函数体一变平凡，
耗时即回到基线）；② 安全门只占 8 ms，且它是防「把静态 `as_class` 当堆对象读头」的唯一屏障，
去掉要付正确性风险，故保留；③ 余下 ~35 ms 是**祖先链校验** —— 2000 万次
「对象 → vtable → super」两级**依赖随机访存**，而链是语义要求的（子类必须通过），省不掉；
④ 精确 vtable 快路径（v6）救不了本项：192 个元素都是 `Figure` 的**子类**实例，精确匹配必失败。

**未做进一步优化**：可回收的只有那 8 ms（安全门），余下 35 ms 是 `adl` 同样要做的类型检查。
按 §1.5「绝不静默降级」，本轮**如实登记**为语义代价。

### 3. 与 C 的其他差异可忽略
除上述两项外，AS3 类被翻译为 C 结构体 + vtable，`override` 虚调用编译成一次
函数指针间接调用、字段访问编译成一次直接内存访问，与手写 C 的函数指针派发等价。
AOT 侧还多走了一层 `Array` 的 `as_value` 24 B 装箱元素（解箱后再虚派发），
但因 192 个元素（≈4.6 KB）与 192 个实例都常驻 L1，装箱开销被缓存完全吸收 ——
这与 `array`（2000 万元素、远超缓存、内存带宽受限，5.41× C）形成清晰对照：
**装箱税的可见程度取决于工作集是否超出缓存**。

### 4. 整数 `%` 零除数守卫无可测成本
热循环内 `shapes[j % 192]`（2000 万次取模）经 `as_int_rem`（v0.3.127 加入除零守卫）。
上表 v3（换成裸 `%`）实测 96–98 ms 对现状 97–98 ms，**无可测成本**。

### 5. 相对原生仍快 6.57×（v0.4.93）
AVM2 的虚方法派发需动态属性查找 + 方法解析，对象字段访问经属性槽位间接寻址，
`Array` 元素还需装箱/拆箱，**且同样要做这次 `#1034` 强制转换**，叠加成本远高于
一次函数指针调用。

### 6. JS 1.16×
V8 对单态调用点（monomorphic call site）已能内联，故接近 C。

## 计时口径
- 四路均内部计时纯计算（C: `clock_gettime` / JS: `hrtime` / as3compiler: `Date.getTime` / 原生 AS3: `getTimer`）。
- 原生 AIR 的 `adl` 启动开销（约 2.6s）不计入。
- 累加采用 `if (sum >= 1e9) sum -= 1e9` 有界校验和，保证 2000 万次累加不溢出 32 位整型且四路结果精确一致。
- 「包进函数」的对照与 §2 的全部变体 A/B 由**临时变体**测得，脚本与产物留 `temp/bench/oopattr/`
  （gitignore 目录，不复现则无意义）；基准本身保持顶层脚本写法不变。
