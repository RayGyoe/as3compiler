# benchmarks — as3compiler 性能基准

对比四种实现同一算法时的性能：**C**、**JavaScript (Node)**、**as3compiler**（AS3 → C → cc）与
**原生 AS3 (AIR/mxmlc)**。每个子目录含 4 个源文件 + `report.md`：

```
benchmarks/<name>/
├── <name>.c            # C 实现（内部 clock_gettime 计时）
├── <name>.js           # JavaScript 实现（内部 hrtime 计时）
├── <name>.as           # as3compiler 版（纯 AS3，内部 Date.getTime 计时）
├── <name>_air.as       # 原生 AIR AS3 版（内部 getTimer 计时）
├── <name>_air-app.xml  # AIR 描述符（mxmlc/adl 运行所需）
└── report.md           # 该基准的结果与分析
```

## 运行

```bash
# 全部 8 个基准（编译四路 + 各跑 3 次取中位数 + 校验四路结果一致）
python3 benchmarks/run.py

# 只跑指定基准
python3 benchmarks/run.py fib nbody
```

依赖：Node ≥ 22.6、系统 `cc`/`clang`、AIR SDK（通过环境变量 `AIRSDK_HOME` 指向 SDK 的 **`bin/`
目录**（不是 SDK 根目录——`run.py` 拼接的是 `$AIRSDK_HOME/mxmlc`），默认
`/Users/ray.lei/Documents/Software/AIRSDK/AIRSDK_51.4.1/bin`）。

```bash
# 本轮使用的命令（AIR SDK 51.4.1）
AIRSDK_HOME=/path/to/AIRSDK_51.4.1/bin python3 benchmarks/run.py
```

### `binarytrees` −12%：`gc_write_barrier` 被 clang 去内联（阶段一百四十一）

**根因（与 `array` 不同源）**：`gc_write_barrier` 的**函数体逐字节未变**，但 clang 这一版开始把
`gc_in_heap`（cost 135）内联**进屏障**，于是屏障本体内联代价从 `-35` 变成 **275 > 阈值 225**，
**584 个调用点全部外联**（8 项基准都在 580–590 次）。反汇编实证：`make()` 里旧版 0 次、新版
**3 次** `bl _gc_write_barrier`（`make` 27 指令/3 调用 → 31 指令/6 调用）。

**修法（已落地）**：把屏障拆成「可内联的两行 wrapper + 真正外联的慢路径」，慢路径**通过一个
`volatile` 函数指针**抵达。三点实测支撑：① 直接把慢路径写成普通函数调用 → clang 的
「单调用点 static 函数」奖励会把慢路径**内联回 wrapper**，代价原样传递，屏障再次全外联；
② 造第二个直接调用点能骗过它，但只在那个调用点**不被 DCE 掉**时成立（不碰 Array/Dictionary 的
程序会让 `gc_write_barrier_value` 消失，回退**静默复发**）；③ 经 `volatile` 指针的间接调用对
两者都免疫（地址逃逸 ⇒ 永不「只被用一次」，`volatile` 载入 ⇒ 不会被 devirtualize）。
代价是热路径多一次可预测比较，间接调用只在 MARK 期间发生（非 GUI 停世界构建里恒不触发）。
**§2.6 禁令内**：全程未用 `__attribute__`。

**同 C 层 A/B**（40 轮长跑交替，每轮 5×300k 次）：旧形态 4.73 s / 新形态 **4.48 s**，
删掉屏障本体 4.45 s ⇒ 屏障快路径重新变回近似免费。单批基准：`binarytrees` 118 → **104 ms**。

### `strings` −11%：分配热路径上的两处「白付的钱」（阶段一百四十一）

**根因一：`GCT_STRING` 的零填充**。`gc_alloc` 清零对象体是为了「未初始化的数组槽在标记期读到 tag 0
而不是野指针」，但 `GCT_STRING` 是 `gc_scan` 里的 **leaf**（`case GCT_STRING: break;`），
**marker 从不扫描它的字节**，而 `as_str_alloc` 的契约本来就是「调用方自己写结尾 NUL」
（57 处调用点已逐一复核：都是 memcpy+显式 NUL 或 snprintf/strcpy，机械审计 0 例外）。
⇒ 这次清零是纯成本，而字符串是本项目最分配密集的负载（`strings` 每次迭代 16 次分配里 14 次是字符串）。

**根因二：审计门（`gc_audit_gate`）在关闭态仍被调用**。它默认关闭，但调用点无条件调用它——
**每次分配一次**（`gc_alloc` 入口）+ **每访问一个空闲链节点一次**（`gc_find_block` 内层循环）。
关掉时每次调用只做几个判断就返回，可**调用本身**（序言、字符串实参、重查缓存标志）就是全部开销。

**修法（已落地）**：① `gc_alloc` 对 `GCT_STRING` 跳过 memset（`if (type != GCT_STRING)`，含理由注释）；
② 三处 `gc_audit_gate` 调用点改为**就地判缓存标志** `if (gc_audit_mode_cache != 0)`——
这正是同文件 `gc_mark_ptr` 早就用的形态（§5700），`-1`（尚未解析）仍会穿过并在门内解析。

**同 C 层 A/B**（长跑 5×300k，交替 n=10 取 min/median）：memset 一项 **−10.4 ms/轮**、
审计门一项 **−11.4 ms/轮**，合计 **−22 ms/轮**（≈ −9%）；单批基准：`strings` 222 → **198 ms**。

### 本轮顺带证明的三件事（对后续有指导意义）

- **`strings` 对 GC 阈值是反向敏感**：把 `ASC_GC_THRESHOLD` 从 8 MiB 往上调，
  16 MiB → 253 ms、32 MiB → 313 ms、128 MiB → 895 ms（8 MiB 时 226 ms）。
  即 `strings` 的开销在**分配路径**而不在「收得太频」⇒ 阶段八十九·四十七 的「少收更省」结论
  **只适用于 `binarytrees` 那副形状**（存活集非空），不能外推到 `strings`（存活集≈0）。
- **`gc_seg_find` 的每次分配计费（`free_bytes -= ...`）值 ~10.6 ms/轮**，但**不能删**：
  它是段归还判定的唯一账本（漏计会让「该段已空」误真而把活对象的内存还给 OS，就是历史上
  「第二次跑基准 SIGSEGV」那个 bug）。本轮只是把它**留在原地**、先摘掉审计门。
- **每类型记账（`gc_dbg_type_bytes[24]`/`count[24]`）值 ~5 ms/轮（2%）**，但它同时是
  `gc_trigger()` 自适应阈值的 O(1) 数据源，且 `ASC_GC_STATS` 的类型分解靠它 ⇒ **本轮不动**
  （2% 换掉一条诊断能力不划算）。

### `array` +52% 回退的根因与修复（阶段一百四十）

热循环 `sum += a[j]` 的生成 C 是 `as_v_int_cast(as_add_v(as_v_num(g_sum), as_array_get(...)))`。
**阶段一百三十四（commit `66b065c`）** 给 `as_v_to_number` 加了 `tag==4 → as_obj_to_number` 与
`tag 5/7 → NAN` 两个分支，clang 内联代价升到 **250 > 阈值 225**，于是 `as_add_v` 对**两个操作数**
都发外联调用 —— 反汇编实证 `main` 里 `bl _as_v_to_number` **2 个**（修复后 1 个，只剩真正动态的数组元素），
2000 万次循环 = **4000 万次外联调用**。

**修法**：照搬既有的 `as_v_int_cast` 可内联包装模式，给 `as_add_v` 的数值分支加 tag 1/2 快路径
（`(a.tag == 1 || a.tag == 2) ? a.num : as_v_to_number(a)`，两个操作数各一）。

**同 C 层 A/B**（同一份生成 C，只改这一处）：还原旧形态 → 191–192 ms；修复版 → **118–119 ms**
（回到 v0.4.93 的 118 ms），`result=959996015` 不变。⇒ 本轮 `array` **122 ms**（C 列同期 +15%，归一化后
**优于**基线 5.90×）。附带新增 `test/unit/inline.ts`（`unit: inline/HotPath`）做**汇编级内联退化护栏**：
`cc -O2 -S` 断言 `main` 里 `as_add_v` 全内联、`as_v_to_number` 外联 ≤1 次（反向验证会在回退时变红）。

### `strings −14%` 与 `binarytrees +6%` 的同源归因：`gc_alloc` 空闲链按尺寸分级（阶段一百二十）

`strings` 的 570 万次分配里字符串约占 420 万，而 `gc_alloc` 原来的空闲链是**单条 first-fit**
（从头线性找第一个够大的块）⇒ 表越长越慢（阶段一百一十九 归因：`as_str_alloc` 换 arena bump
即 248 → 152 ms ⇒ 每次分配 ≈21 ns、合计 ~93 ms、占 38%；关掉回收反而慢 3×）。本轮把空闲链
按**尺寸分级**（`gc_free_small[16]` / `gc_free_mid` / `gc_free_big`，32 B 一级、上限 512 B），
`gc_find_block` 从请求尺寸所属的类**向上爬**到第一个能放下的块（块尺寸**不取整**、精确尺寸，
`free_bytes` 段账目不变）。

**受控 A/B（同一份生成的 C，只改分配器；`temp/sc/`，每行 ≥3 次读数）**：

| 变体 | strings (ms) | binarytrees (ms) |
|---|---|---:|
| 老的两分链（`free_small` + `free_big`） | 248 / 251 / 273 | 97 / 98 |
| **尺寸分级（本轮）** | **211 / 211 / 212** | **103 / 104** |
| 反向实验：分级但**只搜精确类**（不爬类） | — | **442596（7m23s，4300×）** |

三条结论：① 分级让小分配从「链长线性退化」变成**类内 O(1) 命中** ⇒ `strings` **−15%**；
② `binarytrees` **+6%** 是同一容器内的代价（每块分类 + 多链头读取；该基准的箱子尺寸集中，
老的单链 LIFO 恰好最省），故整体是**净收益**（8 项里 1 项 −14% / 1 项 +6% / 6 项持平）；
③ **爬类是承重的**：反向实验（只搜请求尺寸的精确类、不向上爬）让 `binarytrees` 从 103 ms
变成 **442596 ms**，因为它再也复用不到偏大的块、只能一路切新段 —— 这条**不是**可以去掉的复杂度。

### 动态槽强转家族（阶段一百二十）：为什么 `array` 没有回退 45%

同轮的 `unboxAny`/`toInt32Expr` 家族收口（「动态值 → 具体标量槽」一律走 AS3 强转，
`int("10x")` = 0、`int("0x10")` = 16、`var i:int = arr[0]`（`"7"`）= 7，见 `README-CN.md`）
在 `array` 的热循环上每轮多一次强转调用（2000 万次）。**直接调用通用强转助手会让 clang 拒绝内联**
（`-Rpass-missed=inline`：`inline cost: 595` > 阈值 `325`，实测 116 → **169 ms**），
故新增可内联小包装 `as_v_int_cast`/`as_v_uint_cast`（tag 1/2 直取、其余 tag 转交），
实测 **117–118 ms** ⇒ `array` 本轮 **118 ms**，与 v0.4.92 的 119 ms 持平（相对 C 仍是 5.90×，
主因仍是阶段一百一十九 分析的那条 `int`↔`double` 往返携带依赖链，非本轮回归）。

### `oop` +78% 的根因：`unboxAny` 的对象解箱补上了 `#1034` 运行时检查（阶段一百一十九）

`oop.as` 的热循环里有一次**动态值 → 具名类变量**的赋值：

```as3
var s:Figure = shapes[j % 192];     // shapes:Array ⇒ 元素静态类型是 *
```

按 AVM2 语义，把 `*` 赋进 `Figure` 槽是一次**运行时强制转换**，类型不符要抛 `#1034`。
本轮（v0.4.92）在 `unboxAny` 的 `object` 分支补上了这个检查 —— 此前发射的是**未检查**的
`((Figure*)as_v_obj_val(...))`，正是遗留表第 1 项「静默把装箱指针当对象解引用」（§2.4 红线）：

```c
/* v0.4.69：未检查（语义错误） */
g_s = ((Figure*)as_v_obj_val(as_array_get(g_shapes, as_int_rem(g_j, 192))));
/* v0.4.92：vtable 祖先链校验，不符抛 #1034 */
g_s = ((Figure*)as_v_req_inst(as_array_get(g_shapes, as_int_rem(g_j, 192)), &Figure_vt, "Figure"));
```

即 **v0.4.69 的 55 ms 是一份跳过了类型检查的读数**；98 ms 才是语义正确的代价 ——
与 `mandelbrot` 的 `-ffp-contract=off` 同类，都属「AS3 语义优先于 C 语义」的可测代价。

**AIR 确证该检查必需**（`temp/pkgA/arrcoerce`，adl 51.4.1 双端探针 **0/6 行差**）：`Array` 中的
`Number`/`String`/对象字面量落入 `Sprite` 槽 ⇒ `#1034`；子类 `MovieClip` ⇒ 通过（**所以必须
走祖先链校验，不能只比较 vtable**）；`null` ⇒ 通过。

## 结论

- **不分配堆的项仍贴着 C**：`fib` 1.00×、`nbody` 1.06× 落在噪声内；`oop`（1.84×）的两重归因
  已定死（顶层脚本变量为全局 ~8%，加上本轮新增的 `#1034` 对象解箱检查 ~78%，见其 `report.md`）。
  这再次验证「前端只翻译、优化交给 `cc -O2`」的路线在调用密集与字段访问密集型负载上不损失性能 ——
  **不分配堆的两项都不超噪声**；其余超出 C 的项（`oop`/`mandelbrot`/`binarytrees`/`strings`/`array`）
  均已在各自条目里逐一定因，**没有一项是 codegen 退化**。
- **浮点密集的两项不能被「AOT vs C」直接比较**：`mandelbrot`（1.27×）与 `spectralnorm`（0.79×）
  的 C 基线用 clang 默认 FMA 收缩，我方用 `-ffp-contract=off`（阶段九十六，语义要求）。
  仅切换这一个标志、同一份生成 C 的实测：mandelbrot 119 → 93 ms、spectralnorm 34 → 45 ms。
  即 **AOT 在 mandelbrot 上慢、在 spectralnorm 上快，同一开关、方向相反**；
  这是循环形状（依赖链 vs 两次循环不变乘加）与 FMA 交互的结果，不是 codegen 质量变化。
- **`spectralnorm`（0.80× C，17.92× 原生）是 AOT 相对原生差距最大的一项**：`Vector.<Number>`
  单态化为连续 `double` 数组，索引读写是直接访存；AVM2 的 `Vector` 索引每次都要走方法分派，
  密集内层循环无法被有效优化。
- **`binarytrees`（1.42× C，3.40× 原生）**：v0.4.3 已把离屏 GC 下限抬到 8 MiB（1 MiB → 8 MiB，
  293 → 97 ms）。剩下的 1.42× 由两块构成：**① 基准自身 20 次显式 `System.gc()` 的真实成本**
  （见下 GC 专项，v0.4.3 结论）；**② v0.4.93→v0.4.111 期间漂进来的 `gc_write_barrier` 去内联**
  （+13%），已于 v0.4.112 用「可内联 wrapper + `volatile` 函数指针指向外联慢路径」压掉
  （118 → 104 ms），回到 v0.4.93 的 1.43× 基线以内。
- **`strings`（2.44× C，4.59× 原生）**：**96% 在 `split().join()` 的分配上**，不是字符串操作、
  也不是回收。变体归因：去 split/join ⇒ 10 ms、零分配下限 ⇒ 0 ms；而 5,700,645 次 `gc_alloc`
  里 ≈420 万次是字符串分配，把 `as_str_alloc` 改走 arena bump 即 **248 → 152 ms**（⇒ **每
  次分配 ≈21 ns、合计 ~93 ms、占 38%**）；`gc_collect` 计时显示 60 次回收合计仅 ~50 ms。
  关掉回收反而 **慢 3×（733 ms）**，因为空闲链不再复用、first-fit 遍历随堆线性变长 ——
  说明单次分配成本的主因是 **free-list 遍历**，而它属于**运行时实现**、可以优化（size-class
  分级空闲链），**不属于「前端做优化」**。v0.4.112 在**每次分配的固定开销**上又砍掉两笔
  「白付的钱」：`GCT_STRING`（leaf，marker 从不扫它的字节）不再零填充、审计门在关闭态
  不再被调用，合计 −9%（222 → **198 ms**，AOT/C 2.91 → **2.44**，优于 v0.4.93 的 2.59 基线）。
  **注意其阈值敏感方向与 `binarytrees` 相反**：调大 `ASC_GC_THRESHOLD` 只会更慢
  （16/32/128 MiB → 253/313/895 ms），即它的开销在分配路径而非回收次数。
- **`array`（5.55× C）的根因是 `int` 累加器被迫走 `double` 域**，不是每元素体积：
  `sum:int += a[j]`（`a[j]:*`）按 AS3 语义必须翻译成动态加法，于是每轮 `int→double→int`
  往返构成 **循环携带依赖链（~12 周期）**。变体归因：保留全部 24 B 装箱读与 ≈480 MB 搬运、
  **只去掉该往返 ⇒ 119 → 21 ms**（等效带宽从「≈4 GB/s」跳到 ≈22.8 GB/s）。纯 C 同写法对照
  （20 M 次、同访存）：`s = s + a[j]` **30 ms** vs `d = (double)((int)d + a[j])` **116 ms**。
  守卫 0 ms、边界检查 3 ms、`as_add_v`/`as_array_get`/`as_v_to_number` 全部被 `-O2` 内联。
  **AIR 自己 133 ms（6.05× C）**，同样付这笔语义代价。
  > **修正旧结论**：v0.4.92 前的报告把 5.41× 归为「带宽受限」（480 MB ÷ 116 ms ≈ 4.1 GB/s
  > 与 C 同量级）——该推理已被证伪：保留等量访存、只去依赖链即 5.5× 提速（22.8 GB/s），
  > 说明旧读数是被**延迟**压出来的，不是带宽上限。
- **`oop`（1.84× C，6.66× 原生）**：类继承被翻译为 C 结构体 + vtable，`override` 虚调用变成
  一次函数指针间接调用、字段访问变成一次直接内存访问。两重归因：**① ~8%** 来自
  **顶层脚本变量被正确提升为全局**（v0.3.130 的语义修复，把热循环放进函数后即为 0.96× C）；
  **② +78%** 来自本轮（v0.4.92）在 `unboxAny` 补上的 **`#1034` 对象解箱校验** ——
  `var s:Figure = shapes[i]`（`Array` 元素静态类型是 `*`）本就要做运行时强制转换，
  `adl` 同样抛 `#1034`。前一轮的 55 ms 是**跳过该检查**的读数。
- **原生 AS3 全程最慢（3.66–14.58×）**：AVM2 的动态分派、装箱与 `Vector` 索引开销。
  （区间端点：`mandelbrot` 3.66× … `spectralnorm` 14.58×，均为 AIR/C 的绝对比值。）

## GC 回收策略专项（v0.4.3 结论；v0.4.112 对阈值敏感性的**反例**见顶部）

> 本节全部数据来自 **v0.4.3**（2026-09-27）。本轮（v0.4.69）无 GC 触发策略改动，
> `binarytrees` 95 ms / `strings` 241 ms 与本节结论一致，故原文保留作历史记录。

### 0. v0.4.3 的改动：离屏下限由 1 MiB 抬到 8 MiB + 触发判定缓存

上一轮（v0.4.0）把「非 GUI 自动回收阈值下限偏低」登记进 `TODO.md` 遗留表，本轮先做**计时分解**
再定方案（阶段八十九·四十七）。机制（`src/runtime.ts`）：

```c
// 非 GUI 触发：从未派发过帧 → 没有别的东西会调用 gc_step()，于是这里自己收。
if (!gc_frame_driven && gc_inc.state == GC_IDLE) {
    if (gc_trigger_next == 0) gc_trigger_next = gc_trigger();   // 缓存，仅在回收后失效
    if (gc_bytes_allocated >= gc_trigger_next) gc_collect();    // stop-the-world
}
...
size_t floor = gc_frame_driven ? gc_threshold : GC_NONGUI_FLOOR;  // 1 MiB vs 8 MiB
return adaptive > floor ? adaptive : floor;
```

两条路径的目标本就相反，此前却共用同一个下限：

| 路径 | 目标 | 合适下限 |
|---|---|---|
| 帧驱动（`gc_step`，Starling 等） | 每帧停顿有界、小堆要及时开始切片 | 1 MiB（**未改**） |
| 非 GUI（`gc_alloc` 的 stop-the-world） | 无帧时限，要摊薄**单次固定开销** | **8 MiB**（本轮改） |

### 1. 计时分解：一次回收的开销由「重新标记存活集」主导，与累积了多少垃圾无关

方法：临时在 `gc_collect()` 内按相位计时（`prep` = `gc_new` 归位 + `gc_all` 全链置白、
`internal`/`user`/`stack` = 三类根、`drain` = `gc_mark_drain`、`sweep`、`finish`），
`ASC_GC_STATS` 门控 + `atexit` 汇总；用 `ASC_GC_THRESHOLD` 扫不同回收间隔（**测完即删**）。

**binarytrees**：

| 相位 / 单次 | 1 MiB | 4 MiB | 16 MiB | 64 MiB |
|---|---:|---:|---:|---:|
| 回收次数 | 154 | 45 | 24 | 20 |
| `drain`（标记） | **1.08 ms** | 1.04 | 1.02 | 1.03 |
| `sweep` | 0.34 | 0.51 | 0.75 | 0.85 |
| `prep` | 0.20 | 0.25 | 0.34 | 0.37 |
| `stack`（保守栈扫描）**总计** | **0.3 ms / 154 次** | 0.1 | 0.1 | 0.0 |
| **GC 总计** | 247–258 ms | 81 | 50 | 45 |

三点结论：

1. **`drain` 单次开销恒定（≈1.05 ms）**：它 ∝ 存活集（~1 MB，不随间隔变化），与「上次回收后
   累积了多少垃圾」无关。所以**总 GC 时间 ≈ 次数 × 常数**，唯一杠杆是「少收」。
2. **`sweep`/`prep` 只随间隔缓涨**：空闲块会被复用，`gc_all` 长度约等于存活集，故这两项也近似
   ∝ 存活集（不是 ∝ 垃圾量），只是间隔越大保留的块越多。
3. **保守栈扫描完全不是瓶颈**：154 次 `gc_mark_stack` 合计仅 0.3 ms（0.3%），此前怀疑的
   「深栈逐字扫描」被排除。

`strings` 是另一副形状：存活集≈0 ⇒ `drain` = 0，开销全在 `sweep`（∝ 垃圾量），所以它的收益随
间隔增长得**更缓**（1 MiB → 74 ms，16 MiB → 46 ms，256 MiB → 29 ms），但方向一致。

### 2. 修法一：下限按路径二分（`GC_NONGUI_FLOOR` = 8 MiB）

| 离屏下限 | binarytrees | strings | bt 峰值 RSS |
|---|---:|---:|---:|
| **1 MiB（改前）** | 287 ms | 258 ms | 9 MB |
| 4 MiB | 120 ms | 232 ms | 12 MB |
| **8 MiB（选定）** | **97 ms** | **229 ms** | **15 MB** |
| 12 MiB | 88 ms | 236 ms | 19 MB |
| 16 MiB | 88 ms | 218 ms | 23 MB |
| 24 MiB | 82 ms | 239 ms | 30 MB |

- `binarytrees` 在 **12 MiB 后饱和**（88 ms），8 MiB 已拿到 96% 的可得收益，而内存开销只有
  16 MiB 方案的一半；`strings` 曲线非单调（218–239 ms 波动），8 MiB 与 16 MiB 无实质差别。
- **代价**是离屏程序最多多驻留一块下限的垃圾（峰值 RSS 9 → 15 MB）；内存断言最严的
  `examples/gc_bytes.as` 在 8 MiB 下**原界即通过**。
- 12 MiB 以上不再有收益，是因为离屏触发此时已退化到与「基准自身的显式 `System.gc()`」同频。

### 3. 修法二：触发阈值缓存（`gc_trigger_next`）

`gc_trigger()` 需要汇总 24 个 `gc_dbg_type_*` 计数，而 `gc_alloc` **每次分配**都要判定一次。
用 `ASC_GC_THRESHOLD`（`override_threshold` 短路该求和）与默认路径交错对比，稳定差
**87/88 ms vs 98 ms**——也就是说**上一轮报告里被当成「批次波动」的 293 vs 277 ms 其实是这个开销**。
现在把阈值缓存进 `gc_trigger_next`，只在 `gc_finish_cycle`（存活集刚变）失效重算，
每次分配退回一次整数比较。

### 4. 一个硬上限：floor 不能 ≥ 回归测试的总 churn

`examples/gc_alloc_threshold.as` 的总垃圾量实测 **17.8 MB**（1000 次 `churn`）。floor 一旦 ≥ 该值，
该测试里**永远不会触发自动回收**、断言随之失去意义（32 MiB 时实测 `afterChurn` = 17.77 MB，
即完全没回收）。所以本旋钮的可用区间是 **≤ 16 MiB**，8 MiB 落在安全侧。该测试的峰值界已同步改为
`FLOOR_BOUND`（8 MiB 下限 + 一块余量），注释里的过期数字（「1 MiB 下限 / 每轮 50 KB / 共 5 MB」）
也按实测更正；`gc_bytes.as` 不改。

### 5. GUI / 帧路径零影响（论证）

唯一改动是下限选择：`gc_frame_driven` 为真时仍取 `gc_threshold`（1 MiB，与改前相同）；
`gc_trigger_next` 只被非 GUI 分支读取，帧路径仍每帧直接调用 `gc_trigger()`。因此 Starling 等
帧驱动程序的每帧回收频率与内存目标不变（`test.ts` 全部 GUI/离屏示例通过）。唯一可观测差异在
**首帧派发之前**的窗口（GUI 程序启动瞬时也走离屏分支），其阈值由 1 MiB 变为 8 MiB。

### 历史修正

- **「多出的耗时就是 GC 停顿」是按相位分解后才看清的错误归因**（v0.4.0 报告仍未纠正）：

  当时对 `binarytrees`/`strings` 的默认值 272/293 ms 只归因于「真实 GC 停顿」，把**因果搞反**了——
  按相位分解，其中绝大部分是「每次回收都要重新标记存活集」的固定成本**乘以过大的次数**。
  本轮把次数降下来，两项同时变快，`strings` 的内存也一并下降（完全关闭自动回收是 712 ms / 453 MB）。
- 上一轮把 `binarytrees` 的 **293 vs 277 ms** 记为「批次波动」，**实为 `gc_trigger()` 逐次汇总
  24 个计数的开销**，本轮已由 `gc_trigger_next` 消除。
- `array` 的 **C 基线曾误记为 43 ms**：那次测量发生在 `array_asc` 因 `gc_alloc` 超大分配死循环
  而占用 ~415 GB 虚拟地址空间的同一时段，整机内存压力污染了所有读数。该死循环已修复
  （现为超大请求分配专用段），C 基线稳定在 21–22 ms。
- `strings`/`binarytrees` 的 **187 / 80 ms（v0.3.128 记录）现仅对应「关闭自动回收」**；
  272 / 293 ms 对应 **1 MiB 下限**（v0.3.137–v0.4.0）；v0.4.3 起为 **229 / 97 ms**（8 MiB 下限）。
  三者不是同一配置，不可直接比较。
- `mandelbrot` 的 **95 → 122 ms 曾是一个无归因的「回退」**，本轮定位到阶段九十六的
  `-ffp-contract=off`（AS3 语义要求）——不是 codegen 退化。此前几轮把它归为「持平」是
  因为 v0.4.3 报告跑在阶段九十六**之前**。同理，`spectralnorm` 的 48 → 38 ms 也是同一标志。
- **浮点基准的 C 基线自阶段九十六起不再是等价参照**：C 侧由 `run.py` 用裸 `cc -O2` 编译
  （clang 默认 `-ffp-contract=on`），我方带 `-ffp-contract=off`。要比较 AOT 与 C 的**代码质量**，
  应给 C 侧也加 `-ffp-contract=off`（或把我方生成 C 去掉该标志跑 A/B，本轮两行数据即这样得到）。
- **原生 AS3（AIR）列的绝对值跨 SDK 版本不可比**：v0.4.3 报告用 51.3.4，本轮用 51.4.1。
- **`binarytrees`/`strings` 的「GC 区残差」不是一个东西（v0.4.112 拆定）**：v0.4.111 把两项
  合并登记为一行，实际是两个**独立**原因——`binarytrees` 是 `gc_write_barrier` 被 clang 去内联
  （模块增大后的内联预算效应，与 GC 核无关），`strings` 是分配路径上的**固定开销**（`GCT_STRING`
  零填充 + 审计门调用）。两者都不属于「GC 收得太频」，故 v0.4.3 的「少收更省」结论
  对 `strings` 形状**不成立**（实测调大阈值反而更慢），已在该专项标题上标注。
